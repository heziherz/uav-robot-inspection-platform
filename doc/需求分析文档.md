## 2 项目概述

### 2.1 项目背景与现状分析

园区、厂区等封闭管理区域的安防巡检具有**区域大、点位多、重复性高、异常发现要求及时**等特点。传统巡检主要依赖人工步行或车辆巡查，存在以下问题：

1. **覆盖率与时效性不足**：人工巡检难以做到大范围高频覆盖，围墙死角、楼宇顶层、狭窄通道等区域难以抵达；
2. **单视角局限性**：空中视角可以发现大范围异常，但难以判断细节；地面视角细节清楚，但视野受限；
3. **数据分散、闭环困难**：照片、位置、传感器数据、告警记录分散在不同设备或系统中，缺少统一汇聚、存储、检索和分析手段；
4. **复核效率低**：发现可疑目标后缺少自动化的“空中发现 → 地面复核 → 结果归档”联动机制。

本课程项目以园区安防场景为业务原型，建设一套**软件集成仿真平台**，将无人机空中广域巡查与机器狗地面抵近复核的能力通过分布式中间件、分布式存储、检索引擎和负载均衡网关进行企业级系统集成，实现巡检业务的数据闭环。

### 2.2 项目性质与总体约束

> **重要说明**：本项目是**软件集成仿真开发实践**，不要求也不使用真实无人机、机器狗等硬件实体。无人机与机器狗以**仿真模块**形式运行，通过消息中间件与平台完成数据上报和指令流转。课程重点是软件系统集成、中间件部署、分布式存储、消息队列、检索引擎、负载均衡与业务平台开发。

项目总体约束：

| 约束项 | 内容 |
| :--- | :--- |
| 技术组件 | 必须至少覆盖 HDFS、MongoDB/HBase、RocketMQ/Kafka、Nginx、Elasticsearch+Kibana 六类组件 |
| 部署方式 | 允许使用 Docker 单机多容器模拟集群，不要求物理多机 |
| 交付性质 | 可运行的软件原型 + 源代码 + 配置文件 + 文档 |
| 开发周期 | 课内 32 学时，课外建议额外投入不少于 64 学时 |

### 2.3 建设目标

#### 2.3.1 业务目标

构建一套“无人机-机器狗空地协同巡检集成平台”，模拟无人机采集航拍图像、GPS 位置、设备状态，机器狗采集红外图像、环境传感器数据、设备运行状态；平台实现**设备统一接入、巡检任务下发、消息流转、分布式存储、检索分析、可视化展示、负载均衡反向代理**，形成“**高空发现隐患 → 地面复核确认 → 处置闭环归档**”的巡检业务闭环。

#### 2.3.2 技术目标

1. 综合运用分布式文件系统、分布式数据库、高性能消息中间件、负载均衡、分布式全文检索引擎完成异构设备数据汇聚；
2. 打通“设备仿真生产 → 消息中间件流转 → 业务服务消费 → 持久化存储 → 索引检索 → 网关代理 → 前端可视化”完整数据链路；
3. 掌握组件部署调试、消息可靠性、问题排查、系统测试与性能优化方法，理解企业应用集成架构。

#### 2.3.3 素质目标

培养精益求精、追求卓越的大国工匠精神；通过小组协作、文档撰写、技术总结与答辩汇报，提升工程化组织、沟通与总结能力。

## 3 总体业务流程

### 3.1 业务场景假设

1. 巡检园区划分为若干区域/网格，预置巡检点与巡检路线（如：大门、周界围墙、楼宇外墙、设备区、消防通道等）；
2. 无人机可模拟巡航、悬停拍照，上报 GPS、航拍图片（元数据 + 图片文件）、设备状态；
3. 机器狗可模拟进入楼宇楼道、围墙死角、设备区等区域，上报红外图片、温度、可燃气体等传感器数据；
4. 平台预置常见隐患类型，如：人员/车辆闯入、烟火、围栏破坏、设备过热、异常渗漏/积水、环境异常等，仿真设备按设定概率或规则产生告警事件；
5. 隐患处置闭环：值班员对告警进行确认后，可选择对应区域生成“抵近复核任务”并派发给在线机器狗；机器狗到达目标点位复核后上报复核结论（属实/误报/需人工处置），平台归档复核记录并推进告警状态。

### 3.2 核心业务流程

#### 流程 B1：设备接入与状态监控

```text
管理员登记/导入设备档案
      ↓
仿真设备启动 → 向平台发起注册请求 → 平台校验并入库，设备状态置为“在线/待命”
      ↓
仿真设备按周期上报心跳与状态（电量、故障等）
      ↓
平台消费心跳消息并更新状态；心跳超时则自动判定设备“离线”并展示告警提示
```

#### 流程 B2：日常例行巡检任务执行

```text
值班员创建巡检任务（区域/路线、巡检类型、目标设备、计划时间）
      ↓
平台通过消息中间件向目标仿真设备下发任务指令
      ↓
仿真设备消费指令，模拟开始执行（飞行/行走路线模拟），并向平台回执任务开始
      ↓
执行过程中实时上报 GPS/轨迹、图片元数据、传感器数据、设备状态
      ↓
业务服务消费消息：图片文件入 HDFS、结构化数据入 MongoDB、检索数据入 ES
      ↓
任务完成：仿真设备上报完成回执，平台更新任务状态，前端展示执行结果与日志
```

#### 流程 B3：隐患发现与告警处理

```text
无人机/机器狗仿真巡检中发现异常（或按仿真规则触发告警事件）
      ↓
告警消息经消息中间件上报，业务服务持久化并索引
      ↓
值班员在告警列表 / 地图上查看告警（位置、类型、图片、时间、来源设备）
      ↓
值班员确认告警（属实/待核实/误报）
      ↓
如需复核：选择在线机器狗 → 平台下发“抵近复核任务”
      ↓
机器狗执行复核并上报复核结果与红外/可见光证据
      ↓
值班员确认复核结论，处置完成，告警状态关闭归档
```

#### 流程 B4：历史查询与统计分析

```text
值班员/管理员通过前端或 Kibana 按设备、时间、地点、告警类型等条件检索
      ↓
平台从 ES 返回巡检事件/告警记录，从 MongoDB/HDFS 返回详情与图片
      ↓
统计设备在线率、任务完成率、告警趋势、隐患类型分布等并可视化
```

#### 流程 B5：网关统一访问

```text
浏览器（前端页面）、外部客户端 → Nginx（反向代理/负载均衡/限流/安全配置）
      ↓
转发至 Web 前端静态资源 / 后端业务服务集群
      ↓
后端服务通过内部接口访问消息中间件、MongoDB、HDFS、Elasticsearch
```

## 4 系统边界

### 4.1 边界划分原则

为了既满足课程对“设备仿真层也属于本项目交付物”的要求，又让用例模型清晰表达业务交互，本文档区分两层边界：

1. **课程交付系统边界**：本小组交付的完整软件系统包括“仿真设备模块 + 消息中间件 + 业务服务 + 存储/检索组件 + Nginx 网关 + Web 前端”。该边界内的全部组件均由小组开发与部署。
2. **业务平台用例建模边界**：在用例建模中，将“无人机仿真模块”“机器狗仿真模块”作为**与平台交互的外部参与者**，因为它们承担与业务平台不同的职责（数据生产者与指令执行端），其通过消息中间件与平台交换数据。这样处理更清晰地表达“设备接入”“任务下发”“数据上报”等接口型用例。

### 4.2 系统范围内（本系统要做的事）

| 类别 | 具体内容 |
| :--- | :--- |
| 设备仿真 | 无人机仿真：GPS 轨迹、航拍图片元数据、飞行/巡检状态、设备电量与故障模拟；机器狗仿真：路线行走、红外图片元数据、环境传感器（温湿度/气体等）、设备状态、复核结论模拟；多设备并发运行 |
| 设备接入与监控 | 设备注册/台账管理、心跳上报、在线/离线判定、状态查询 |
| 消息流转 | 设备上报消息生产/消费、持久化、分区路由；平台任务指令下发；消息可靠性处理 |
| 分布式存储 | 巡检图片/视频等大文件存 HDFS；设备、任务、告警、状态等结构化数据存 MongoDB（或 HBase） |
| 检索分析 | 巡检事件、告警数据写入 ES；支持按设备编号、时间、告警类型、位置检索与聚合统计；Kibana 可视化 |
| 业务功能 | 巡检任务创建/下发/进度跟踪/日志归档、告警展示与确认、复核派单与闭环、历史查询 |
| 网关与安全 | Nginx 反向代理、负载均衡、基础限流与安全头配置；登录认证与简单权限控制 |
| Web 可视化 | 设备 GIS 地图、设备状态面板、任务管理、告警列表、检索结果、统计图表 |
| 部署与运维 | Docker 容器化部署脚本、组件健康检查、日志查看、基础备份恢复演示 |

### 4.3 系统范围外（本系统不做的事）

以下内容**不属于**本系统实现范围：

| 类别 | 说明 |
| :--- | :--- |
| 真实硬件控制 | 不实现真实无人机的飞控、电机、云台控制、RTK 差分定位；不实现真实机器狗的运动控制、机械臂等 |
| 实体通信链路 | 不实现图传/数传无线链路、基站组网、4G/5G 回传等真实通信设施 |
| 真实视频流处理 | 不做实时视频低延迟直播/转码；只处理仿真图片元数据与文件 |
| 人工智能识别 | 目标检测、烟火识别等 AI 算法非强制内容；隐患通过仿真规则/脚本触发（如后续作为拓展可另行评估） |
| 与第三方安防平台对接 | 不做与真实门禁、摄像头、消防报警等第三方系统的协议对接 |
| 真实地图测绘 | 不接入高精度 GIS 服务，前端以简化坐标/示意图或开源底图实现位置展示 |
| 商业运维能力 | 不涉及生产环境监控告警（Prometheus/Grafana 等）、容灾多机房、真实用户规模运营 |

### 8.2 数据流概览

| 数据流 | 内容 | 途径 |
| :--- | :--- | :--- |
| 上行实时数据 | 心跳、状态、GPS、传感器、影像元数据、告警、回执 | MQ → 业务服务 → MongoDB/HDFS/ES |
| 图片二进制 | 模拟巡检/复核图片文件 | 仿真模块/上传接口 → HDFS |
| 下行指令 | 任务创建、任务下发、复核派单 | Web/业务服务 → MQ → 仿真设备 |
| 查询数据 | 设备、任务、告警、检索结果 | 前端 → Nginx → 业务服务 → MongoDB/ES/HDFS |

### 8.3 数据一致性要求

1. 设备在线状态最终一致：以最新心跳时间为准，允许短时延迟；
2. 重复消费幂等：同一消息（含业务唯一键，如 alarmId、traceNo）重复写入不产生重复业务数据；
3. HDFS 文件与 MongoDB 元数据通过 fileId/objectName 关联，删除/归档需一致处理；
4. 告警状态迁移必须记录时间与操作人，便于追溯。

### 9.1 消息 Topic 设计（示意）

> 若选用 RocketMQ/Kafka，以下 Topic 可兼容实现；Topic 命名仅为建议，最终以架构设计为准。

| Topic | 方向 | 主要消息内容 |
| :--- | :--- | :--- |
| topic_device_heartbeat | 设备 → 平台 | 心跳：deviceNo、timestamp、battery、status |
| topic_device_status | 设备 → 平台 | 状态变更：上线/下线/故障/电量变化 |
| topic_device_gps | 无人机 → 平台 | GPS/轨迹：deviceNo、lat/lng、altitude、speed |
| topic_device_media_meta | 设备 → 平台 | 影像元数据：fileId、deviceNo、taskId、type、坐标、hdfsPath |

| topic_device_alarm | 设备 → 平台 | 告警事件：alarmId、type、level、位置、证据 |
| topic_platform_command | 平台 → 设备 | 巡检/复核任务指令 |
| topic_device_task_ack | 设备 → 平台 | 任务回执：开始/进度/完成/失败 |
| topic_device_task_log | 设备 → 平台 | 执行阶段日志 |

分区建议：以 `deviceNo` 作为分区键，保证同一设备消息有序；告警/任务类消息按业务 ID 幂等去重。

### 9.3 前端与网关接口

1. Web 静态资源与后端 API 均通过 Nginx 统一入口访问，配置跨域与转发规则；
2. 浏览器与后端通过 JSON 交互；实时刷新可采用定时轮询或 WebSocket；
3. Kibana 通过独立端口提供给运维人员访问（或经网关转发），作为数据可视化入口之一。

### 9.4 设备侧接入接口说明

设备仿真模块与平台之间同时支持：

1. **注册接口**：仿真设备启动时调用 REST 注册接口（或发送注册消息）完成设备接入；
2. **消息上报**：心跳、遥测等按周期通过 MQ 发送；
3. **指令消费**：订阅 `topic_platform_command` 消费任务指令，并发送回执到任务回执 Topic；
4. **指令消息协议**：统一 JSON 格式，含 `msgId`（幂等键）、`type`、`timestamp`、`deviceNo`、`payload` 等字段。

## 12 验收与测试建议

### 12.1 验收主线（用于答辩演示）

1. **数据链路演示**：启动仿真设备 → 观察 MQ 控制台消息收发与持久化 → 数据在 MongoDB/HDFS 可查；
2. **图片存储演示**：模拟图片上传 HDFS，可通过查询/下载验证；
3. **检索演示**：写入多条告警/巡检记录后，按设备、时间、类型、位置检索返回正确结果，Kibana 仪表盘可见；
4. **任务闭环演示**：创建巡检任务 → 设备执行 → 产生告警 → 确认并发起机器狗复核 → 复核结果回填 → 告警闭环归档；
5. **网关演示**：通过 Nginx 统一入口访问前端/API，验证反向代理与负载均衡日志。

### 12.2 测试类型与最低要求

| 测试类型 | 最低要求 |
| :--- | :--- |
| 功能测试 | 覆盖全部 P0 用例的通过路径与关键异常路径（离线、重复、失败重发） |
| 接口测试 | 核心 REST 接口（认证、设备、任务、告警、检索、文件）正反向用例 |
| 消息可靠性测试 | 生产-消费完整性、重启后消息不丢、重复消费幂等 |
| 性能测试 | 3+3 设备并发运行下的消息吞吐、任务下发延迟、检索响应记录 |
| 回归测试 | 对缺陷修复项重新执行相关用例并记录结果 |

### 12.3 测试报告要求

按已有“测试用例”模板扩充并记录：用例编号、测试模块、测试标题、前置条件、步骤、预期/实际结果、测试状态、备注（BUG 现象与修复说明），最终纳入课程设计报告。

## 13 假设、约束与风险

### 13.1 主要假设

1. 采用选题 1“园区安防空地协同巡检集成平台”作为业务场景，业务与设备数据均为软件仿真；
2. 巡检图片使用程序生成的模拟图片或预先准备样例图片，不追求真实图像质量；
3. GIS 展示以简化坐标或示意图底图实现，不接入商业地图服务；
4. 消息中间件在 RocketMQ 与 Kafka 中最终选择其一，本需求文档的 Topic 设计兼容两者；
5. 结构化分布式数据库默认选型 MongoDB；如小组论证选用 HBase，需求内容不变，仅影响数据建模与实现；
6. 前端页面支持 2 个角色（值班员、管理员）即满足 P1 权限要求；运维人员可仅通过 Kibana/命令行完成运维用例。

### 13.2 主要风险与应对

| 风险 | 影响 | 应对措施 |
| :--- | :--- | :--- |
| 多组件版本兼容问题 | 部署失败、联调受阻 | 统一 Docker 镜像版本；参考官方文档；预留排错时间 |
| 单机资源不足 | 集群节点/容器资源紧张 | 精简节点数量、控制演示数据量；分模块部署验证 |
| MQ Topic/消息格式不一致 | 上下游数据对不上 | 先定 Topic 与 JSON 协议再开发；保留样例消息脚本 |
| 消费重复/丢失 | 数据不一致 | 消息幂等键、消费确认、重试与日志留痕 |
| 时间紧、联调复杂 | 演示不完整 | 尽早做最小链路联调（仿真→MQ→存储→前端），再逐步扩展功能 |
| 演示数据不稳定 | 现场演示效果差 | 提供可重复的初始化脚本与“一键复位”脚本，答辩前预演 |
