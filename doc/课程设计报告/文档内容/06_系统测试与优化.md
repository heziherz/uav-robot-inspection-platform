### 6.4.2 关键用例的实测证据

**（1）TC-005 影像归档 —— HDFS 目录结构**

```text
/uav/media/
  ├── DOG-001/  DOG-002/  DOG-003/
  └── UAV-001/
        ├── 20260914/   133 个文件
        ├── 20260915/    24 个文件

```

**结论**：完全符合契约规定的路径规范 `/uav/media/{设备编号}/{yyyyMMdd}/{fileId}.jpg`，验证了"按设备与日期分区"的设计目标。

**（2）TC-012 任务执行过程 —— 状态机推进**

```text
  +1s   status=DISPATCHED  progress=0        ← 指令已投递，等待设备响应
  +2s   status=RUNNING     progress=0        ← 收到 STARTED 回执
  +5s   status=RUNNING     progress=50       ← 收到 PROGRESS 回执
  +8s   status=FINISHED    progress=100      ← 收到 FINISHED 回执

回执流水：STARTED(0) / PROGRESS(50) / FINISHED(100)
```

**结论**：六态状态机按设计推进，且 `DISPATCHED` 与 `RUNNING` 的区分得到验证——前者表示"指令已发出但设备未响应"，后者表示"设备确认开始执行"。

**（3）TC-014 回执超时 —— 说明**

由于"设备在线时下发、随即失联"的时间窗口仅约 1 秒（设备在 1 秒内即回执），无法稳定构造该场景。实测采用**直接构造"已下发且已超时"的任务状态**，验证超时扫描逻辑本身。这与用例意图一致，特此说明。

**（2）消费滞后（LAG）**

**结果**：消费组 `platform-service-group` 各分区 **LAG 全程为 0**，后端消费完全跟得上生产。

**（3）网关转发开销**

| 请求类型 | 实测耗时 |
| :--- | ---: |
| Nginx 静态资源 | 10.3 ms |
| Nginx → 后端 API 转发 | 4.0 ms |

### 6.6.2 优化验证：分区数提升的效果

这是本轮性能优化的核心内容。

**优化前的问题**：6 个上行 topic 的分区数**均为 1**。而 Kafka 的**并行单位是分区**，因此单个 topic 的消费并行度被物理限制为 **1**——`concurrency` 调大了也没有多余分区可分。

**优化措施**（两项必须同时做）：

```properties
# deploy/docker-compose.yml
KAFKA_NUM_PARTITIONS: 3

# platform-service/application.properties
spring.kafka.listener.concurrency=3
```

**表 6-7 优化前后对比**

| 项 | 优化前 | 优化后 |
| :--- | :--- | :--- |
| topic 分区数 | 1 | **3** |
| 消费并发度配置 | 未配置（默认 1） | **3** |
| **单个 topic 的消费并行度** | **1**（硬上限） | **3** |
| 消费者实例数 | 6（2 实例 × 6 监听器） | 36（2 × 6 × 3 并发） |
| 分区总数 | 6 | 18 |

**说明**：分区数**只能增加不能减少**，因此该优化在已部署环境中通过 `deploy/init/alter-topics.ps1` 脚本执行；新环境由 `KAFKA_NUM_PARTITIONS` 在创建 topic 时自动生效。

### 6.6.3 优化验证：后端双实例与负载均衡

**验证方法**：连续请求，观察响应头 `X-Upstream`（Nginx 配置中新增，用于回传实际处理请求的后端地址）。

**表 6-8 负载均衡实测分布**

| 请求次数 | platform-service-1 | platform-service-2 |
| ---: | ---: | ---: |
| 20 | 16 | 4 |
| 100 | 49 | 51 |
| 100 | 50 | 50 |
| 30（故障恢复后） | 15 | 15 |

**结论**：长期分布精确均衡。

> **关于 20 次时的 16:4**：Nginx 采用 `worker_processes auto`（28 个 worker），其**轮询计数器是每 worker 独立维护**的。小样本下请求被内核分配到 worker 的分布不均，会导致观测到的后端分布出现偏差；样本增大后趋于精确均衡。这是 Nginx 的既有行为，不是配置问题。

**故障转移验证**：停掉 `platform-service-2` 后，请求全部转发到存活的实例，**服务全程可用**（返回 401 = 接口正常响应）。其中一次响应头显示 `172.18.0.7:8080,`（逗号表示"先尝试该实例、失败后回退"），是 Nginx 首次探测到故障实例的正常行为。

## 6.7 测试发现的问题与修复

本轮测试共发现并修复 **3 个缺陷**。以下按发现顺序记录。

### 问题 1：异常处理不统一，业务校验失败返回 500 ★

**发现方式**：接口测试 IT-02（错误密码登录）。

**现象**：登录密码错误时返回 `HTTP 500` 而非 `401`。

**排查过程**：

1. 查看后端日志，发现抛出的异常无人接住：

   ```text
   java.lang.IllegalArgumentException: 用户名或密码错误
       at com.uav.platformservice.service.AuthService.login(AuthService.java:42)
   ```

2. 全项目扫描 `throw` 语句：共 **31 处，但只有 `TaskController` 有一个 `@ExceptionHandler`**。
3. 关键认知：`@ExceptionHandler` 是**控制器级**的，只对声明它的 Controller 生效——其余模块的校验失败全部落到 Spring 兜底，返回 500。

**影响范围**（远大于单个登录接口）：

| 模块 | 后果 |
| :--- | :--- |
| 登录 | ❌ 500 |
| 用户管理（8 处校验） | ❌ 全部 500 |
| 设备 / 任务 / 告警 / 影像的资源校验 | ❌ 500 |
| 任务服务（`TaskController` 有处理器） | ✅ 400 |

**修复方案**：引入三个专用异常 + 全局处理器。

| 新增 | 映射 | 语义 |
| :--- | :---: | :--- |
| `BusinessException` | **400** | 业务校验失败（参数非法、状态不允许） |
| `AuthException` | **401** | 认证失败（密码错误、账号停用） |
| `NotFoundException` | **404** | 资源不存在 |
| `GlobalExceptionHandler` | — | `@RestControllerAdvice` 统一处理 |

**关键设计决策**：**只拦截这三类，其余异常放行**。

> 项目原先把"业务校验失败"与"服务端内部错误"**混用了同一种异常类型**
> （`IllegalStateException` / `IllegalArgumentException`）。
> 若一刀切映射为 400，会把 `消息发送失败`（Kafka 故障）、`JWT 签名失败` 这类
> **真实的服务端故障误报成"客户端请求有误"**，排查时被严重误导。
>
> 因此拆分为两个明确的类型：**业务问题 → 400/401/404；服务端故障 → 保持 500**。

**修复过程中发现的次级问题**：第一轮替换时使用了 `throw new XxxException(` 这一模式，**漏掉了 `.orElseThrow(() -> new XxxException(...))` 的写法**，导致"下发不存在的任务"仍返回 500。该问题由**异常状态码复验**抓出（原有的 23 条接口用例不覆盖"资源不存在"路径）。

### 问题 2：资源不存在返回 200 而非 404

**发现方式**：异常状态码复验。

**现象**：`GET /api/devices/NOT-EXIST` 返回 **200 + 空响应体**。

**原因**：`DeviceService.find()` 使用 `orElse(null)`，接口无法区分"没有这个设备"与"请求成功但没数据"。

**修复**：改为 `orElseThrow(() -> new NotFoundException(...))` → 返回 404 与明确消息。

> **排查中同步确认无需改动的**：另有 7 处 `orElse(null)` 属于**正常业务分支**
> （例如心跳处理中"设备不存在"表示"新设备首次上报，需自动注册"），
> **不能一律改成抛异常**。这提示：同一写法在不同上下文中语义不同，需逐一判断。

### 问题 3：`.gitignore` 规则误伤正式文件（非代码缺陷）

**发现方式**：提交测试脚本时，发现其未出现在待提交列表。

**现象**：`.gitignore` 中两条规则

```gitignore
性能测试/         ← 无前导斜杠，会匹配【任意层级】的同名目录
deploy/test/
```

导致以下内容**一直未进入版本库**，组员拉取代码时无法获得：

| 内容 | 规模 |
| :--- | :--- |
| `doc/性能测试/` 三份文档 | 约 1300 行 |
| `deploy/test/` 三个脚本与载荷 | 约 900 行 |

而仓库根目录**并没有「性能测试」文件夹**——该规则 100% 是误伤。

**修复**：删除 `性能测试/` 规则；`deploy/test/` 收窄为 `deploy/test/results/`（仅忽略实验产出的 CSV）；补回全部 9 个文件。

> **经验**：`.gitignore` 中写无前导斜杠的目录名会匹配**任意层级**。
> 用于忽略"某个特定目录"时应写绝对路径（如 `/xxx/`），否则容易误伤同名子目录。

| # | 优化项 | 措施 | 实测效果 |

| 9 | **时序集合 + TTL** | 遥测数据改用时序集合 | 存储与索引体积降低，7 天自动过期 |
| 10 | **列表接口服务端分页** | 全量返回 → 服务端分页 | 告警列表响应体由 352 KB 降至数 KB |
| 11 | **任务编号原子化** | 毫秒时间戳 → 数据库原子计数器 | 消除并发场景下的编号碰撞缺陷 |

## 6.9 本章小结

本章完成了系统的功能测试、接口测试与性能测试，并对测试中发现的问题进行了修复。

**测试执行**：共 57 项测试，通过 53 项，4 项待界面验证。任务执行跟踪、告警双写检索、影像归档、设备离线检测等核心链路均端到端验证通过。

**测试发现并修复的 3 个问题**：

1. **异常处理不统一**（影响最大）—— 31 处业务校验中只有一处被正确处理，其余均返回 500。修复方式不是逐个打补丁，而是**引入专用异常类型 + 全局处理器**，并从设计上区分"客户端错误"与"服务端故障"。
2. **资源不存在返回 200 而非 404** —— 修正接口语义。
3. **`.gitignore` 误伤正式文件** —— 约 2200 行的文档与脚本一直未进入版本库。

**性能优化的实测收益**：Kafka 分区数由 1 提升至 3 后，单个 topic 的消费并行度由 **1 提升至 3**；后端扩展为双实例后，Nginx 负载均衡分布精确均衡（100 次请求 49:51），且单实例故障时服务不中断。

**测试方法论方面的收获**：本轮测试最重要的经验是——**"功能看起来正常"与"接口语义正确"是两回事**。登录失败返回 500，从用户视角只是"报错了"，功能测试很容易放过；但它会让调用方无法区分"密码错了"与"服务器崩了"。此外，**异常状态码复验**这一环节抓出了第一轮修复的漏网之处（`.orElseThrow` 写法未被替换），说明**测试用例的覆盖面比数量更重要**。
