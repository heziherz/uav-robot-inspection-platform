# 第 2 章 相关技术基础

本章介绍项目所使用的六类技术组件的基本原理与核心特征，并说明它们在系统中所承担的角色。

## 2.1 分布式文件系统 HDFS

### 2.1.1 架构原理

Hadoop 分布式文件系统（HDFS）采用主从（Master/Slave）架构，由两类节点组成：

- **NameNode（名称节点）**：集群的元数据管理者。它维护整个文件系统的目录树、文件与数据块的映射关系、以及每个数据块所在的 DataNode 位置，全部元数据常驻内存。
- **DataNode（数据节点）**：实际的数据存储者。文件被切分为固定大小的数据块（Block，默认 128 MB），每个块以副本形式存储在多个 DataNode 上。

客户端读写文件的流程体现了 HDFS 最关键的设计决策——**元数据与数据分离**：

```text
写文件：
  ① 客户端 → NameNode：请求创建文件
  ② NameNode → 客户端：返回可用的 DataNode 地址（HTTP 307 重定向）
  ③ 客户端 → DataNode：直接写入数据块
  ④ DataNode → 客户端：确认写入成功

读文件：
  ① 客户端 → NameNode：请求读取文件
  ② NameNode → 客户端：返回数据块所在 DataNode 地址
  ③ 客户端 → DataNode：直接读取数据块
```

**为什么不让 NameNode 中转数据**：文件数据量远大于元数据量，若所有数据都经 NameNode 转发，NameNode 会立即成为整个集群的瓶颈与单点故障。让客户端直连 DataNode，NameNode 只需处理轻量的元数据请求，从而具备管理数亿文件的能力。

这一设计直接影响了本项目的接口实现方式（见 5.2.3 节）：通过 WebHDFS 访问 HDFS 时，创建文件请求会收到 307 重定向，客户端必须手动跟随该重定向才能完成数据写入。

### 2.1.2 访问方式

HDFS 提供三类访问接口：

| 方式 | 端口类型 | 说明 |
| :--- | :--- | :--- |
| Hadoop Java Client | RPC（默认 8020） | 官方客户端，需引入 `hadoop-client` 依赖 |
| 命令行 `hdfs dfs` | 本地命令 | 需在装有 Hadoop 的机器上执行 |
| **WebHDFS REST** | HTTP（默认 9870） | 通过标准 HTTP 请求访问，语言无关 |

本项目采用 **WebHDFS**，原因见 5.2.3 节的设计说明。

### 2.1.3 在本项目中的角色

HDFS 承担**巡检影像大文件**的存储。无人机航拍与机器狗红外拍摄产生的图片文件具有"一次写入、多次读取、单文件较大"的特征，与 HDFS 的设计定位高度契合。文件按 `/uav/media/{设备编号}/{日期}/` 分目录存储，避免单一目录下海量文件条目撑爆 NameNode 内存。

## 2.2 分布式数据库 MongoDB

### 2.2.1 数据模型

MongoDB 是面向文档的 NoSQL 数据库，数据以 BSON（类 JSON 的二进制格式）文档形式存储，文档组织在集合（Collection）中。与关系型数据库的对应关系为：文档对应行、集合对应表。

其核心特点是**无固定 Schema**：同一集合中的文档可以拥有不同字段。这一特性使得业务字段变更时无需执行 DDL 迁移，适合需求仍在演进的项目阶段。

### 2.2.2 时序集合

MongoDB 5.0 起引入**时序集合（Time Series Collection）**，专门优化带时间戳的测量类数据存储。创建时需指定三个关键参数：

| 参数 | 含义 | 本项目取值 |
| :--- | :--- | :--- |
| `timeField` | 时间字段名，**必须是 Date 类型** | `eventTime` |
| `metaField` | 元数据字段名，用于将同源数据归组 | `deviceNo` |
| `granularity` | 数据点的时间间隔粒度 | `seconds` |
| `expireAfterSeconds` | 文档自动过期时长 | `604800`（7 天） |

时序集合的收益来自**分桶存储（Bucketing）**：同一 `metaField`（即同一设备）在相邻时间段内的测量值被压缩存放在同一个桶（Bucket）中，而非每条记录独立存储。这使得存储空间占用与索引体积大幅降低，同时提升查询效率。

> **注意**：`timeField` 必须是 BSON 的 `Date` 类型，不能是 long 型时间戳，否则写入时会报错。这是本项目实际遇到并解决的问题之一（见 5.3 节）。

### 2.2.3 在本项目中的角色

MongoDB 是系统的**权威数据存储**，承载四类数据：

- **设备状态**（`device_status`）：每台设备一条文档，心跳到达时覆盖更新；
- **遥测数据**（`telemetry`、`sensor_data`）：时序集合，批量写入、7 天自动过期；
- **告警明细**（`alarm`）：普通集合，支持处置状态更新；
- **任务台账与回执流水**（`task`、`task_log`）：前者记录当前状态、后者记录历史流水。

## 2.3 消息中间件 Kafka

### 2.3.1 核心概念

Apache Kafka 是分布式流处理平台，其核心抽象包括：

| 概念 | 含义 |
| :--- | :--- |
| **Topic（主题）** | 消息的逻辑分类，生产者向主题发布、消费者从主题订阅 |
| **Partition（分区）** | 主题的物理分片，是 Kafka 的**并行基本单位** |
| **Offset（偏移量）** | 消息在分区内的唯一递增编号 |
| **Producer（生产者）** | 消息发布方 |
| **Consumer Group（消费者组）** | 一组协同消费的消费者，组内每个分区只被一个消费者消费 |
| **Broker（代理）** | Kafka 服务实例 |

### 2.3.2 关键特性

**分区是并行的上限。** 这是 Kafka 最重要的语义约束：一个分区在同一时刻只能被同一消费者组内的一个消费者消费。因此：

```text
消费并行度上限 = 分区数
```

这意味着当主题只有 1 个分区时，即使消费者组内有 10 个消费者实例，也只有一个能真正工作。**本项目的容量压测实验正是围绕这一约束展开的**（见 6.5 节）。

**分区内有序，分区间无序。** Kafka 只保证同一分区内消息的先后顺序。因此若业务要求"同一设备的消息必须按序处理"，就需要以设备编号作为消息的 Key——Kafka 会依据 Key 的哈希值将其路由到固定分区，从而保证同源消息的有序性。本项目所有设备上报消息均以 `deviceNo` 作为 Key。

**持久化与副本。** Kafka 将消息持久化到磁盘（顺序写以获得高吞吐），并支持分区级副本（Replica）实现高可用。副本数（`replication.factor`）与最小同步副本数（`min.insync.replicas`）共同决定了可靠性等级。

**KRaft 模式。** Kafka 3.3 起引入 KRaft（Kafka Raft）模式，以内部 Raft 协议替代 ZooKeeper 完成集群元数据管理。本项目采用 KRaft 单节点部署，减少了组件依赖，简化了容器编排。

### 2.3.3 在本项目中的角色

Kafka 是系统的**中枢神经**，承担双向通道：

- **上行**：设备上报心跳、位置、传感器、影像元数据、告警事件、任务回执，共 6 个主题；
- **下行**：平台向设备下发任务指令，1 个主题。

其价值不仅是"传消息"，更在于**将设备端与平台端彻底解耦**：设备不直连业务数据库、也不持有平台接口，平台同样不持有设备接口。这一解耦使得上报链与下发链在代码依赖上各自只指向 Kafka，从而避免了双向依赖环（详见 4.2 节说明）。

> **补充说明**：影像大文件不走消息通道，而是由设备通过**独立的文件通道**自行上传至分布式存储，消息中只携带存储引用。**两条通道分离**可避免 MB 级文件挤占消息通道（详见 5.2.3 节）。

## 2.4 负载均衡 Nginx

### 2.4.1 核心能力

Nginx 是高性能的 HTTP 服务器与反向代理服务器，在本项目中承担三项职责：

**反向代理。** 客户端请求先到达 Nginx，由 Nginx 转发至后端服务。相比后端直接对外暴露，反向代理带来三重收益：隐藏后端拓扑、提供统一入口、便于集中实施限流与安全策略。

**负载均衡。** 通过 `upstream` 块定义后端服务集群，Nginx 可按轮询、加权轮询、IP 哈希等策略分发请求，是实现水平扩展的关键组件。

**静态资源托管。** Nginx 处理静态文件的效率远高于应用服务器，因此前端构建产物（HTML/CSS/JS）由 Nginx 直接返回。

### 2.4.2 在本项目中的角色

Nginx 是系统**唯一的对外入口**，按路径分流：

```text
浏览器请求
  ├── /            → 返回前端静态资源（React 构建产物）
  └── /api/...     → 反向代理至后端业务服务
```

## 2.5 Elasticsearch 分布式检索引擎

### 2.5.1 架构原理

Elasticsearch 是基于 Lucene 构建的分布式搜索引擎。其核心机制是**倒排索引（Inverted Index）**：与传统数据库"文档 → 词项"的正向查找不同，倒排索引建立"词项 → 文档列表"的映射，使得全文检索无需遍历全部文档。

数据组织层次为：**索引（Index）→ 分片（Shard）→ 文档（Document）**。索引在创建时可指定分片数，分片可分布于不同节点从而实现水平扩展；副本分片提供高可用与读吞吐扩展。

### 2.5.2 检索与聚合

**布尔查询**支持 `must` / `should` / `filter` / `must_not` 四类子句。其中 `filter` 子句不参与相关性评分计算，且结果可被缓存，是**过滤型检索**的推荐写法——本项目告警检索即采用 `bool.filter` + `term` 组合。

**聚合分析（Aggregation）** 是 ES 区别于普通搜索引擎的重要能力：

- `terms` 聚合：按字段值分组统计，如"按告警类型统计数量"；
- `date_histogram` 聚合：按时间间隔分桶，如"按小时统计告警趋势"。

这两类聚合恰好满足本项目的统计分析需求，而这类"分组 + 分桶"的统计分析若在文档数据库中实现则需要全表扫描与内存计算，效率差距显著。

### 2.5.3 按天滚动索引

对于持续增长的事件类数据，常见实践是**按时间切分索引**（如 `alarm-2026.09.16`）。其收益包括：

- 单个索引体积可控，避免超大索引导致的性能下降；
- 便于按时间范围清理或归档历史数据；
- 便于为不同时间段配置差异化策略。

### 2.5.4 在本项目中的角色

Elasticsearch 承担**告警事件的检索与分析**，与 MongoDB 形成"双写"：

- **MongoDB** 存权威明细，负责告警处置状态的更新；
- **Elasticsearch** 存检索副本，负责多条件检索与聚合统计。

**以 MongoDB 为准，ES 可随时重建**——这一取舍明确了冲突时的处理原则（见 5.2.5 节）。同时，系统坚持"业务查询走 MongoDB 动态条件查询、聚合统计走 Elasticsearch"，使两者各展所长。

## 2.6 Docker 容器虚拟化技术

### 2.6.1 核心概念

Docker 是轻量级的容器化技术。与虚拟机不同，容器**不模拟硬件、不包含独立操作系统内核**，而是直接复用宿主内核，通过命名空间（Namespace）实现资源隔离、通过控制组（Cgroup）实现资源限制。因此容器启动速度在秒级、资源开销远低于虚拟机。

| 层次 | 说明 |
| :--- | :--- |
| **镜像（Image）** | 只读模板，包含应用及其全部运行依赖 |
| **容器（Container）** | 镜像的运行实例，可独立启停 |
| **数据卷（Volume）** | 独立于容器生命周期的持久化存储 |
| **网络（Network）** | 容器间的隔离网络，同一网络内可通过**服务名**互相访问 |

### 2.6.2 Docker Compose 编排

Docker Compose 通过声明式 YAML 文件定义多容器应用，一条 `docker compose up -d` 即可启动全部服务。其关键能力包括：

- **服务定义与依赖声明**：`depends_on` 指定启动顺序；
- **环境变量注入**：使同一份代码可在不同环境使用不同配置；
- **数据卷挂载**：实现配置文件的挂载与数据的持久化；
- **内建 DNS**：同一网络内的容器可通过服务名互相解析。

### 2.6.3 在本项目中的角色

Docker 是本项目**多组件环境的统一交付方式**。项目涉及六类中间件，各自依赖复杂、版本敏感，容器化带来三重收益：

1. **版本隔离**：各组件运行在独立镜像中，从根本上避免依赖冲突；
2. **一键编排**：8 个容器通过一份 `docker-compose.yml` 统一管理；
3. **快速重置**：容器与数据卷可独立删除重建，便于反复排错。

## 2.7 本章小结

本章介绍了项目所使用的六类技术组件。这些组件并非孤立存在，而是在系统中形成了明确的分工与协作关系：

| 组件 | 在系统中的角色 | 解决的核心问题 |
| :--- | :--- | :--- |
| **Kafka** | 消息中枢（双向通道） | 设备与平台解耦、高吞吐数据汇聚 |
| **MongoDB** | 权威结构化存储 | 设备状态、遥测、告警、任务数据的持久化 |
| **HDFS** | 影像大文件存储 | 大文件的高吞吐可靠存储 |
| **Elasticsearch** | 检索与分析 | 多条件检索、聚合统计 |
| **Nginx** | 统一网关 | 外部访问入口、静态托管、负载均衡 |
| **Docker** | 环境交付 | 多组件版本隔离与一键编排 |

其中 Kafka 处于**拓扑中枢**位置——所有设备数据经它进入平台，所有控制指令经它发往设备，而正是这一安排使得系统在代码依赖上呈现为无环的有向图。这一架构特征将在第 4 章展开说明。
