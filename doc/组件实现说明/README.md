### 2.2 关键设计手法对照

同一类设计思想在不同组件上的体现：

| 设计手法 | Kafka | MongoDB | HDFS | Elasticsearch | Nginx |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **分区 / 分片** | 分区（`deviceNo` 作键） | 时序集合分桶 | 按 `设备/日期` 分目录 | 按天滚动索引 | — |
| **幂等设计** | 消费端 `msgId` 去重 | `_id` 主键 | 文件路径唯一 | **`_id = alarmId`** | — |
| **批量优化** | 生产端攒批 | **攒批 + 定时兜底** | — | 可用 `_bulk`（未用） | — |
| **自动清理** | 日志保留策略 | **TTL 自动过期** | 目录整体删除 | 索引整体删除 | — |
| **解耦** | 生产者/消费者解耦 | Repository 屏蔽存储细节 | 元数据与文件分离 | 主存储与检索副本分离 | 前后端解耦 |

### 2.3 遇到的问题对照

| 组件 | 遇到的问题 | 根因 |
| :--- | :--- | :--- |
| Kafka | 容器内外都连不上 | **广告监听器**返回客户端不可达的地址（"门牌号"问题） |
| MongoDB | 配置不生效，仍连 localhost | Spring Boot 4 **重命名了配置前缀**，旧名静默失效 |
| HDFS | 上传路径出现 `D:\school\...` | Linux 容器不认 Windows 反斜杠，`Paths.get()` 将整串当文件名 |
| Elasticsearch | 经纬度字段不是 `geo_point` | **未定义索引模板**，动态映射无法推断类型 |
| Nginx | 页面刷新 404 | SPA 路由需 `try_files` 回退到 `index.html` |

**共同规律**：这些问题**都不是代码逻辑错误，而是跨系统协作时的"约定不一致"**——地址约定、配置项命名、路径分隔符、数据类型、路由规则。这正是分布式系统集成所特有的挑战。

## 三、各组件的关键约束（一句话）

| 组件 | 必须记住的约束 |
| :--- | :--- |
| **Kafka** | **并行度上限 = 分区数**。当前主题只有 1 个分区 → 消费并行度锁死为 1 → 这是系统吞吐的**硬天花板**，加 CPU / 内存都无效 |
| **MongoDB** | 时序集合的 `timeField` **必须是 Date 类型**，不能是 long 时间戳 |
| **HDFS** | WebHDFS 的 `CREATE` 返回 **307**，**必须手动跟随** Location 头才能写入成功 |
| **Elasticsearch** | `date` 字段必须是 **ISO-8601 字符串**；`_id` 用业务主键才能保证幂等 |
| **Nginx** | SPA 必须配 `try_files $uri $uri/ /index.html`，否则刷新子路由页面会 404 |

## 五、各组件的已知不足（汇总）

| 组件 | 主要不足 |
| :--- | :--- |
| **Kafka** | 所有上行主题**仅 1 个分区**（硬瓶颈）；单 Broker 副本数 1；无死信队列 |
| **MongoDB** | 深分页 O(页码)；无副本集；部分字段缺索引；`findAll()` 全表加载 |
| **HDFS** | 每次上传重复 MKDIRS；整文件读入堆内存；同步阻塞；无重传机制 |
| **Elasticsearch** | **无索引模板**（`geo_point` 失效）；无超时；无批量写入；未做全文检索 |
| **Nginx** | 后端单实例（负载均衡未发挥）；无限流；无安全响应头；无 HTTPS |

> 完整清单见各组件文档的"当前不足与优化方向"章节。
