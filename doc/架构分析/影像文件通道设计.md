# 影像文件通道设计

> **本文回答**：设备的影像文件应该如何传递到平台与存储？
> **背景**：项目早期实现中，仿真端将图片存本地、把**本地绝对路径**写进消息，平台据此路径去读文件。该设计存在根本性缺陷，本文分析问题本质并给出正确方案。

---

## 一、问题：一个不成立的前提

### 1.1 原始实现

```text
仿真端：生成图片 → 写本地磁盘 D:\...\sim-files\IMG-xxx.jpg
      → 发消息 { ..., localPath: "D:\\school\\...\\IMG-xxx.jpg" }
                                    ↑ 把【设备本地文件系统】的信息塞进了消息契约
平台：收到消息 → 用 localPath 去读文件 → 上传 HDFS
```

### 1.2 为什么这是错的

**这条链路成立的前提是"设备与平台共享文件系统"。** 而现实中这个前提根本不成立——无人机在空中、机器狗在园区，平台在机房，两者之间只有网络，没有共享磁盘。

**它之所以能跑，只是因为 Docker 的绑定挂载把这个前提"人工制造"了出来**：

```yaml
platform-service:
  volumes:
    - ../backend/device-simulator/sim-files:/app/sim-files:ro    # ← 人工制造共享文件系统
```

### 1.3 缺陷清单

| # | 缺陷 | 说明 |
| :-: | :--- | :--- |
| 1 | **契约污染** | `localPath` 把设备端的实现细节泄漏进跨系统契约。平台既无法解析 `D:\...` 这类路径，也不该关心 |
| 2 | **强耦合** | 设备与平台的文件布局被绑死在一起，任一方调整目录结构都会影响另一方 |
| 3 | **仅单机可行** | 真机部署（设备与平台分离）时链路直接断裂 |
| 4 | **平台做无用功** | 平台要把文件整体读一遍再写一遍，白白消耗一倍带宽与内存 |
| 5 | **平台承担存储压力** | 所有影像字节都要流经平台进程 |
| 6 | **可靠性割裂** | 文件在设备本地，设备故障可能丢文件，而平台已入库了元数据 |

### 1.4 代码中的证据

**证据一：`MediaService` 里有一段专门"绕开"这个问题的逻辑**

```java
// 容器模式下：消息里是宿主机绝对路径，容器里读不到 → 用挂载目录 + 文件名重新拼
String fileName = msg.localPath().replaceAll("^.*[\\\\/]", "");   // 正则剥前缀
String realPath = simFilesDir + "/" + fileName;
```

> **当一段代码需要靠"正则剥离路径前缀"才能工作时，说明它绕的是一个设计问题，而不是实现问题。**

**证据二：曾经真实发生过的畸形路径**

HDFS 中一度出现过这样的路径：

```text
/app/sim-files/D:\school\all\项目\企业项目实践\backend\device-simulator\sim-files\IMG-UAV-001-xxx.jpg
```

Windows 路径被整个当成了文件名。这不是偶发 Bug，而是"跨系统传递环境相关路径"这一错误设计的必然产物。

## 二、问题出在哪一层：契约层

根本问题不是"代码怎么写"，而是 **`MediaMetaMessage` 契约中不该有 `localPath` 这个字段**。

```java
public record MediaMetaMessage(
        String msgId, String deviceNo, String fileId, String fileType,
        int size,
        String localPath,      // ← 问题在这里
        double lat, double lng, long eventTime) { }
```

`localPath` 是**设备端的内部信息**，平台既无法理解也无法使用。它出现在契约里，等于要求"平台的运行环境必须能访问设备端的文件系统"——这是一个荒谬的隐含要求。

### 核心原则

> **跨系统契约应传递「标识」，而不是「位置」。**
>
> **位置（path）** 是各系统内部的环境相关信息，随部署方式而变；
> **标识（id）** 是双方共享的语义，与各自环境无关。

这条原则适用于所有跨系统设计：

| 场景 | ✗ 传递位置 | ✓ 传递标识 |
| :--- | :--- | :--- |
| 影像文件 | `D:\...\IMG-001.jpg` | `fileId = IMG-001` + 存储引用 |
| 数据库记录 | 表名 + 行号 | 业务主键 |
| 服务调用 | 固定 IP + 端口 | 服务名（由注册中心解析） |
| 容器寻址 | 容器 IP | 服务名（由 DNS 解析） |

> **本项目在容器寻址上做对了**（Kafka 用 `kafka:9092` 而非 IP），却在文件传递上做错了——**同一个原则，在两个地方的应用不一致**。

## 三、文件传输的四种方式

### 3.1 两种不可行方案

| 方案 | 做法 | 为什么不可行 |
| :--- | :--- | :--- |
| **A. 文件本体走消息** | 把文件字节编码后放进 Kafka 消息 | **MB 级文件会撑爆消息中间件**——体积、磁盘、网络带宽全被挤占，且会拖慢同主题的其他消息。这正是"消息传引用，不传本体"这条原则的由来 |
| **B. 共享文件系统** | 设备与平台挂载同一目录（当前做法） | 只在单机可行；设备与平台强耦合；平台做无用的搬运 |

> **方案 A 的例外**：若文件确实很小（几 KB 级，如缩略图），理论上可以走消息。但**判断标准应是"文件相对消息体的大小"**，而非绝对大小——让一条消息比普通消息大三个数量级，任何消息中间件都会受影响。

### 3.2 两种可行方案

#### 方案 C：设备直传存储

```text
设备：拍照 → 自己 PUT 到存储（HDFS / 对象存储）→ 拿到存储引用
      → 发消息 { fileId, storageRef, ... }（只有引用，无路径）
平台：消费消息 → 只写元数据，不搬运文件
```

| 优点 | 缺点 |
| :--- | :--- |
| 平台**完全不搬运数据**，省一倍带宽与内存 | 设备需要存储凭据，**安全边界问题**（外部设备直写内网存储） |
| 契约干净，只有引用 | 存储路径规范需在设备侧维护 |
| 与真实摄像头 / IPC 的做法一致 | 平台无法在上传环节做校验 |

#### 方案 D：平台提供上传入口

```text
设备：拍照 → POST 文件到平台上传接口 → 拿到 fileId
      → 发消息 { fileId, ... }
平台：接收文件 → 落 HDFS → 记录元数据
```

| 优点 | 缺点 |
| :--- | :--- |
| 安全边界清晰（设备只需访问平台网关） | 平台仍需接收全部文件字节 |
| 平台可校验（大小 / 类型 / 频率 / 病毒扫描） | 多一跳网络传输 |
| 实现简单，无需存储凭据分发 | 平台成为带宽瓶颈 |

#### 方案 E：预签名 URL（方案 C 的安全版本，业界标准）

```text
设备：拍照
  ① → POST /api/media/upload-ticket { fileId, size, fileType }
  ② ← { uploadUrl, expiresIn: 300 }
  ③ → PUT <uploadUrl> 携带文件字节        ← 直传存储，不经平台
  ④ ← 201 Created
  ⑤ → Kafka: { fileId, fileType, size, lat, lng, eventTime }   ← 只有引用
平台：签发凭证时校验配额；消费消息时只写元数据
```

| 优点 | 缺点 |
| :--- | :--- |
| **兼具 C 的性能与 D 的安全** | 需要实现凭证签发与校验逻辑 |
| 凭证有时效（如 5 分钟）、有范围限制 | 需要存储系统支持预签名（S3 / OSS 原生支持） |
| 平台可在签发前做校验（拒绝超大文件、限制频率） | HDFS 无原生预签名能力，需自行实现 |

**现实中的选择**：无人机通常走 **E**（直传云端对象存储，如大疆的做法）；访问受限或需强管控的场景走 **D**。

## 四、本项目采用的方案

### 4.1 选定：设备直传 HDFS（方案 C）

**选择理由**：

| # | 理由 |
| :-: | :--- |
| 1 | **修掉核心缺陷**：契约不再含路径，彻底消除对共享文件系统的依赖 |
| 2 | **体现正确原则**：设备自己上传、平台不搬运——这是方案 C/D/E 共有的正确内核 |
| 3 | **改动可控**：HDFS 端口已映射到宿主机（`9870:9870`），仿真端可直接访问，无需新建服务 |
| 4 | **删除 hack**：可以彻底移除 Docker 挂载与"正则剥路径"逻辑 |
| 5 | 与真实设备的上传行为一致（摄像头/无人机均自行上传） |

**方案 E（预签名 URL）是生产环境的更优解**，但需要实现凭证签发与校验服务，超出课程项目的合理范围。本方案在架构方向上与 E 一致（设备直传 + 消息传引用），**后续升级为 E 时，平台侧代码无需改动**。

### 4.2 目标链路

```text
┌──────────┐                                        ┌──────────┐        ┌────────┐
│ 仿真设备  │                                        │  平台     │        │  HDFS  │
└────┬─────┘                                        └────┬─────┘        └───┬────┘
     │ ① 生成图片，本地暂存                              │                  │
     │                                                  │                  │
     │ ② POST /api/media/upload-auth                    │                  │
     │    X-Device-No / X-Device-Ts / X-Device-Token     │                  │
     │─────────────────────────────────────────────────→│                  │
     │                                    ③ 校验设备身份  │                  │
     │                                      （HMAC 令牌） │                  │
     │←─────────────────────────────────────────────────│                  │
     │    { storageRef: "/uav/media/DOG-001/.../x.jpg" } │                  │
     │    ★ 路径由【平台】决定，设备只是执行者              │                  │
     │                                                  │                  │
     │ ④ PUT /webhdfs/v1{storageRef}  ──────────────────────────────────────→│
     │    （307 跟随 → 写 DataNode）                      │                  │ 落盘
     │←─────────────────────────────────────────────────────────────────────│
     │                                                  │                  │
     │ ⑤ Kafka: { fileId, storageRef, size, lat, lng }   │                  │
     │    ★ 只有引用，无任何本地路径                       │                  │
     │─────────────────────────────────────────────────→│                  │
     │                                    ⑥ 校验路径规范  │                  │
     │                                      → 写元数据    │                  │
```

> **②③ 这一步是后续补上的"设备身份门禁"**：设备必须先取得平台授权才允许上传。
> 详见第 4.4 节。

### 4.3 关键设计点

**（1）契约字段变更**

```java
// 改前：传递位置
String localPath      // D:\...\sim-files\IMG-xxx.jpg

// 改后：传递引用
String storageRef     // /uav/media/UAV-001/20260919/IMG-UAV-001-xxx.jpg
```

`storageRef` 是**存储系统给出的引用**，平台可直接用它读取文件，且与设备环境无关。

**（2）上传成功才发消息**

设备端逻辑改为"上传成功后才发送元数据消息"。上传失败则不发消息——避免平台收到"有元数据、无文件"的记录。

```java
String storageRef = storageClient.upload(localFile, deviceNo, fileId);
if (storageRef == null) {
    log.warn("[{}] 影像上传失败，本次跳过上报", deviceNo);
    return;                    // 不发消息
}
sendToKafka(TOPIC_MEDIA_META, new MediaMetaMessage(..., storageRef, ...), "影像元数据已上报");
```

**（3）平台侧不再搬运**

```java
// 改前：读取本地文件 → 上传 HDFS → 回填路径（两次数据库写 + 3 次 HTTP）
// 改后：只写一次元数据
public void handleMediaMeta(MediaMetaMessage msg) {
    MediaDoc doc = toDoc(msg);
    doc.setStorageRef(msg.storageRef());
    doc.setUploaded(true);        // 设备上传成功才会发消息
    mediaRepository.save(doc);
}
```

**（4）路径规范单点维护**

改造前，路径规范由**平台**维护（`HdfsService.BASE_DIR`）；改造后由**设备**维护（上传时决定路径），平台只存引用。

> **这是一个取舍**：严格来说，存储路径应由平台或存储系统决定（预签名 URL 正是如此），由设备决定会导致平台失去对存储布局的控制权。本项目接受这一简化，**在方案 E 中该问题自然解决**。

**（5）存储引用的语义泛化**

字段名从 `hdfsPath` 改为 `storageRef`，是为了**不把平台绑死在 HDFS 上**。若将来换成对象存储（S3 / OSS），只需更换设备端的存储客户端，**平台侧字段与代码无需改动**。

### 4.4 设备身份门禁（后续补强）

#### 4.4.1 为什么要补这一层

方案 C 解决了"平台不搬运文件"，但留下一个洞：**平台对"谁在传"毫无约束**。

| 漏洞 | 后果 |
| :--- | :--- |
| 任何程序都能编一个 `deviceNo` 调接口 | 无法分辨真实设备与伪造请求 |
| 设备自行拼接路径 | 平台无从验证"授权的路径"是否被遵守 |
| 已停用/已删除的设备 | 照样能上传 |

#### 4.4.2 补强方案：先授权，后上传

```text
① 设备生成影像
        │
        ▼
② 设备 → POST /api/media/upload-auth
        X-Device-No / X-Device-Ts / X-Device-Token
        │
   ┌────┴──────────────────────────────┐
   │ 平台校验三件事：                    │
   │  ① 令牌有效？（HMAC 签名匹配）      │
   │  ② 未超时间窗？（±5 分钟）          │
   │  ③ 设备已注册？                    │
   └────┬──────────────────────────────┘
        │ 通过 → 签发 storageRef（★ 路径由平台决定）
        │ 失败 → 401 / 403，设备不上传
        ▼
③ 设备按平台签发的路径上传 HDFS
        │
        ▼
④ 设备发消息 → 平台校验路径规范 → 入库
```

#### 4.4.3 令牌设计：没有"有效期"，只有"时间偏差容忍窗口"

```text
token = HMAC-SHA256(deviceNo + ":" + 当前时间戳, secret) 的前 16 字节
```

**关键点：时间戳取自"本次请求的时刻"，不是"令牌签发的时刻"。**

| 常见误解 | 实际情况 |
| :--- | :--- |
| "设备长期在线，令牌有效期要设长一点" | ❌ 不存在"令牌过期要续期"——设备**每次请求都现算一个** |
| "5 分钟太短，设备要不停刷新" | ❌ **没有刷新这回事**，平台也**不存令牌**（无状态） |
| "那 5 分钟是什么？" | ✅ 是**时间偏差容忍窗口**：只用来覆盖网络延迟与时钟偏差，同时也界定了重放窗口 |

**窗口设多少**：业界请求签名普遍采用 **5 分钟**（AWS SigV4、微信支付签名均为 5 分钟）——刚好覆盖"时钟偏差 + 网络延迟"，同时把重放窗口压得足够小。本项目仿真端与平台同机部署、时钟完全一致，5 分钟几乎全部留给网络延迟（内网毫秒级），**绰绰有余**。

#### 4.4.4 与其他令牌机制的对照

这张表可用于说明"为什么选 HMAC 而不是别的"：

| 场景 | 用什么机制 | "有效期"的真实含义 |
| :--- | :--- | :--- |
| **每请求签名**（本方案） | **HMAC + 时间戳** | 窗口 5 分钟（容忍时钟偏差 + 压缩重放窗口） |
| 登录会话 | Access Token + Refresh Token | Access 15min~1h；Refresh 7~30 天 |
| **长期在线设备** | **mTLS 设备证书** | **1~10 年，靠 CRL/OCSP 吊销** |
| 一次性上传授权 | 预签名 URL | 15 分钟 ~ 7 天（按需设定） |

> **注意第三行**：真正的"设备长期在线"场景，业界用的是 **mTLS 设备证书**，
> **而不是拉长令牌有效期**——证书不靠"过期"来保证安全，靠**吊销**（CRL / OCSP）。
> 这才是为长期在线设备设计的机制。本项目采用 HMAC 签名属于轻量级方案，适用于仿真场景。

#### 4.4.5 这套门禁仍未能解决的

| 做不到 | 原因与缓解 |
| :--- | :--- |
| **阻止设备绕过平台直写 HDFS** | HDFS 未开鉴权，存储层无强制力。**但**绕过平台的上传会因"路径不符合平台签发规范"**被拒绝入库**——检索不到、用不了，等于没传（应用层强制力） |
| 防住"合法设备上传垃圾内容" | 只校验身份，不校验内容。内容审核是另一套机制 |

## 五、其他选型的必要性说明

### 5.1 为什么设备不把文件 POST 给平台（方案 D）

方案 D 也能修正契约问题，但平台仍需接收并转发全部文件字节。本项目已部署 HDFS 且端口已暴露，**让设备直传可以省掉平台的整条搬运链路**，是更彻底的解耦。

**方案 D 更适合的场景**：设备无法直连存储（网络受限）、或平台需要在上传环节做强管控（内容审核、病毒扫描）。

### 5.2 为什么仍需保留平台侧的 HDFS 读取能力

设备的写入与平台的读取是**两个方向的需求**：

| 方向 | 谁来做 | 用途 |
| :--- | :--- | :--- |
| **写入** | **设备** | 产生影像后上传 |
| **读取** | **平台** | 前端预览、下载影像 |

因此平台侧的 `HdfsService` **保留 `download()`**，仅 `upload()` 退出主链路（保留作为运维补偿手段）。

## 六、改造后的收益与遗留

### 6.1 收益

| # | 收益 |
| :-: | :--- |
| 1 | **契约干净**：消息中不再出现任何本地路径，跨系统边界清晰 |
| 2 | **消除共享文件系统依赖**：删掉 Docker 挂载后链路依然通——这是检验解耦是否成功的标志 |
| 3 | **平台零搬运**：影像字节从设备直达存储，平台只处理元数据 |
| 4 | **消除一类 Bug**：路径分隔符差异、"正则剥前缀"这类问题不再存在 |
| 5 | **可平滑升级**：将来换对象存储或改用预签名 URL，平台侧代码无需改动 |
| 6 | **与真实设备行为一致**：摄像头、无人机均自行上传，而非把路径交给平台 |

### 6.2 遗留问题

> **说明**：下表中标注"已解决"的两项，是在本文档初稿之后通过补充"设备身份门禁"（4.4 节）
> 与"路径规范校验"而修正的。记录在此以体现演进过程。

### 关于"设备不直连平台"的表述修正

原架构文档的表述是：

> "仿真设备**不登录 Web、不调用业务接口、不直连数据库**，仅通过消息中间件完成'上报数据'与'接收指令'两类交互。"

**这一表述是不完整的**——它只考虑了状态与遥测数据，漏掉了文件传输。真实设备需要**两条通道**：

| 通道 | 承载 | 协议 |
| :--- | :--- | :--- |
| **消息通道** | 状态、遥测、指令、元数据 | Kafka |
| **文件通道** | 影像、视频等大文件 | HTTP / 对象存储 API |

**修正后的表述应为**：

> "仿真设备通过**消息中间件**完成状态上报与指令接收；通过**文件通道**（存储直传或上传接口）传输影像大文件。**两条通道分离，避免大文件挤占消息通道**。"

## 八、一页速记

```text
【问题本质】
  原设计假设"设备与平台共享文件系统"——现实中不成立
  仅靠 Docker 绑定挂载人工制造出该前提

【问题出在契约层】
  MediaMetaMessage.localPath 把设备端实现细节泄漏进跨系统契约

【核心原则】
  ★ 跨系统契约传递【标识】，不传递【位置】
     位置 = 环境相关信息（随部署而变）
     标识 = 双方共享语义（与环境无关）
  （本项目在容器寻址上做对了：用服务名而非 IP；
    却在文件传递上做错了——同一原则，两处不一致）

【四种方式】
  A 文件走消息    ✗ MB 级文件撑爆消息中间件
  B 共享文件系统  ✗ 仅单机可行，强耦合
  C 设备直传存储  ✓ 本项目采用
  D 平台上传入口  ✓ 安全但平台仍需搬运
  E 预签名 URL    ★ 业界标准，兼具 C 的性能与 D 的安全

【本项目方案：设备直传 + 身份门禁】
  ① 设备 → POST /api/media/upload-auth（HMAC 令牌）
     平台校验：令牌有效 + 未超时间窗(±5min) + 设备已注册
     → 通过则签发 storageRef（★ 路径由平台决定）
  ② 设备按平台签发的路径上传 HDFS
  ③ 设备发消息（只有 storageRef，无本地路径）
  ④ 平台校验路径规范 → 入库

【令牌的关键认知】
  ★ 没有"有效期"，只有"时间偏差容忍窗口"
     时间戳取【本次请求的时刻】，不是签发时刻
     → 设备在线多久都无所谓，不存在续期
     → 平台无状态，不存令牌
  窗口 5 分钟 = 覆盖网络延迟 + 时钟偏差（业界标准：AWS SigV4 / 微信支付同为 5 分钟）
  窗口同时也是【重放窗口】，故不宜过大

【不同场景的机制对照】
  每请求签名      HMAC + 时间戳      窗口 5 分钟
  登录会话        Access/Refresh     15min~1h / 7~30天
  长期在线设备    mTLS 证书          ★ 1~10 年，靠 CRL/OCSP 吊销
  一次性上传授权  预签名 URL         15min~7天

【验证标准】
  删掉 sim-files 挂载后链路依然通畅 = 解耦成功
```
