# 接口设计说明

> **本文回答**：本项目的"接口"是怎么划分与设计的？
> 覆盖三个层次——**组件接口**（平台 ↔ 中间件）、**业务接口**（REST API）、**前后端接口**（前端 ↔ 后端约定）。
>
> **配套**：《[需求分析与总体架构技术选型.md](需求分析与总体架构技术选型.md)》（总体架构）、《[../需求分析/仿真数据与消息契约说明.md](../需求分析/仿真数据与消息契约说明.md)》（消息契约）

---

## 一、三层接口框架

| 层次 | 谁 ↔ 谁 | 协议 | 典型例子 |
| :--- | :--- | :--- | :--- |
| **组件接口** | 平台 ↔ 中间件 / 存储 / 检索引擎 | 各组件原生协议 | Kafka produce、WebHDFS、ES `_search` |
| **业务接口** | 外部 ↔ 平台 | REST / HTTP | `GET /api/devices` |
| **前后端接口** | 前端 ↔ 后端 | REST + 约定 | 认证头、分页结构、错误格式 |

```text
┌──────────┐  前后端接口   ┌──────────┐  业务接口   ┌─────────────────┐
│  Web 前端 │ ──────────→ │  Nginx   │ ─────────→ │  platform-service│
└──────────┘   (HTTP+约定) └──────────┘   (REST)   └────────┬────────┘
                                                            │ 组件接口
                          ┌─────────────┬─────────────┬─────┴───────┐
                          ▼             ▼             ▼             ▼
                       Kafka        MongoDB         HDFS      Elasticsearch
                    (原生协议)     (驱动协议)   (WebHDFS REST)   (REST)
```

**关键认知**：三层协议不同，但**底层的设计原则是共通的**——统一出口、契约显式、幂等、传递标识而非位置。原则想清楚了，换个协议照样能用。

## 二、组件接口：平台与中间件的对接

### 2.1 组件与交互方式对照

| 组件 | 交互方式 | 用到的操作 | 客户端选择 |
| :--- | :--- | :--- | :--- |
| **Kafka** | 原生二进制协议 | produce / consume（7 个 topic） | `spring-kafka`（官方封装） |
| **MongoDB** | 驱动协议 | `find` / `insert` / `save` / `findAndModify` | `spring-data-mongodb` |
| **HDFS** | **WebHDFS REST** | `MKDIRS` / `CREATE` / `GETFILESTATUS` / `OPEN` | **裸 `HttpClient`** |
| **Elasticsearch** | **REST** | `PUT /_doc` / `POST /_search` / `aggs` | **裸 `HttpClient`** |
| **Nginx** | 配置文件 | `upstream` / `location` / `proxy_pass` | 配置 |
| **Docker** | CLI + YAML | `compose up` / `build` | 配置 |

### 2.2 一处刻意的选择：HDFS 与 ES 用裸 HTTP

| 组件 | 为什么不用官方客户端 |
| :--- | :--- |
| **Elasticsearch** | 客户端与服务端**版本必须严格匹配**（业界公认的工程坑）；项目只用三类操作，HTTP 完全够用 |
| **HDFS** | `hadoop-client` 是数十 MB 的依赖树且需配置 `core-site.xml`；项目只需"上传 + 读取"两个功能 |

**收益**：

- ES 从 9.x 升到 10.x **不需要改代码**（REST 协议不变）
- HDFS 换成对象存储时，**只需替换实现类**，上层逻辑不动

**代价**：手写 JSON、手动解析响应、**需要自己配超时**（当前未配，是已知不足）。

### 2.3 契约的定义位置

| 契约 | 定义在哪 | 为什么这样放 |
| :--- | :--- | :--- |
| Topic 名称 | `config/Topics.java` 常量类 | 避免字符串散落各处，改名只改一处 |
| 消息体字段 | `model/*Message.java` 的 **record** | 编译期校验、不可变、无样板代码 |
| 存储路径规范 | `MediaService.buildStorageRef()` | **签发与校验共用同一方法**，规则不会两边跑偏 |

### 3.2 认证与权限规则

系统有**两条认证通道**，由 `AuthInterceptor` 统一拦截分流：

```java
public boolean preHandle(...) {
    if ("OPTIONS".equalsIgnoreCase(request.getMethod())) return true;

    // ① 设备通道：上传授权接口走设备令牌（HMAC），不走 JWT
    if (request.getRequestURI().startsWith("/api/media/upload-auth")) {
        return verifyDevice(request, response);
    }

    // ② 人机通道：其余接口走 JWT + 角色校验
    String auth = request.getHeader("Authorization");
    if (auth == null || !auth.startsWith("Bearer ")) return reject(response, 401, "未登录，请先登录");
    Map<String, Object> claims = JwtUtil.parse(auth.substring(7));
    if (claims == null) return reject(response, 401, "登录已过期，请重新登录");

    String role = (String) claims.get("role");
    if (!hasPermission(request, role)) return reject(response, 403, "当前角色无权执行该操作");
    ...
}
```

**表 3-1 权限规则**

| 规则 | 依据 |
| :--- | :--- |
| `/api/devices` **写操作** + `/api/users` → **ADMIN** | 需求 UC-21/22 的参与者是**系统管理员** |
| `/api/tasks` 全部 → **登录用户** | 需求 UC-12 的参与者是**巡检值班员**，不是管理员 |
| `/api/media/upload-auth` → **设备令牌** | 设备没有"登录"概念，也不该持有用户 JWT |

> **关键点：权限规则对齐的是需求中的"参与者定义"，而不是一律收紧。**
> 若把 `/api/tasks` 也限成 ADMIN，反而违背了 UC-12 的规格。

**为什么认证放在拦截器而不是各 Controller**：认证是**横切关注点**，
分散写会重复且容易漏。集中在一处 → "一处生效、全局覆盖"。
**设备通道也遵循同一原则**——不因为它只有一两个接口就另起一套校验逻辑。

### 3.3 关键接口示例

#### 示例 1：创建并下发任务

**请求**

```http
POST /api/tasks?autoDispatch=true
Authorization: Bearer <token>
Content-Type: application/json

{
  "taskType": "ROUTINE",
  "deviceNo": "UAV-001",
  "area": "园区东侧",
  "description": "日常空中巡查"
}
```

**成功响应**（200）

```json
{
  "taskId": "TASK-20260919-0006",
  "taskType": "ROUTINE",
  "deviceNo": "UAV-001",
  "deviceType": "DRONE",
  "status": "DISPATCHED",
  "progress": 0,
  "dispatchCount": 1,
  "msgId": "CMD-TASK-20260919-0006-1",
  "createBy": "operator",
  "createTime": 1789610527284
}
```

**失败响应**（400，设备离线）

```json
{
  "status": 400,
  "message": "任务已保存为草稿（TASK-20260919-0007），但设备离线，无法下发: DOG-003（当前状态 OFFLINE）"
}
```

> **注意这条错误信息的三个要素**：说明了**结果**（已存为草稿）、**原因**（设备离线）、**上下文**（当前状态）。
> 值班员看到就知道：任务没丢，等设备上线后手动下发即可。

#### 示例 2：列表查询（分页 + 多条件）

**请求**

```http
GET /api/alarms?status=PENDING&alarmType=ENV&level=WARN&startTime=1789600000000&page=1&size=10
```

**响应**

```json
{
  "total": 2183,
  "items": [
    {
      "alarmId": "ALM-DOG-001-1789610393814",
      "deviceNo": "DOG-001",
      "alarmType": "ENV",
      "level": "WARN",
      "description": "可燃气体浓度超标: 4.97 ppm",
      "lat": 29.5621, "lng": 106.5503,
      "handleStatus": "PENDING",
      "eventTime": 1789610393814
    }
  ]
}
```

> **`{total, items}` 是列表接口的统一结构**，前端所有分页表格都按这个取数。

#### 示例 3：设备申请上传授权（设备通道）

**请求**

```http
POST /api/media/upload-auth
X-Device-No: DOG-001
X-Device-Ts: 1789610393
X-Device-Token: 3f8a1c9e2b4d6a70
Content-Type: application/json

{ "fileId": "IR-DOG-001-1789610393814", "fileType": "INFRARED" }
```

**成功响应**（200）

```json
{ "storageRef": "/uav/media/DOG-001/20260919/IR-DOG-001-1789610393814.jpg" }
```

**失败响应**（401）

```json
{ "status": 401, "message": "设备令牌无效或已过期" }
```

> **`storageRef` 由平台决定**——设备只是执行者，存储布局规则掌握在平台手里。

## 四、前后端接口约定

前端 29 处调用能保持一致，靠的是五条约定。

### 约定 1：认证 —— 一个请求头，拦截器统一注入

```javascript
// src/api.js
api.interceptors.request.use(config => {
  const token = localStorage.getItem('token')
  if (token) config.headers.Authorization = `Bearer ${token}`
  return config
})
```

**各页面无需关心令牌**——只管调接口。

### 约定 2：分页 —— 固定响应结构

```json
{ "total": 2183, "items": [ ... ] }
```

列表接口一律返回此结构，前端直接喂给 antd Table 的 `total` + `dataSource`。

### 约定 3：时间 —— 一律毫秒时间戳

```javascript
render: t => new Date(t).toLocaleString()
```

后端返回 `Long`，前端负责格式化。**不传格式化字符串**——展示格式是前端的事。

> ⚠ **例外**：写入外部系统时是另一套——MongoDB 时序集合要求 `Date` 类型、
> ES 的 `date` 字段要求 ISO-8601 字符串。**跨系统传时间，每一跳都要核对格式**（这是踩过的坑）。

### 约定 4：错误 —— 统一响应体

```json
{ "status": 400, "message": "设备离线，无法下发: DOG-003（当前状态 OFFLINE）" }
```

前端直接 `message.error(e.response?.data?.message)`，**不需要翻译错误码**。

### 约定 5：登录失效 —— 拦截器统一处理

```javascript
api.interceptors.response.use(res => res, err => {
  if (err.response?.status === 401) {
    localStorage.removeItem('token'); localStorage.removeItem('user')
    window.location.reload()
  }
  return Promise.reject(err)
})
```

## 五、贯穿三层的四条设计原则

### 原则 1：统一出口，收口横切逻辑

| 层 | 出口 | 收口了什么 |
| :--- | :--- | :--- |
| 后端 → Kafka | `MessagePublisher` | 序列化、发送、日志、异常 |
| 后端 → 前端 | `@ExceptionHandler` | 业务异常 → 400 + 可读消息 |
| 前端 → 后端 | `api.js` 拦截器 | 令牌注入、401 处理 |

> **同一思路在三层的重复应用**——这才是"设计一致"的含义，而不是三层各写各的。

### 原则 2：入站适配器 vs 出站适配器

```text
        Controller ─┐                    ┌─ Repository
                   ├─→ Service ─→ 业务 ─→├─ MessagePublisher
        Consumer  ─┘                    ├─ HdfsService
     （入站适配器）                       └─ ES Client（出站适配器）
```

**Controller 与 Consumer 属于同一层**——都是"外部输入进系统的入口"，
只是协议不同（HTTP vs 消息）。二者都只做**协议转换与路由**，业务逻辑全部下沉到 Service。

### 原则 3：幂等键

| 位置 | 幂等键 | 机制 |
| :--- | :--- | :--- |
| 设备侧指令 | `msgId` | `processedMsgIds` 集合去重 |
| ES 文档 | `_id = alarmId` | 重复写入变**覆盖**而非新增 |
| 任务台账 | `taskId` | MongoDB 原子计数器生成 |
| 影像文件 | `fileId` | 存储路径唯一 |

> ⚠ **幂等有隐含前提：标识必须唯一。**
> 本项目踩过一个坑——taskId 用毫秒时间戳生成，批量处置时同毫秒内**编号碰撞**，
> 导致指令被设备侧的幂等保护**静默丢弃**（勾 3 条只执行 1 条，且无任何错误日志）。
> **幂等机制必须与"标识生成的正确性"一起设计。**

### 原则 4：传递标识，不传递位置 ★

| 位置 | 做对了吗 |
| :--- | :--- |
| 容器寻址 | ✅ 用服务名 `kafka:9092`，不用 IP |
| 前端传设备 | ✅ 传 `deviceNo`，不传数据库地址 |
| **影像文件** | ❌ 原来传 `localPath`（设备本地绝对路径）→ **已改为传 `storageRef`** |

> **同一原则，之前在文件传递上没有贯彻**——这是"设计一致性"的反面教材。
> 详见图《[影像文件通道设计.md](影像文件通道设计.md)》。
>
> 教训：**原则要靠检查清单落地，不能靠自觉。**

## 六、值得注意的设计选择

| # | 选择 | 理由 |
| :-: | :--- | :--- |
| 1 | **`/api/tasks/available-devices` 而非让前端自己过滤** | "在线 + 已启用"是**业务规则**，收敛在后端一处，避免前端各处重复实现、口径不一 |
| 2 | **批量处置用 `PUT` 而非 `POST`** | `PUT` 语义幂等——重复提交同一批告警不会产生额外效果 |
| 3 | **`/api/alarms` 与 `/api/alarms/search` 并存** | 前者走 MongoDB（业务查询），后者走 ES（检索层）。**保留两条路径本身就是对"异构存储分工"的说明** |
| 4 | **统计接口全部走 ES 聚合，不走 MongoDB** | `terms` / `date_histogram` 是 ES 原生能力，底层靠 `doc_values` 列式存储，效率远高于在文档库里写聚合管道 |
| 5 | **设备通道单独一个接口而非复用现有接口** | 设备与人的认证方式根本不同（HMAC vs JWT），混在一起会让权限规则变得难以理解 |

## 七、速查表

```text
【三层接口】
  组件接口   平台 ↔ 中间件      Kafka / MongoDB / WebHDFS / ES REST
  业务接口   外部 ↔ 平台        REST，31 个端点
  前后端     前端 ↔ 后端        认证头 + {total,items} + 统一错误体

【两条认证通道】
  人机通道   Authorization: Bearer <JWT>   → 角色校验
  设备通道   X-Device-No / Ts / Token      → HMAC 校验

【三种权限规则】
  ADMIN       /api/devices 写 + /api/users
  登录用户    其余业务接口（对齐需求中的参与者定义）
  设备令牌     /api/media/upload-auth

【前端五约定】
```
