# 微服务演进路线与扩展性设计

> **本文档回答三个问题**：
> ① 当前"模块化单体"到"微服务"该怎么拆、按什么顺序拆？
> ② 拆完之后，高并发与网络问题怎么解决？
> ③ 日后要接入新的监控设备类型（固定摄像头、门禁、环境监测站…）该怎么办？
>
> **配套文档**：《[需求分析与总体架构技术选型.md](需求分析与总体架构技术选型.md)》（当前架构）、《[../性能测试/容量评估报告.md](../性能测试/容量评估报告.md)》（实测瓶颈）

---

## 〇、当前状态与本文档的定位

**当前实现**：`platform-service` 是一个 **模块化单体（Modular Monolith）** —— 单个 Spring Boot 应用，内部按领域分包（设备 / 任务 / 告警 / 影像 / 统计 / 认证），模块间通过接口调用解耦。

**这不是权宜之计，而是有意的演进策略**（理由见第七章）。本文档给出**从模块化单体走向微服务的完整路线**，可作为课程报告「第 7 章 总结与展望」的素材。

---

## 一、拆分的判据：不是按技术分层

### 1.1 最常见的错误拆法

照着"技术层次"拆成**消息服务 / 存储服务 / 检索服务**——这是错误的。

**为什么错**：这样拆出来的边界是**技术**，而每次业务变更都要同时改好几个服务。

> **举例**：业务说"告警要支持新阈值"。
> 按技术拆的话，得同时改：消息服务（新增字段）、存储服务（新增表/集合）、检索服务（新增索引）—— **一次需求改三个服务**，跨服务联调、联测、发布成本成倍放大。

### 1.2 正确的判据：四个"不同"

拆分的对象是**"变化或伸缩的原因"**，不是"技术种类"。

| 判据 | 含义 | 拆的信号强度 |
| :--- | :--- | :--- |
| **伸缩特征不同** | 一个需要 100 个实例，一个只需要 2 个 | ★★★ 强 |
| **变化速率不同** | 一个天天改，一个半年不动 | ★★★ 强 |
| **故障影响不同** | 一个挂掉不能拖垮另一个 | ★★ 中 |
| **团队边界不同** | 不同团队分别负责 | ★★ 组织因素 |

**一句话**：**拆的是"变化的原因"，不是"技术的种类"。**

## 二、逐模块分析：谁真的需要独立伸缩

### 2.1 数据接入服务（设备接入 + 遥测写入）★★★ 优先级 P0

| 维度 | 分析 |
| :--- | :--- |
| **伸缩特征** | **与设备数线性相关**。6 台 → 10 万台是 **1.6 万倍**。这是全系统唯一"规模必然爆炸"的点 |
| **业务逻辑** | 几乎为零：收消息 → 攒批 → 写库 |
| **状态** | 无状态，天然可水平扩展 |
| **故障隔离** | 它挂了不应影响查询、告警处置、任务下发 |
| **优化空间** | 攒批大小、Mongo 连接池、消费并行度——**全部只与它相关** |

**结论：第一个必须拆。它与设备管理、告警逻辑没有任何耦合的理由。**

### 2.2 检索分析服务（读路径）★★★ 优先级 P0

| 维度 | 分析 |
| :--- | :--- |
| **读写特征** | **完全相反**。写：高频小消息、顺序追加；读：低频大查询、随机聚合 |
| **资源冲突** | 一个跨月聚合查询能吃掉大量 CPU / 内存 / ES 连接——与写入服务同进程会**直接拖垮接入** |
| **伸缩方向** | 前端用户增长 → 扩读实例；设备增长 → 扩写实例。**两个方向不该绑定** |

**这是最经典的读写分离拆分点。** 现实中"统计接口把线上写入服务拖挂"是高频事故，隔离收益极大。

### 2.3 告警服务 ★★ 优先级 P1

| 维度 | 分析 |
| :--- | :--- |
| **变化速率** | **极高**。告警规则是业务最常改的东西（今天加气体阈值、明天加温度、后天加联动） |
| **可靠性** | 需要**独立死信队列 + 重试**。遥测丢一条无所谓，**告警丢一条是事故** |
| **伸缩** | 与事件量相关，远小于遥测量 |

**核心理由是"变化速率"**：告警规则天天改，若与接入服务同一部署单元，每次改规则都要重启接入服务。

### 2.4 任务调度服务 ★★ 优先级 P1

| 维度 | 分析 |
| :--- | :--- |
| **状态** | 有状态（六态任务状态机），且状态重要 |
| **可靠性** | 指令下发必须保证，需要独立的超时扫描与重发 |
| **伸缩** | 与人操作频率相关，**低频**——不需要多实例，但需要**高可靠** |

**它的诉求是"隔离与可靠"，与接入服务的"高吞吐"诉求完全相反**，因此应分开部署、独立调优。

### 2.5 影像服务 ★★ 优先级 P2

| 维度 | 分析 |
| :--- | :--- |
| **资源特征** | **大文件 + 高带宽**，与消息处理是两种完全不同的负载 |
| **伸缩** | 存储容量与带宽需求独立于其他一切 |
| **可演进** | 未来可接 CDN、对象存储（S3 / OSS）、独立生命周期管理 |

**上传下载占满带宽时，不该让心跳消息一起卡住。**

### 2.6 认证服务 ★ 优先级 P2

全局共享、调用频繁、变化少 → 独立后可集中缓存。
企业环境通常不自研，而是**对接统一认证**（LDAP / OAuth2 / SSO / 企业微信）——独立出来是为了**将来能替换**。

### 2.7 设备台账 / API 聚合层 优先级 P3

低频写、读取也轻。**优先级最低**，可留在 API 层，出现压力再拆。

## 三、拆分优先级总表

按「伸缩压力 × 变化频率」排序：

```text
P0  数据接入服务        ← 唯一随设备数线性爆炸；无业务逻辑；必须最先能独立扩容
P0  检索分析服务        ← 读写隔离；一个慢查询不能拖垮写入
──────────────────────────────────────────────────────
P1  告警服务            ← 规则高频变化 + 需要独立死信重试
P1  任务调度服务        ← 高可靠诉求，与高吞吐诉求冲突
──────────────────────────────────────────────────────
P2  影像服务            ← 带宽 / 存储独立演进
P2  认证服务            ← 全局共享，为替换统一认证预留
──────────────────────────────────────────────────────
P3  设备台账 / API 聚合  ← 有压力再拆
```

> **注意两类不同的拆分理由**：
> P0 是**因伸缩**而拆；P1 是**因变化频率与可靠性**而拆。二者的驱动力完全不同，不能混为一谈。

## 四、拆进程只是第一步：必须配套解决的问题

拆分本身不产生价值，**解决下面这四类问题才产生价值**。

### 4.1 分区数与数据倾斜 ★ 已有实测依据

《容量评估报告》的实测结论：**当前所有 topic 只有 1 个分区，消费并行度被物理锁死为 1**。设备数上去后：

- 分区数必须提高（例如 12 / 24 个）
- **但会引入新问题：数据倾斜**。当前用 `deviceNo` 作分区键以保证"同一设备消息有序"，设备多了之后，上报频率高的"热门设备"会撑爆单个分区

**解法**：用 `deviceNo + 时间窗` 作复合键（如 `DOG-001#2026091710`），**牺牲"同设备全序"换取分区均衡**。

> **这是一个必须做的取舍，不是免费的**。答辩时应能说清代价。

### 4.2 背压与流控

设备暴增时真正的崩溃链条：

```text
设备数暴涨 → Kafka 堆积 → 消费端拉得过快 → 堆内存爆 → OOM
```

**必须有的措施**：

| 措施 | 作用 |
| :--- | :--- |
| `max.poll.records` 调优 + 消费端限流 | 控制单次拉取量，避免内存暴涨 |
| **死信队列（DLQ）** | 处理失败的消息不能无限重试、卡住整个分区 |
| **监控指标用 LAG，不是 CPU** | LAG 增长才是"处理不过来"的直接证据（性能测试已论证） |

### 4.3 网络问题：当前项目存在真实隐患 ⚠

代码审查发现：`AlarmService` / `HdfsService` / `StatsService` 中的三个 `HttpClient` **均未配置超时**，Java 默认是**无限等待**。

**在单机 Docker 环境下不会暴露，一上真实网络就是生产事故**：

```text
ES 响应变慢 → 消费线程全部阻塞在等待 → 整条消费链路停止 → Kafka 堆积
```

企业级必须具备：

| 能力 | 作用 |
| :--- | :--- |
| **超时** | connect timeout + request timeout，必须显式配置 |
| **重试 + 指数退避** | 应对瞬时抖动 |
| **熔断** | 下游持续失败时快速失败，避免耗尽线程池 |
| **降级** | ES 不可用时，检索功能降级，但**写入必须继续** |

### 4.4 幂等机制要升级

当前设备侧的 `processedMsgIds` 是一个**无界的 `Set`**，长时间运行必然内存泄漏。

| 方案 | 特点 |
| :--- | :--- |
| Redis + TTL | 最常用；去重窗口可控 |
| 布隆过滤器 | 空间效率极高，但**有假阳性**（可能误判未处理过的消息为已处理） |

## 五、关键扩展设计：如何接入新的设备类型

**这一节决定系统是"能长大"，还是"每加一种设备就改一遍"。**

### 5.1 现状的问题

当前 `deviceType` 只有 `DRONE` / `ROBOT_DOG` 两种，且**每种消息对应一个独立的 `@KafkaListener`**（共 6 个消费者类）。

接入一种"固定摄像头"需要改动：

- 仿真端：新增一个设备类
- 平台端：新增一个 Consumer
- 前端：新增类型判断分支
- 代码中散布大量 `if (deviceType == DRONE) ...`

**这是"对修改开放"，设备类型越多越混乱。**

### 5.2 改进设计：把设备类型"数据化"

**① 设备类型定义从枚举变为配置**（新增 `device_type` 集合）

```json
{
  "typeCode": "FIXED_CAMERA",
  "name": "固定摄像头",
  "capabilities": {
    "reportsPosition": false,
    "reportsSensor": false,
    "reportsMedia": true,
    "mediaIntervalSec": 30,
    "supportsCommand": false
  }
}
```

**② 消息契约泛化**

统一的 `DeviceEventMessage`：以 `eventType`（HEARTBEAT / POSITION / SENSOR / MEDIA / ALARM）区分事件，`payload` 承载类型特有的字段。

**③ 消费者改用策略模式路由**

一个通用消费者 + `Map<String, EventHandler>`：

```java
EventHandler handler = handlers.get(msg.eventType());
if (handler == null) {
    deadLetterQueue.send(msg);      // 未知事件类型落死信队列，不阻塞分区
    return;
}
handler.handle(msg);
```

**④ 前端按能力动态渲染**

设备详情面板读取 `capabilities` 决定显示哪些字段，而不是写死 `if (type == DRONE)`。

### 5.3 收益

> **新增一种设备类型 = 加一条配置 + 注册一个 Handler，平台骨架零修改。**

这是**开闭原则（OCP）—— "对扩展开放，对修改关闭"** 在架构层面的落地，也是"日后要接入其他监控设备"的真正解法。

## 六、演进路线

```text
阶段 0  模块化单体  ← 当前所处阶段
        关键：把【模块边界】画对，内部按领域分模块、通过接口调用
        ★ 这一步做好了，后续拆分是"搬代码"；做不好就是"重写"

阶段 1  拆出 P0 两个服务：数据接入 + 检索分析
        理由：这两条的伸缩特征与读写特征最冲突，收益最大

阶段 2  拆出 P1 两个服务：告警 + 任务调度
        理由：它们有独立的可靠性诉求与变更频率

阶段 3  影像服务、认证服务
        并引入统一网关治理：超时、重试、熔断、限流、链路追踪
```

### 为什么是"分阶段"而不是"一次拆完"

**关键澄清**：分阶段**不是因为课程学时不够**，而是因为下面三条在真实企业里同样成立：

| # | 理由 |
| :--- | :--- |
| 1 | **拆错的代价高于不拆**。边界画错后改回来是重写级的成本。先用单体把边界验证对，再物理拆分，风险最小 |
| 2 | **拆分引入的新问题需要配套解**。超时、重试、熔断、分布式追踪、跨服务调试——不解决这些，拆完只会更难维护 |
| 3 | **Monolith First 是业界主流策略**。Martin Fowler、Sam Newman 均主张"先把模块边界做对，再按压力拆"。Shopify、Stack Overflow 至今仍是模块化单体——不是拆不动，是没必要 |

## 七、落地动作清单（按优先级）

| # | 动作 | 成本 | 为什么优先 |
| :--- | :--- | :--- | :--- |
| 1 | **给 3 个 HttpClient 加超时** | 5 行代码 | 消除一个真实的生产事故隐患 |
| 2 | **消息契约泛化 + Handler 策略路由** | 中 | "能长大"的地基，越早做越省事 |
| 3 | **设备类型数据化（capabilities 配置）** | 中 | 让"加设备"变成加配置而非改代码 |
| 4 | **topic 分区数提高 + 复合 key** | 小 | 已实测的硬瓶颈 |
| 5 | **拆数据接入服务** | 大 | 第一个真正独立的进程 |
| 6 | **拆检索分析服务** | 大 | 读写隔离 |
| 7 | 引入 Redis（幂等去重 + 缓存）、死信队列、熔断 | 中 | 高并发配套 |
| 8 | 告警 / 任务 / 影像 / 认证服务 | 大 | 按需 |

## 八、结论

> **企业级做法不是"拆得越多越好"，而是**：
> **① 先把模块边界画对；② 再按伸缩压力与变化频率逐段拆分；③ 每拆一段，配齐它的治理手段（超时、重试、熔断、死信、幂等）。**
>
> 当前项目处于**阶段 0（模块化单体）**：模块边界已按领域划分、依赖方向清晰，**具备向微服务演进的基础**。文档第四章列出的问题（分区倾斜、背压、网络超时、幂等升级）是演进过程中必须同步解决的配套项。
