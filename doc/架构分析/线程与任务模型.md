# 仿真端线程与任务模型

> **这份文档回答一个问题**：设备、任务、线程这三者是什么关系？为什么"每台设备一个线程池"的设计会在设备数上来之后崩溃？
>
> 本文的结论是 **C 组规模扫描实验**（见《[性能压测实验手册.md](性能压测实验手册.md)》第四章）的理论依据。

---

## 一、三个概念

| 概念 | 是什么 | 在本项目里 | 消耗的资源 |
| :--- | :--- | :--- | :--- |
| **设备** | 一个**逻辑实体**，就是个 Java 对象 | `DroneSimulator` / `RobotDogSimulator` 实例 | **仅内存**（几十字节），**不消耗线程** |
| **任务** | 一段**待执行的代码**，被登记为"每隔 N 秒跑一次" | `Runnable`，如 `sendHeartbeat` | **不消耗资源**，只是一条排队记录 |
| **线程** | 真正干活的 **OS 级执行单元** | `sim-sched-0` … `sim-sched-27` | **CPU 时间 + 约 1 MB 线程栈** |

**核心判断**：

> **设备不消耗线程，任务才消耗线程 —— 而且只在任务触发的那一瞬间消耗。**

一台设备"活着"的表现，本质上就是**它注册的几个定时任务在周期性地被触发**。设备对象本身只是内存里存着"我电量多少、我走到哪了"的一块数据，它不占用任何 CPU。

---

## 二、关系图

```text
        注册                排队等待              分配
设备 ──────────→ 任务 ──────────────→ 线程池 ──────────→ 线程执行
(对象)          (Runnable)          (共享资源)         (OS 资源)
  │                 │                    │
  │                 │                    └─ 人手有限，轮流干
  │                 └─ 99.9% 的时间在"等待下一次触发"
  └─ 只提供状态（电量 / 位置 / 路线），不提供算力
```

**读法**：设备是**组织单位**，任务是**工作单位**，线程是**执行单位**。设备通过"注册若干任务"来表达"我需要周期性地做这些事"。

### 用代码对照

```java
// ① 设备 = 一个对象（DroneSimulator 实例）
new DroneSimulator("UAV-001", kafkaTemplate, scheduler, settings)

// ② 注册任务 = 告诉调度器"这个 Runnable 每 N 秒跑一次"
schedule(this::sendHeartbeat, 0, 5);      // 任务 1
schedule(this::sendPosition,  1, 2);      // 任务 2

// ③ 线程 = 由共享池提供，设备对象里不持有
scheduler.scheduleAtFixedRate(task, initialDelay, period, TimeUnit.SECONDS);
```

## 三、本项目注册了哪些任务

### 3.1 任务清单（精确到代码位置）

**所有设备共有的 2 个任务**（父类 `DeviceSimulator.start()`）：

| 任务 | 周期 | 首次延迟 |
| :--- | ---: | ---: |
| `safeSendHeartbeat` → `sendHeartbeat()` | 5 s | 0 |
| `safeSendPosition` → `sendPosition()` | 5 s（被子类覆盖） | 1 s |

**无人机额外 1 个**（`DroneSimulator.onStarted()`）：

| 任务 | 周期 | 首次延迟 |
| :--- | ---: | ---: |
| `sendMediaMeta` → 航拍影像元数据 | 10 s | 3 s |

**机器狗额外 2 个**（`RobotDogSimulator.onStarted()`）：

| 任务 | 周期 | 首次延迟 |
| :--- | ---: | ---: |
| `sendSensor` → 环境传感器 | 3 s | 2 s |
| `sendMediaMeta` → 红外影像元数据 | 12 s | 5 s |

### 3.2 汇总

| 设备类型 | 任务数 | 位置周期 | 实际消息速率 |
| :--- | ---: | ---: | ---: |
| 无人机 UAV | **3** | 2 s | 0.80 条/秒 |
| 机器狗 DOG | **4** | 3 s | 0.95 条/秒 |

**6 台设备（3 + 3）= 3×3 + 3×4 = 21 个任务。**

> 注意：**任务数 ≠ 消息数**。一个任务一次触发发一条消息，但告警是**数据驱动**的（在 `sendSensor` / `sendMediaMeta` 内部按概率触发），不单独占任务。

### 3.3 一次性任务

指令回执走的是 `scheduleOnce()`，不是周期任务：

```java
scheduleOnce(() -> sendTaskAck(cmd.taskId(), "STARTED",  0, "任务开始执行"), 1);
scheduleOnce(() -> sendTaskAck(cmd.taskId(), "PROGRESS", 50, "执行中"),       4);
scheduleOnce(() -> sendTaskAck(cmd.taskId(), "FINISHED", 100, "任务执行完成"), 8);
```

这类任务**短命**（执行完就消失），不登记进 `periodicTasks`，也不贡献稳定的线程占用。

## 四、任务数 ≠ 线程数

这是最容易混淆的一点。

### 4.1 为什么任务不需要一对一配线程

因为**定时任务绝大部分时间在睡觉**：

```text
sendHeartbeat 的时间轴（周期 5 秒）：

 触发 ├─ 跑约 1 毫秒 ─┤                                          触发 ├─ 跑约 1 毫秒 ─┤
                     └──────────── 睡觉 4999 毫秒 ─────────────────┘

                     这 4.999 秒里，它没有占用任何线程
```

**线程只在"跑的那 1 毫秒"被占用，跑完立刻还回池子**去执行别的任务。所以

> **28 个线程服务 1750 个任务在数学上完全成立** —— 只要任务不是全部"撞"在同一时刻。

### 4.2 JDK 的实际行为

`ScheduledThreadPoolExecutor` 的线程是**按需创建**的，触发条件是：

```java
// 每次调用 schedule*() 时
void ensurePrestart() {
    int wc = workerCountOf(ctl.get());
    if (wc < corePoolSize)
        addWorker(null, true);      // ← 新建一个线程
    else if (wc == 0)
        addWorker(null, false);
}
```

**含义**：每注册一个任务，只要当前线程数还没到核心线程数上限，就建一个线程。

这直接决定了旧代码和新代码的差异 —— 见下节。

## 五、旧设计的缺陷

### 5.1 问题代码

```java
// DeviceSimulator.java（改造前）
protected final ScheduledExecutorService scheduler = Executors.newScheduledThreadPool(4);
```

**这是一个实例字段** —— 每 `new` 一台设备就创建一个 4 线程池。

### 5.2 后果推导

按 §4.2 的 JDK 行为：

```text
一台无人机  →  注册 3 个任务  →  3 < 4，建 3 个线程
一台机器狗  →  注册 4 个任务  →  4 = 4，建 4 个线程
```

**任务数与线程数被绑成了 1:1**，尽管这些线程 99.9% 的时间都在睡觉。

| 设备总数 | 任务总数 | 旧实现线程数 | 线程栈内存（约 1 MB/线程） |
| ---: | ---: | ---: | ---: |
| 6 | 21 | 21 | 21 MB |
| 50 | 175 | 175 | 175 MB |
| 100 | 350 | 350 | 350 MB |
| **500** | **1750** | **1750** | **约 1.75 GB** |
| 1000 | 3500 | 3500 | **约 3.5 GB** |

### 5.3 为什么这是"假瓶颈"

**关键在于：这个瓶颈和系统架构毫无关系，纯粹是仿真代码的实现问题。**

设备还没把 Kafka 压垮，**操作系统的上下文切换开销先把机器打垮了**。如果拿这样的数据去评估平台容量，测出来的"上限"其实是仿真器自己的上限，**结论是错的**。

> 这也是性能测试的一条通用纪律：**压测工具本身的瓶颈必须先排除，否则测的是工具不是系统。**

## 六、改造后的模型

### 6.1 新设计

```java
// 新建 config/SimulatorSchedulerConfig.java
@Bean(destroyMethod = "shutdown")
public ScheduledExecutorService deviceScheduler(SimulatorSettings settings) {
    int threads = settings.getSchedulerThreads() > 0
            ? settings.getSchedulerThreads()
            : Math.max(4, Runtime.getRuntime().availableProcessors());
    // 全局唯一，所有设备注入同一个
}
```

设备通过构造器注入这个共享池，自己**不再持有线程池**。

### 6.2 效果对比

| 设备总数 | 任务总数 | 改造前线程数 | **改造后线程数** |
| ---: | ---: | ---: | ---: |
| **6** | 21 | 21 | **21** ← 一样 |
| 50 | 175 | 175 | **28** |
| 100 | 350 | 350 | **28** |
| 500 | 1750 | 1750 | **28** |
| 1000 | 3500 | 3500 | **28** |

改造后线程数**恒为 28**（= `max(4, CPU 逻辑核数)`），与设备数彻底解耦。

> **⚠ 实验时的注意点**：6 台设备时 21 个任务还没撑到 28 的上限，
> **两种实现碰巧结果相同** —— 所以**不能用"6 台时线程数没变"来判断改造失败**。
> 差别要到 **50 台以上**才显现。真正的验证点是 C2 里 **500 台时线程数仍是 28**。

### 6.3 配套的保活机制

改造引入了一个**必须处理的副作用**：

本工程**不是 Web 应用**（`@SpringBootApplication` 但不开端口），进程存活完全依赖池里的**非守护线程**。

- **改造前**：每台设备自带线程池，天然把 JVM 撑住
- **改造后**：只剩一个共享池，**若池里没有任何任务，就没有线程，主线程一结束 JVM 立刻退出**

因此显式声明：

```java
t.setDaemon(false);   // 非守护：保证有设备任务在跑时 JVM 不会退出
```

并在设备数为 0 时给出警告。**这是改造中最容易踩的坑，也是实验 C1 的必做检查点。**

## 七、线程数该设多少

线程数不是越多越好，也不是越少越好。

| 线程数 | 后果 |
| :--- | :--- |
| **太少** | 任务排队等线程 → **实际发送周期被拉长** → 实测速率低于理论速率 |
| **太多** | 大量线程在睡觉，但每个占约 1 MB 栈内存；上下文切换开销上升 |
| **合适** | 任务基本不排队，线程数可控 |

**经验值**：这种"**短任务、长间隔**"的场景，线程数取 **CPU 核数**是合理起点，可用 `sim.device.scheduler-threads` 覆盖。

### 7.1 本项目有一个加速恶化的因素

发送影像元数据的任务里包含**写磁盘**操作：

```java
String localPath = generatePlaceholderFile(fileId, size);   // 真实文件 I/O，阻塞
```

磁盘 I/O 是**阻塞**的，耗时毫秒级（比 CPU 计算长几个数量级）。500 台设备时影像任务频繁触发，**多个线程同时卡在磁盘写入上**，可用于其他任务的线程就少了 —— 这会放大"线程不够"的影响。

### 7.2 实验中的判据

C2 组要专门对比"实测速率 vs 理论速率"，并按下表归因：

| 现象 | 含义 | 调节手段 |
| :--- | :--- | :--- |
| 速率不达标 + **LAG = 0** | **设备侧排队**（线程不够，或磁盘 I/O 拖慢） | `--sim.device.scheduler-threads=64`<br>`--sim.device.write-media-files=false` |
| 速率不达标 + **LAG 上涨** | **平台侧到顶**（消费不过来） | 见 E1：加分区分 + 提消费并发 |

**这个判据的意义**：同样是"速率上不去"，两种归因的**优化方向完全相反** —— 一个要加设备侧线程，一个要改平台侧架构。分不清就会优化错方向。

## 八、验证方法

### 8.1 数线程数

```powershell
# 找到仿真端 PID
Get-Process java | Select-Object Id, WS

# 数 sim-sched- 开头的线程（JDK 路径按本机调整）
& "D:\school\all\config\jdks\jdk-25.0.3\bin\jcmd.exe" <PID> Thread.print |
  Select-String "sim-sched-" | Measure-Object
```

**预期**：不管跑 6 台还是 500 台，结果都是 **28**。

### 8.2 对照实验（可选，很有说服力）

在 500 台档位下，分别用 `--sim.device.scheduler-threads=28` 和 `=128` 各跑一次，对比：

| 线程数 | 实测速率 | 是否达到理论值 |
| ---: | ---: | :--- |
| 28 | | |
| 128 | | |

若 128 时速率明显上升 → 说明 **28 线程确实不够，任务在排队** —— 直接量化了"线程池大小"这个参数的影响。

## 九、与答辩的关系

这个知识点适合回答以下提问：

| 可能的提问 | 回答要点 |
| :--- | :--- |
| **"你们做过性能优化吗？"** | 举这个例子：定位到一个"设备数 × 4"的线程爆炸问题，改成共享池后线程数从 1750 降到 28，且与设备数解耦。 |
| **"瓶颈分析怎么做？"** | 强调**先排除压测工具自身的瓶颈** —— 否则测的是工具不是系统。这就是一个真实的例子。 |
| **"任务和线程什么关系？"** | 用"组织单位 / 工作单位 / 执行单位"三层来讲，强调**定时任务 99.9% 时间在睡觉**，所以少量线程可以服务大量任务。 |
| **"加线程能提升性能吗？"** | 分情况：**设备侧排队**时加线程有效；**平台侧到顶**时加线程无效，必须改架构（加分区分 + 提并发）。 |

## 附录：一页速记

```text
设备 (对象)  ──注册──→  任务 (Runnable)  ──排队──→  线程池 (共享)  ──分配──→  线程 (OS)

· 设备只占内存，不占线程
· 任务只在触发的那一瞬间占线程   ← 定时任务 99.9% 时间在睡觉
· 线程数应由"并发任务数"决定，而不是"设备数"

无人机 = 3 个任务（心跳 / 位置 / 影像）
机器狗 = 4 个任务（心跳 / 位置 / 传感器 / 影像）

旧设计：线程池是设备实例字段  →  线程数 = 任务数  →  500 台 = 1750 线程  ✗
新设计：全局共享一个池        →  线程数 = 28 常数  →  500 台 = 28 线程    ✓
```
