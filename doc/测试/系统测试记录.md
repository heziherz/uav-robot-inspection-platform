### A-1 设备身份门禁生效 ✅

**验证方法**：观察仿真端与平台端日志的授权链路。

**实际结果**：

```text
设备端： [存储] 上传成功: /uav/media/DOG-001/20260920/IR-DOG-001-1789875762715.jpg (1024 字节)
平台端： [上传授权] DOG-001 已获准上传（INFRARED）→ /uav/media/DOG-001/20260920/IR-DOG-001-1789875762715.jpg
平台端： [影像入库] IR-DOG-001-1789875762715 已归档: /uav/media/DOG-001/20260920/...
```

**结论**：完整链路打通 —— 设备申请授权 → 平台校验 HMAC 令牌并签发路径 → 设备按签发路径上传 → 平台校验路径规范后入库。

### A-2 设备令牌被拒（反向验证）✅

**验证方法**：用**错误的密钥**启动一个临时仿真端容器，观察是否被拒绝。

**实际结果**：

```text
[UAV-002] 上传授权被拒绝（401）: {"status":401,"message":"设备令牌无效或已过期"}
[UAV-002] 未获上传授权，本次跳过上报
```

**结论**：**密钥不一致就传不上去** —— 这是设备令牌机制的验收测试，证明门禁真正生效，而非装饰。

### A-3 Kafka 分区数提升 ✅

**验证方法**：`deploy/init/alter-topics.ps1 -Show`

**实际结果**：7 个 topic 分区数**全部为 3**（改造前 6 个上行 topic 均为 1）。

```text
topic_device_alarm        3        topic_device_media_meta   3
topic_device_gps          3        topic_device_sensor       3
topic_device_heartbeat    3        topic_device_task_ack     3
topic_platform_command    3（原本就是 3）
```

### A-4 Nginx 负载均衡 ✅

**验证方法**：连续请求，观察响应头 `X-Upstream`（该头在 Nginx 配置中新增，用于回传实际处理请求的后端）。

**实际结果**：

| 请求次数 | 172.18.0.10（实例1） | 172.18.0.7（实例2） |
| ---: | ---: | ---: |
| 20 | 16 | 4 |
| 100 | 49 | 51 |
| 100 | 50 | 50 |
| 30（恢复后） | 15 | 15 |

**结论**：长期分布精确均衡。**20 次时的 16:4 是小样本波动**——Nginx 采用 `worker_processes auto`（28 个 worker），轮询计数器是**每 worker 独立**的，短窗口内分布可能不均，大样本趋于均衡。

### A-5 故障转移 ✅

**验证方法**：停掉 `platform-service-2`，继续请求。

**实际结果**：请求全部转发到存活的 `platform-service-1`；其中 1 次显示 `172.18.0.7:8080,`（逗号表示"先试了它、失败后回退"）——Nginx 首次探测到故障实例的正常行为。**服务全程可用**（HTTP 401 = 接口正常响应，只是未带令牌）。

**结论**：Nginx 被动健康检查生效，单实例故障不影响服务。

## 五、测试发现的问题与修复

### 问题 1：异常处理不统一，校验失败返回 500 ★

**发现方式**：接口测试 IT-02。

**现象**：登录密码错误时返回 `HTTP 500`，而不是 `401`。

**排查过程**：

1. 查看后端日志，发现抛出的异常无人接住：

   ```text
   java.lang.IllegalArgumentException: 用户名或密码错误
       at com.uav.platformservice.service.AuthService.login(AuthService.java:42)
   ```

2. 全项目扫描 `throw` 语句：**共 31 处，但只有 `TaskController` 有一个 `@ExceptionHandler`**。
3. 关键认知：`@ExceptionHandler` 是**控制器级**的，只对声明它的 Controller 生效。

**影响范围**（远大于单个登录接口）：

| 模块 | 异常类型 | 后果 |
| :--- | :--- | :--- |
| 登录 | `IllegalArgumentException` | ❌ 500 |
| 用户管理（8 处校验） | `IllegalArgumentException` | ❌ 全部 500 |
| 设备 / 任务 / 告警 / 影像的资源校验 | `IllegalStateException` / `IllegalArgumentException` | ❌ 500 |
| 任务服务（`TaskController` 有处理器） | `IllegalStateException` | ✅ 400 |

**修复**：引入三个专用异常 + 全局处理器。

| 新增 | 映射 | 语义 |
| :--- | :---: | :--- |
| `BusinessException` | **400** | 业务校验失败（参数非法、状态不允许） |
| `AuthException` | **401** | 认证失败（密码错误、账号停用） |
| `NotFoundException` | **404** | 资源不存在 |
| `GlobalExceptionHandler` | — | `@RestControllerAdvice` 统一处理 |

**关键设计**：**只拦截这三类，其余异常放行**。理由——项目原先把"业务校验失败"和"服务端内部错误"混用了同一异常类型；若一刀切映射为 400，会把 `消息发送失败`、`JWT 签名失败` 这类**真实的服务端故障**误报成"客户端请求有误"，排查时被严重误导。

**验证**：修复后接口测试 **23/23 通过**；异常状态码复验 **13/13 通过**；确认 4 处内部错误仍返回 500。

### 问题 2：资源不存在返回 200 而非 404

**发现方式**：异常状态码复验。

**现象**：`GET /api/devices/NOT-EXIST` 返回 **200 + 空响应体**。

**原因**：`DeviceService.find()` 使用 `orElse(null)`，接口无法区分"没有这个设备"与"请求成功但没数据"。

**修复**：改为 `orElseThrow(() -> new NotFoundException(...))` → 返回 404 + 明确消息。

**排查中确认无需改动的**：另有 7 处 `orElse(null)` 属于正常业务分支（如心跳处理中"设备不存在 = 新设备，需自动注册"），**不能一律改成抛异常**。

### 问题 3：`.gitignore` 误伤正式文件（非代码缺陷）

**发现方式**：提交时发现测试脚本未出现在待提交列表。

**现象**：`.gitignore` 中两条规则

```gitignore
性能测试/         ← 无前导斜杠，匹配【任意层级】的同名目录
deploy/test/
```

导致以下内容**一直未进入版本库**，组员拉取代码时无法获得：

| 内容 | 规模 |
| :--- | :--- |
| `doc/性能测试/` 三份文档 | 约 1300 行 |
| `deploy/test/` 三个脚本 + 载荷 | 约 900 行 |

而仓库根目录**根本没有「性能测试」文件夹**，该规则 100% 是误伤。

**修复**：删除 `性能测试/` 规则；`deploy/test/` 收窄为 `deploy/test/results/`（仅忽略实验产出的 CSV）；补回全部 9 个文件。

## 七、非缺陷的观察项

| # | 观察 | 说明 |
| :-: | :--- | :--- |
| 1 | **回执流水有 ≤2 秒可见延迟** | `task_log` 采用攒批写入（`BATCH_SIZE=20` + 每 2 秒 flush），因此任务状态（实时更新）与回执流水（批量落库）之间会有短暂时间差。实测查询 3 秒后 3 条回执全部出现。**这是设计使然，非缺陷。** |
| 2 | **20 次请求时负载分布不均（16:4）** | Nginx 的轮询计数器是**每 worker 独立**的（`worker_processes auto` = 28）。小样本波动正常，100 次以上趋于精确均衡。 |
| 3 | **新建设备编号由平台生成** | `POST /api/devices` 会**忽略**请求中传入的 `deviceNo`，由 `generateDeviceNo()` 自动分配（如 `UAV-004`）。测试脚本初次未意识到这点，误判为设备创建失败。 |

## 八、测试结论

1. **功能完整性**：设备接入、消息流转、分布式存储、检索分析、任务管理、告警处置、权限控制、影像管理八大模块功能正常，14 项可自动验证的功能用例全部通过。

2. **接口健壮性**：23 项接口测试全部通过；异常路径（未认证 401、越权 403、参数错误 400、资源不存在 404）状态码语义正确，且**服务端内部故障仍如实返回 500**，未被混淆。

3. **本轮修复的缺陷共 3 项**：异常处理不统一（影响 31 处校验）、资源不存在返回 200、`.gitignore` 误伤正式文件。

4. **新增改动的有效性已全部验证**：设备身份门禁（含反向验证）、Kafka 分区数提升、后端双实例负载均衡与故障转移。

5. **待补充**：4 项需界面人工验证的用例（TC-009 / 011 / 016 / 017）；性能测试中的容器资源占用需按 10 容器口径重新采集。
