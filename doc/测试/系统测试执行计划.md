## 三、执行阶段

### 阶段 0：应用待生效的改动

```powershell
cd "D:\school\all\项目\企业项目实践\deploy"
docker compose up -d --force-recreate kafka          # ① 让分区数配置生效
.\init\alter-topics.ps1                              # ② 6 个 topic 提到 3 分区
docker compose up -d --build platform-service-1 platform-service-2   # ③ 双实例
docker rm -f platform-service                        # ④ 移除旧单实例容器
docker compose up -d --force-recreate nginx          # ⑤ 新 upstream 生效
```

**通过标准**：`docker compose ps` 显示 9 个容器 Up。

> ⚠ **内存提示**：9 容器约占 6.1 GiB / 8 GiB（76%）。若 ES 变得不稳定，可停 `platform-service-2` 降回单实例。

### 阶段 1：冒烟测试（不通过则停止）

| # | 检查 | 通过标准 |
| :-: | :--- | :--- |
| 1 | 前端首页 | HTTP 200 |
| 2 | 登录 | 拿到 token |
| 3 | 设备列表 | 6 台 ONLINE |
| 4 | 后端日志 | 无 ERROR |

### 阶段 2：新增改动验证（A 类，5 项）★ 本阶段为重点

| # | 项 | 操作 | 通过标准 | 执行方 |
| :-: | :--- | :--- | :--- | :--- |
| A-1 | **设备令牌生效** | 观察仿真端日志 | 出现 `[上传授权] XXX 已获准上传` 与 `[存储] 上传成功` | 自动 |
| A-2 | **令牌被拒（反向验证）** | 改设备端 `device.token.secret` 后重启 | 出现 `[设备鉴权] 令牌无效或已过期`，上传被拒 | 手动 |
| A-3 | **分区数生效** | `.\init\alter-topics.ps1 -Show` | 6 个 topic 均为 3 分区 | 自动 |
| A-4 | **负载均衡生效** | 连续请求看 `X-Upstream` 响应头 | 在两个实例间交替 | 自动 |
| A-5 | **故障转移** | 停 `platform-service-2` 后继续请求 | 请求全部转至 `platform-service-1`，服务不中断 | 手动 |

> **A-2 是设备令牌机制的验收测试**——密钥不一致就传不上去，证明门禁真正生效。

## 四、记录方式

### 4.1 记录表结构

| 字段 | 说明 |
| :--- | :--- |
| 用例编号 | TC-xxx / IT-xx / A-x / D-x |
| 测试模块 | 设备仿真 / 消息中间件 / 分布式存储 / 检索 / 任务 / 告警 / 权限 / 网关 |
| 测试标题 | 简短描述 |
| 前置条件 | 执行该用例需要的前提 |
| 测试步骤 | 关键操作 |
| 预期结果 | 依据需求规格 |
| **实际结果** | **实测输出（含关键数据）** |
| 测试状态 | 通过 / 不通过 |
| 备注 | 不通过时记录现象与排查 |

### 4.2 数据来源

| 类别 | 记录方式 |
| :--- | :--- |
| A 类、C 类 | 脚本自动生成 Markdown，直接并入记录 |
| B 类、D 类 | 手工记录（含截图编号） |

### 4.3 原则

> **如实记录**——不通过就写不通过，并记录现象与排查过程。
> 指导说明书「学术诚信」条款明确要求：**如实记录项目遇到的问题，不虚构测试结果**。

## 六、风险与应对

| 风险 | 应对 |
| :--- | :--- |
| **内存不足**（9 容器，ES 已占 99.6%） | 停 `platform-service-2` 降回单实例，或停 Kibana 释放约 0.9 GiB |
| **测试数据不足**（告警概率已降至 1%） | 等待积累；或临时调高仿真端告警概率；或用脚本灌数据 |
| **容器被暂停**（宿主机休眠） | `docker unpause` 恢复（已知问题） |
| **某个用例不通过** | **如实记录**，排查后决定修复或写入报告「不足」章节 |
| **报告中的预期值与实测不符** | 以实测为准修改报告，并记录差异原因 |

## 七、执行顺序

```text
阶段 0  应用改动        ← 必须先做，否则后续测的是旧代码
   ↓
阶段 1  冒烟测试        ← 不通过则停止，先修环境
   ↓
阶段 2  新增改动验证     ← ★ 重点：三处新改动还没在运行环境验过
   ↓
阶段 3  功能测试（18）
   ↓
阶段 4  接口测试（23）   ← 脚本自动化
   ↓
阶段 5  性能测试（3）
   ↓
        同步文档、替换报告中的预期值为实测值
```
