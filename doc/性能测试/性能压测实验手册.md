## 〇、实验前必读

### 0.1 三个观测口径（所有实验都在看这三件事）

| 口径 | 看什么 | 工具 | 说明什么 |
| :--- | :--- | :--- | :--- |
| **资源** | 每个容器的 CPU% / 内存 / IO | `collect-stats.ps1` | 谁先到顶 = 瓶颈是谁 |
| **速率** | 每秒产生多少条消息 | `measure-rate.ps1` | 系统的"产出"，与理论值对比 |
| **积压** | 每个 topic 的 LAG | `collect-stats.ps1` | **最关键的判据**，见下 |

### 0.2 唯一的判定标准：LAG

```
LAG = 消息进 Kafka 的速度 － 后端消费掉的速度
```

- **LAG 稳定在 0** → 后端跟得上，**没到瓶颈**
- **LAG 缓慢增长但能回落** → 处于临界区
- **LAG 单调增长不再回落** → **到顶了**，此刻的速率就是当前配置的上限

> 为什么用 LAG 而不是看 CPU：CPU 打满不代表到顶（可能还有余量），LAG 增长才是"真的处理不过来了"的**直接证据**。

### 0.3 已测定的环境快照（作为对照组）

主机：**20 物理核 / 28 逻辑核 / 15.8 GB 内存**；Docker Desktop 分到 **28 CPU + 8 GB**。

**8 个容器空载资源占用（实测）**：

| :--- | ---: | ---: | ---: | ---: |
| elasticsearch | 0.94% | **1020** | 1 GiB | **99.6%** ⚠ |
| kibana | 1.46% | **922** | 1 GiB | **90.0%** ⚠ |
| kafka | 1.88% | 1066 | 无 | — |

## 二、A 组 · 建立基线（不改代码，10 分钟）

### A1 · 资源画像

**目的**：得到"系统空载时各容器吃多少"的静态成本表。

**原理**：容器资源占用分两类 —— **固定成本**（与设备数无关，如 ES/Kibana 的基础内存）和**变动成本**（随负载增长，如 MongoDB 随写入增长）。分清楚这两类，才能解释 D 组的内存曲线为什么不是直线。

**操作**：
```powershell

# 顺便看各容器的内存限额
docker inspect --format "{{.Name}} -> {{.HostConfig.Memory}}" $(docker ps -q)
```

**预期**：数字与 §0.3 的表接近（ES/Kibana 会很高，因为它们各限了 1 GB 且空闲也占满）。

**怎么读**：`HostConfig.Memory = 0` 表示**没设限额**。ES/Kibana 有值（1073741824 = 1 GiB）。

**记录**：

**目的**：确认 6 台设备的实际速率，作为后续所有档位的对照原点。

## 三、B 组 · 灌数据压平台侧（不改代码，30 分钟）

**这组的定位**：用 Kafka 官方压测工具**绕开设备侧**，直接往 topic 灌合法消息，**单独逼出平台侧（消费 + 存储）的吞吐上限**。快、可重复、不依赖仿真端。

### B1 · 单 topic 阶梯加压

**目的**：找出"平台侧每秒能消化多少条消息"。

**原理**：后端每个 topic 只有 **1 个消费线程**（6 个消费者各 1 线程，且 topic 只有 1 个分区）。单线程做着"解析 JSON → 攒批 → 写 MongoDB"的活。速率一旦超过它的处理能力，消息就在 Kafka 里堆积 —— 也就是 LAG 开始涨。

**操作**：

```powershell
# ---------- 第 0 步：把合法载荷送进 Kafka 容器 ----------
cd "D:\school\all\项目\企业项目实践"
docker cp deploy\test\payloads\sensor.jsonl kafka:/tmp/sensor.jsonl

# ---------- 第 1 步：确认压测脚本存在（不同版本名字可能不同）----------
docker exec kafka ls /opt/kafka/bin/ | findstr perf
# 预期看到 kafka-producer-perf-test.sh

# ---------- 第 2 步：起采集（另开一个 PowerShell 窗口，保持运行）----------
cd deploy\test
.\collect-stats.ps1 -Tag "B1-ladder" -IntervalSec 5 -DurationSec 600

# ---------- 第 3 步：回到第一个窗口，逐档加压 ----------
# 每档跑 60 秒，中间不断档地观察 LAG

# --- 档位 1：100 msg/s ---
docker exec kafka /opt/kafka/bin/kafka-producer-perf-test.sh `
  --topic topic_device_sensor `
  --num-records 6000 --throughput 100 `
  --payload-file /tmp/sensor.jsonl `
  --producer-props bootstrap.servers=localhost:9092

# --- 档位 2：500 msg/s ---
docker exec kafka /opt/kafka/bin/kafka-producer-perf-test.sh `
  --topic topic_device_sensor `
  --num-records 30000 --throughput 500 `
  --payload-file /tmp/sensor.jsonl `
  --producer-props bootstrap.servers=localhost:9092

# --- 档位 3：1000 msg/s ---
docker exec kafka /opt/kafka/bin/kafka-producer-perf-test.sh `
  --topic topic_device_sensor `
  --num-records 60000 --throughput 1000 `
  --payload-file /tmp/sensor.jsonl `
  --producer-props bootstrap.servers=localhost:9092

# --- 档位 4：2000 msg/s ---
docker exec kafka /opt/kafka/bin/kafka-producer-perf-test.sh `
  --topic topic_device_sensor `
  --num-records 120000 --throughput 2000 `
  --payload-file /tmp/sensor.jsonl `
  --producer-props bootstrap.servers=localhost:9092
```

> `--num-records 6000 --throughput 100` = 以 100 条/秒的限速发 6000 条，正好 60 秒。
> 档位越高，`--num-records` 同比放大以保持 60 秒时长。
>
> **每档结束前**，在采集窗口旁边另开一个窗口看实时 LAG：
> ```powershell
> docker exec kafka /opt/kafka/bin/kafka-consumer-groups.sh --bootstrap-server localhost:9092 --describe --all-groups
> ```

**预期**：低档位（100/500）LAG 保持 0；某档开始 LAG 持续上涨不回落。

**怎么读**：

| 现象 | 含义 |
| :--- | :--- |
| LAG 全程 0 | 平台侧还没到顶，继续加档 |
| LAG 涨了但停下来后又回落到 0 | 临界区，上限就在这附近 |
| **LAG 单调上涨不回落** | **到顶了，记下这一档的 msg/s 作为上限** |
| 灌数据本身报文里 `records/sec` 远低于 `--throughput` | **瓶颈在生产者侧**（Kafka 单分区写），不是消费者侧 —— 这本身也是结论 |

| 100 | | | |

### B2 · 定位"先垮的是谁"

**目的**：LAG 到顶的那一刻，**找出是哪个组件先撑不住**。

**原理**：整条消费链路是 **Kafka → 消费线程 → MongoDB / Elasticsearch**。任何一环变慢，前面全会堵住。看谁的资源曲线先异常，谁就是瓶颈。

**操作**：回到 B1 到顶的那一档，重跑一次，同时：

```powershell
# 窗口 1：资源采集
.\collect-stats.ps1 -Tag "B2-bottleneck" -IntervalSec 3 -DurationSec 180

# 窗口 2：实时盯 ES 堆（同步进行）
while ($true) {
  curl.exe -s "http://localhost:9200/_cat/nodes?v&h=heap.percent,heap.current,heap.max,cpu"
  Start-Sleep -Seconds 5
}

# 窗口 3：实时盯 MongoDB
while ($true) {
  docker exec mongodb mongosh --quiet --eval "const s=db.serverStatus(); print('conn='+s.connections.current+' insert='+s.opcounters.insert+' query='+s.opcounters.query)"
  Start-Sleep -Seconds 5
}
```

**怎么读**：

| 现象 | 瓶颈 |
| :--- | :--- |
| **ES `heap.percent` 逼近 100** | ES 内存不足（**最可能**，因为已占 99.6%） |
| MongoDB `connections` 逼近 100 | Mongo 连接池耗尽（驱动默认 `maxPoolSize=100`） |
| 两者都正常，但 `platform-service` CPU 单核打满 | 消费线程算力到顶（单分区单线程） |
| 都正常，LAG 却涨 | 下游同步阻塞（写 ES 是同步 HTTP，见 E2） |

**记录**：

| 组件 | 到顶时的值 | 是否触及上限 |
| :--- | :--- | :--- |
| Elasticsearch heap | | |
| MongoDB 连接数 | | |
| platform-service CPU | | |

### B3 · 多 topic 并发灌

**目的**：验证"6 个消费者是不是真并行"。

**原理**：后端有 **6 个独立的 `@KafkaListener`**，各自一个容器/线程。理论上它们互不干扰，总吞吐应该是单 topic 的若干倍。但 `@Scheduled` 刷盘、Mongo 连接池、Tomcat 线程是共享的，实际会互相拖累。

**操作**：同时开 3 个 PowerShell 窗口，分别对 `topic_device_heartbeat` / `topic_device_gps` / `topic_device_sensor` 灌数据（各用 B1 的到顶速率），持续 60 秒。

> 心跳和 GPS 的载荷结构不同，需要各自的 payload 文件。**最省事的做法**：直接用**仿真端**当负载源（见 C 组），它会同时产生全部 6 种消息且内容天然合法 —— 若嫌构造载荷麻烦，B3 可以并入 C 组做。

**怎么读**：若三路并发时**总吞吐 ≈ 单路吞吐**（没有提升），说明它们实际在互相争抢同一个下游资源。

### C2 · 规模阶梯扫描

**目的**：得到"设备数 → 资源 / 速率 / 积压"的完整曲线。

**原理**：设备数增加时消息速率应**近似线性增长**（每台速率固定）。当某一档开始"设备数翻倍但速率不翻倍"，就说明设备侧或平台侧到拐点了。

**操作**：

```powershell
# ---------- 档位 1：50 台（25 + 25）----------
cd "D:\school\all\项目\企业项目实践\backend\device-simulator"
.\mvnw spring-boot:run "-Dspring-boot.run.arguments=--sim.device.drone-count=25 --sim.device.dog-count=25 --sim.device.log-payload=false"

# ---------- 稳定 60 秒后，在另一个窗口采集 3 分钟 ----------
cd "D:\school\all\项目\企业项目实践\deploy\test"
.\collect-stats.ps1 -Tag "C2-50dev" -IntervalSec 5 -DurationSec 180
# 采集结束后立刻测速率
.\measure-rate.ps1 -WindowSec 30
```

档位 2/3/4 依次把 `drone-count` / `dog-count` 改成 **50/50、100/100、250/250**，标签对应改成 `C2-100dev` / `C2-200dev` / `C2-500dev`。

> **每档之间要停掉上一档的仿真端**（Ctrl+C），避免设备叠加。
>

## 五、D 组 · 内存梯度标定（核心实验，最耗时）

> **这组回答你的核心问题**：**每增加 1 GB 内存，能多扛多少台设备？**

### D0 · 先理解两个前提（否则测出来的数没意义）

**前提一：Docker 的内存是"整机配额"，不是"按容器分配"。**
`.wslconfig` 里的 `memory=` 设的是**整个 WSL2 虚拟机**的天花板，所有容器共享这 8 GB。

**前提二：ES 和 Kibana 是"固定成本"，各占 1 GB 且不随设备数变化。**

这两点合起来导致一个后果：**不能简单地"把内存设成 1 GB 然后测"** —— 光 ES+Kibana 就要 2 GB，1 GB 档连中间件都起不来。

所以本实验分**两种口径**，两个都要做，结论才完整：

| 口径 | 做法 | 回答什么问题 |
| :--- | :--- | :--- |
| **口径 A：全栈** | Kibana 保留，ES 限额随档位等比下调 | 实际部署时"给这台机器多少内存能扛多少台" |
| **口径 B：精简** | **停掉 Kibana**（与容量无关，纯可视化），释放 1 GB | 排除了可视化组件后的纯数据链路容量 |

### D1 · 最小可运行内存（下界探索）

**原理**：8 个容器的固定内存需求是可估的：ES 1 + Kibana 1 + Kafka ≥1 + Mongo 0.5 + HDFS 两个 ≈1 + 后端 0.4 + Nginx ≈ 5.7 GB（实测）。把 VM 内存调到这个值以下，一定会有容器起不来。

### D2 · 内存梯度 × 设备上限（核心曲线）

**目的**：**画出"VM 内存 → 能扛的设备数"曲线**，算出**边际容量（台/GB）**。

## 六、E 组 · 瓶颈对照实验（最有说服力，40 分钟）

### E1 · 分区数对照 ★ 全组最重要

**目的**：**直接证明"单分区是消费吞吐的硬上限"**，并量化优化收益。

**原理**：
- Kafka 的并行单位是**分区**，不是消费者。**一个分区同一时刻只能被同一个消费组里的一台消费者消费。**
- 当前 7 个业务 topic 分区数都是 1 → 消费并行度**物理上限 = 1**，无论怎么调 `concurrency` 都没用。
- 反过来，只加分区分、不加 `concurrency`，消费者数量还是 1 → 提升也有限。
- **两者必须同时加**，才能真正提升。

**操作**（这是一个"改前 / 改后"对照，要做两次 B1）：

```powershell
# ---------- 第 ① 步：先测改造前基线 ----------
# 直接用 B1 的结论填在这里：单 topic 上限 = ______ msg/s

# ---------- 第 ② 步：把 topic 分区数从 1 改成 3 ----------
docker exec kafka /opt/kafka/bin/kafka-topics.sh --bootstrap-server localhost:9092 `
  --alter --topic topic_device_sensor --partitions 3

# 确认改成功
docker exec kafka /opt/kafka/bin/kafka-topics.sh --bootstrap-server localhost:9092 `
  --describe --topic topic_device_sensor
```

```powershell
# ---------- 第 ③ 步：只加分区分，不动 concurrency，重跑 B1 ----------
# 记录吞吐 → 预计提升有限（消费者还是 1 个）
```

```powershell
# ---------- 第 ④ 步：再加上并发，重跑 B1 ----------
# 编辑 backend\platform-service\src\main\resources\application.properties，加一行：
#     spring.kafka.listener.concurrency=3
# 然后重建后端容器：
cd "D:\school\all\项目\企业项目实践\deploy"
docker compose up -d --build --force-recreate platform-service
Start-Sleep -Seconds 40
# 确认现在有 3 个消费者实例
docker exec kafka /opt/kafka/bin/kafka-consumer-groups.sh --bootstrap-server localhost:9092 --describe --group platform-service-group
```

**预期与怎么读**：

| 配置 | 消费并行度 | 预期吞吐 | 说明 |
| :--- | ---: | :--- | :--- |
| 1 分区 + concurrency=1 | 1 | 基准 | 改造前 |
| **3 分区 + concurrency=1** | **1** | **几乎不变** | ← **反直觉，但这就是重点**：分区多了，消费者没多 |
| **3 分区 + concurrency=3** | **3** | **明显提升** | 两者必须同时加 |
| 1 分区 + concurrency=3 | **1** | **零提升** | ← **直接证明分区数才是硬上限** |

> **做不做第 4 行（1 分区 + concurrency=3）你自己决定** —— 它能给出最干净的证明，但需要改回分区数（分区只能加不能减，得删 topic 重建）。
>
> **删 topic 重建的方法**（谨慎，会丢该 topic 的消息）：
> ```powershell
> docker exec kafka /opt/kafka/bin/kafka-topics.sh --bootstrap-server localhost:9092 --delete --topic topic_device_sensor
> docker exec kafka /opt/kafka/bin/kafka-topics.sh --bootstrap-server localhost:9092 --create --topic topic_device_sensor --partitions 1 --replication-factor 1
> ```

### E3 · 索引对照

**目的**：量化"缺索引"的代价。已定位的缺口：`alarm` 集合**没有 `eventTime` 单字段索引**，`level` / `deviceNo` 也没索引。

**原理**：没有合适索引时，MongoDB 要么全集合扫描（COLLSCAN），要么把结果全取出来在内存里排序（SORT 阶段）。数据量一大就会撑爆内存或超时。

**操作**：
```powershell

" | findstr /C:"totalDocsExamined" /C:"executionTimeMillis" /C:"stage"
```

```powershell
# ---------- 加索引 ----------
docker exec mongodb mongosh --quiet uav_platform --eval "
db.alarm.createIndex({eventTime:-1}, {name:'idx_eventTime'});
db.alarm.createIndex({handleStatus:1, eventTime:-1}, {name:'idx_status_time'});
db.alarm.createIndex({deviceNo:1, eventTime:-1}, {name:'idx_device_time'});
db.alarm.createIndex({level:1}, {name:'idx_level'});
printjson(db.alarm.getIndexes());
"
```

```powershell
# ---------- 加索引后再看一次执行计划，对比 ----------
# 命令同"加索引前"
```

| :--- | :--- |

| `stage: IXSCAN` | 用上了索引 ✅ |

### E4 · 深分页对照

**目的**：量化 `skip/limit` 的代价。

**原理**：`queryAlarms` 用的是 `skip((page-1)*size).limit(size)`。MongoDB 执行 `skip` 时必须**先扫描并丢弃前面所有文档** —— 翻到第 500 页时，前面 5000 条全被白扫一遍。而且每页还要额外做一次 `count()`，共 **2 次往返**。

**操作**：
```powershell
# 先登录拿 token
$token = (curl.exe -s -X POST http://localhost/api/auth/login `
  -H "Content-Type: application/json" `
  -d '{\"username\":\"admin\",\"password\":\"admin123\"}' | ConvertFrom-Json).token

# 对比不同页码的耗时
foreach ($p in 1, 10, 50, 100, 500) {
  $t = Measure-Command {
    curl.exe -s -o $null "http://localhost/api/alarms?page=$p&size=10" -H "Authorization: Bearer $token"
  }
  "page=$p  ->  $([math]::Round($t.TotalMilliseconds,1)) ms"
}
```

**怎么读**：理想情况下各页耗时应该接近（B-Tree 索引直接定位）。若**耗时随页码线性增长**，就证实了深分页问题。

**记录**：

| page | 1 | 10 | 50 | 100 | 500 |
| :--- | ---: | ---: | ---: | ---: | ---: |
| 耗时 ms | | | | | |

> **优化方向**（答辩可讲）：把 `skip/limit` 换成**游标分页**（用上一页最后一条的 `eventTime` 作为查询起点），复杂度从 O(page) 降到 O(1)。

## 七、F 组 · 积压与故障恢复（选做）

### F1 · 积压与追赶

**目的**：测**消息积压后恢复的追赶速率** —— 这是评估"系统宕机后多久能追上"的关键指标。

**原理**：Kafka 会把消息持久化在磁盘上，消费者停掉期间消息不会丢，只是 offset 落后。重启后消费者会从上次 offset 继续，以**最大能力**追赶。追赶速率 ≈ 该 topic 的消费上限。

**操作**：
```powershell

  --producer-props bootstrap.servers=localhost:9092

# ③ 看积压了多少
docker exec kafka /opt/kafka/bin/kafka-consumer-groups.sh --bootstrap-server localhost:9092 --describe --group platform-service-group

# ④ 重启后端，立刻开始计时，每 10 秒看一次 LAG

}
```

**怎么读**：LAG 从峰值降到 0 的耗时 → 追赶速率 = 积压条数 ÷ 追赶耗时。

### F2 · 强杀恢复

**目的**：验证容器**非优雅停止**后能否自愈、数据是否丢失。

**原理**：`docker kill` 发 SIGKILL，进程没有机会刷盘/提交 offset。但没有提交的 offset 意味着**重启后会重复消费** —— 这时就考验**幂等设计**（MongoDB 的 `_id`、`processedMsgIds`）。

**操作**：
```powershell
# ① 记录当前各集合文档数
docker exec mongodb mongosh --quiet uav_platform --eval "print('telemetry='+db.telemetry.countDocuments()+' sensor='+db.sensor_data.countDocuments()+' alarm='+db.alarm.countDocuments())"

# ② 强杀容器（不是 stop，是 kill）
docker kill kafka
docker kill mongodb

# ③ 重新拉起
docker compose up -d kafka mongodb
Start-Sleep -Seconds 60

# ④ 再记一次文档数，并看 LAG
docker exec mongodb mongosh --quiet uav_platform --eval "print('telemetry='+db.telemetry.countDocuments()+' sensor='+db.sensor_data.countDocuments()+' alarm='+db.alarm.countDocuments())"
docker exec kafka /opt/kafka/bin/kafka-consumer-groups.sh --bootstrap-server localhost:9092 --describe --group platform-service-group
```

**怎么读**：

| 现象 | 含义 |
| :--- | :--- |
| Kafka 起来后 LAG 能重新归零 | 消费自愈 ✅ |
| MongoDB 文档数不减少 | 数据没丢 ✅ |
| 重新消费时文档数**暴增** | **幂等失效**，同一条消息被写了多次 ⚠ |
| 容器反复重启不健康 | 数据卷损坏，需要重置 |

### F3 · 幂等验证

**目的**：验证重复投递同一条消息**不会产生重复数据**。

**原理**：契约里要求幂等。设备侧用 `processedMsgIds` 去重，平台侧心跳用 `_id` 覆盖、指令用 `msgId` 去重。

**操作**：
```powershell
# 手动把同一条消息投两次
echo '{"msgId":"SEN-DUP-TEST","deviceNo":"DOG-001","temperature":25.0,"humidity":50.0,"gasValue":1.0,"deviceTemp":40.0,"eventTime":1789551000001}' > dup.txt
docker cp dup.txt kafka:/tmp/dup.txt

for ($i=1; $i -le 2; $i++) {
  docker exec kafka sh -c "cat /tmp/dup.txt | /opt/kafka/bin/kafka-console-producer.sh --bootstrap-server localhost:9092 --topic topic_device_sensor"
  Start-Sleep -Seconds 3
}

# 看写了几条
docker exec mongodb mongosh --quiet uav_platform --eval "print('重复消息写入条数 = ' + db.sensor_data.countDocuments({'deviceNo':'DOG-001','temperature':25.0,'humidity':50.0}))"
```

**怎么读**：预期**写入 2 条**（传感器数据是追加型、天然允许重复）。若换成**心跳**或**指令**投两次，则预期只生效 1 次（有幂等保护）。

> 这个对比本身就是结论：**幂等不是全局要求，而是"按数据类型区分"的** —— 遥测类追加数据允许重复（重复无害），控制指令必须幂等（重复有害）。

## 八、G 组 · 读路径压测（选做）

### G1 · HTTP 并发压测

**目的**：测接口在高并发下的延迟与错误率，验证"同步阻塞 I/O 会拖垮线程池"。

**原理**：`/api/alarms`、`/api/stats/*` 内部都是**同步阻塞**调用（Mongo 查询 / ES 聚合），Tomcat 默认 200 个线程。请求一多，线程全部耗在等待下游返回上。

**操作**：
```powershell
$token = (curl.exe -s -X POST http://localhost/api/auth/login -H "Content-Type: application/json" -d '{\"username\":\"admin\",\"password\":\"admin123\"}' | ConvertFrom-Json).token

# 20 并发 × 100 次请求
$url = "http://localhost/api/alarms?page=1&size=20"
$results = 1..100 | ForEach-Object -Parallel {
  $t = Measure-Command {
    curl.exe -s -o $null -w "%{http_code}" $using:url -H "Authorization: Bearer $($using:token)"
  }
  $t.TotalMilliseconds
} -ThrottleLimit 20

$sorted = $results | Sort-Object
"p50 = $([math]::Round($sorted[49],1)) ms"
"p95 = $([math]::Round($sorted[94],1)) ms"
"max = $([math]::Round($sorted[99],1)) ms"
```

> `ForEach-Object -Parallel` 需要 PowerShell 7+。若你是 Windows PowerShell 5.1，改用多个窗口同时跑循环，或用 k6 等工具。

**记录**：

| 并发 | p50 | p95 | max | 错误率 |
| ---: | ---: | ---: | ---: | ---: |
| 1 | | | | |
| 10 | | | | |
| 20 | | | | |

### G2 · 定时器争抢验证

**目的**：验证"4 个 `@Scheduled` 共用 1 个线程"的实际影响。

**原理**：`TelemetryService` / `SensorService` / `TaskLogService` 各有一个 `@Scheduled(fixedRate=2000)` 刷盘，`DeviceService` 有一个 5 秒的离线检测 —— **共 4 个定时任务**。Spring 默认的 `TaskScheduler` **只有 1 个线程**，它们必须排队。更糟的是 `flush()` 持锁做 Mongo 往返，一个卡住其余全部推迟。

**操作**：
```powershell
# 在后端日志里数「批量写入」的实际间隔
docker compose logs --tail=200 platform-service | Select-String "批量写入"

# 然后编辑 application.properties 加：
#     spring.task.scheduling.pool.size=4
# 重建容器后同样再数一次，对比间隔是否更均匀
cd deploy
docker compose up -d --build --force-recreate platform-service
```

**怎么读**：若日志里刷盘间隔明显大于 2 秒且忽长忽短 → 调度器在排队。调到 4 线程后间隔应更接近 2 秒。

### 9.2 踩坑速查

| 现象 | 原因 | 解决 |
| :--- | :--- | :--- |
| `exec: "C:/Program Files/Git/opt/..."` | Git Bash 改写了容器内路径 | `export MSYS_NO_PATHCONV=1` |
| `measure-rate.ps1` 报 0 | 仿真端没在跑 | 启动仿真端 |
| 改了 `.wslconfig` 内存没生效 | WSL 没重启 | `wsl --shutdown` + 重启 Docker Desktop |
| 分区数改不动（只能加） | Kafka 分区不可减 | 删 topic 重建 |
| 灌数据报 `records/sec` 远低于设定 | 生产者侧到顶 | 降档位，或调 `linger.ms` / 压缩 |
| 加了索引但执行计划还是 COLLSCAN | 索引没建成功 | `db.alarm.getIndexes()` 确认 |
| 仿真端进程秒退 | 共享池内无任务 | 检查设备数是否为 0 |

### 9.3 实验纪律

1. **一次只改一个变量** —— 否则测出的差异无法归因。
2. **每档先稳定 60 秒再开始采集** —— 避免把爬升过程当成稳态。
3. **加压前就启动采集** —— 否则漏掉峰值。
4. **每档记录完再进下一档** —— 数据不落盘等于没做。
5. **改配置前先备份** —— 尤其 `docker-compose.yml` 和 `.wslconfig`。
