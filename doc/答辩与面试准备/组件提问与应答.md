## 一、先看清提问的六种套路

无论答辩还是面试，关于某个组件的问题**几乎都落在这六类里**。认清类型，就知道该往哪个方向答。

| # | 类型 | 典型问法 | 考察什么 | 应答结构 |
| :-: | :--- | :--- | :--- | :--- |
| 1 | **选型类** | "为什么用 X 不用 Y？" | 有没有做过技术对比 | 备选方案 → 对比维度 → 选定理由 → **代价** |
| 2 | **原理类** | "X 是怎么做到的？" | 是否理解底层机制 | 机制 → **为什么这样设计** |
| 3 | **应用类** | "在你的项目里具体怎么用的？" | 是不是真做过 | 具体配置 / 代码 / 数据 |
| 4 | **踩坑类** | "用 X 遇到过什么问题？" | 真实动手能力 | **现象 → 排查 → 根因 → 解决** |
| 5 | **深度类** | "X 挂了怎么办？""怎么优化？" | 有没有系统性思考 | 影响面 → 降级方案 → 优化路径 |
| 6 | **对比类** | "你这和真实生产环境差在哪？" | 有没有清醒的自我认知 | **如实承认 + 说明为什么 + 怎么演进** |

> **关键认知**：第 4 类（踩坑）和第 5 类（深度）是**最能拉开差距**的。选型类和原理类可以靠背书，但踩坑和优化必须真做过才答得出来。
>
> **本项目的优势**：踩坑记录非常扎实（9 个真实问题 + 性能压测发现），这是最大的加分项。

## 二、逐组件高频问题与应答

### 2.1 HDFS

#### 【选型类】为什么用 HDFS 存图片，不直接存数据库或本地文件系统？

**应答要点**：

| 方案 | 问题 |
| :--- | :--- |
| 存数据库 BLOB | 撑爆数据库；备份恢复极慢；数据库的事务/查询能力对二进制数据毫无价值 |
| 存本地文件系统 | 容量有上限；无冗余，磁盘坏了数据就没了；多实例部署时无法共享 |
| **HDFS** | 容量可线性扩展；多副本容错；为"大文件、一次写入多次读取"深度优化 |

**加分补充**：HDFS 的定位与本项目的影像特征是匹配的——**单文件较大、写入后不再修改、读取频次低于产生速度**。反过来，如果是海量小文件，HDFS 就不合适了（见下一个问题）。

#### 【原理类】上传一张图片到 HDFS，背后发生了什么？

**应答要点**（这是最能体现理解深度的一题）：

```text
① 客户端 → NameNode： 请求创建文件（op=CREATE）
② NameNode → 客户端： 307 Temporary Redirect
                      Location: http://datanode:9864/...
③ 客户端 → DataNode： PUT <Location>，携带真实文件字节
④ DataNode → 客户端： 201 Created
```

**关键点必须讲出来**：

> **307 不是异常，是 HDFS 架构的必然结果。** NameNode 只存元数据（文件在哪、由哪些块组成），DataNode 才存数据。让客户端直连 DataNode 是为了**避免 NameNode 成为瓶颈和单点**——数据量比元数据大好几个数量级，若都经 NameNode 转发，它立刻会被压垮。

**主动补充易失分点**：Java 的 `HttpClient` 默认 `followRedirects = NEVER`，不自动跟随重定向，必须手动读取 `Location` 头再发一次请求。

#### 【应用类】为什么按"设备 / 日期"分目录？

**应答要点**：HDFS 的 NameNode 把**整个目录树的元数据常驻内存**。若所有文件堆在一个目录下，百万级条目会耗尽 NameNode 内存，且列目录极慢。按 `设备 / 日期` 两级分区后：单目录文件数可控、可按日期整目录清理、排查时从路径就能读出数据来源与时间。

#### 【陷阱题】HDFS 适合存小文件吗？你的项目有这个问题吗？

⚠️ **这是陷阱题**。诚实答案是"不适合，而且我的项目**确实有这个隐患**"——仿真端每次产生影像都写一个新文件，实测已积累数千个 1-2 KB 的小文件。

**应对方式**（承认 + 展示理解）：

> "HDFS 不适合小文件，因为 NameNode 的元数据是按**文件数**而非数据量增长的——1000 万个 1KB 文件会让元数据占用达到数 GB，比数据本身还大。
>
> 我的项目确实有这个隐患：仿真端每个影像生成一个独立文件，目前积累了数千个。不过影像本身在真实场景中应该是 MB 级，所以问题不突出。如果要优化，通用做法是**文件合并**（HAR 归档或 SequenceFile），或者如果场景确实是小文件为主，应该改用对象存储。"

#### 【深度类】HDFS 挂了会影响什么？

**应答要点**：影响面是**局部的**——只有影像上传和读取不可用，设备数据上报、告警、任务下发都不受影响。

**为什么会这样**（这个解释很加分）：因为影像元数据先写 MongoDB（`uploaded=false`），文件上传是第二步，失败时元数据仍在，标记为待重传。

**但必须承认**：目前**没有实现自动重传任务**，`uploaded=false` 的记录会一直留着。这是一个明确的优化点。

### 2.2 Nginx

#### 【选型类】为什么需要 Nginx？后端直接对外不行吗？

**应答要点**（从"不用会怎样"切入最有力）：

| 不用 Nginx 的问题 | Nginx 的解决 |
| :--- | :--- |
| 后端端口、实例数暴露 | 客户端只看到 80 端口，拓扑被隐藏 |
| 静态文件由应用服务器处理，效率低 | Nginx 零拷贝直接返回 |
| 限流、安全策略要在每个服务里各写一遍 | 网关一处配置，全局生效 |
| 后端扩容要通知客户端改地址 | 客户端地址不变，扩容透明 |
| **前后端跨域** | **同源，完全不需要处理 CORS** |

**最后一条最实际**：前端和 API 都经 80 端口，属于同源请求。**很多人在前后端分离项目上卡在跨域，其实反向代理从架构层面就消除了这个问题。**

#### 【原理类】反向代理和正向代理的区别？

**应答要点**：

| | 正向代理 | 反向代理 |
| :--- | :--- | :--- |
| 代理谁 | **客户端** | **服务端** |
| 客户端知情吗 | 需要显式配置代理地址 | **不知情**，以为直接访问了服务器 |
| 典型场景 | 科学上网、爬虫 | 负载均衡、统一入口 |

#### 【原理类】Nginx 为什么能抗高并发？

**应答要点**（核心是"不等待"三个字）：

> Nginx 用**事件驱动 + 异步非阻塞**模型。传统模型是"一个连接一个线程"，线程大部分时间在**阻塞等待** I/O；而 Nginx 发起一个操作后**立即返回事件循环**去处理其他连接，等操作完成再被唤醒。
>
> 配合 Linux 的 `epoll`（O(1) 复杂度找出就绪连接），少量 Worker 进程就能支撑数万并发连接。

**用实测数据佐证**：本项目 Nginx 容器内存占用仅 **27 MiB**，是 8 个容器中最低的。

#### 【踩坑类】前端页面刷新返回 404 是怎么回事？

**应答要点**（现象 → 根因 → 解决）：

> **现象**：页面内切换标签正常，但直接在地址栏访问子路径或刷新时返回 404。
>
> **根因**：前端是单页应用（SPA），路由由 JavaScript 处理。服务器上只有 `index.html`，并不存在 `/tasks` 这个文件，Nginx 找不到就返回 404。
>
> **解决**：配置 `try_files $uri $uri/ /index.html` —— 先找实际文件，找不到就返回首页，由前端接管路由。

**加分补充**：这个问题**开发环境不会暴露**（Vite dev server 自带回退），**页面内导航也不暴露**（不触发真实请求）。只有直接访问或刷新时才出现——**开发服务器替我们做的默认行为，生产环境需要显式补上**。

#### 【陷阱题】负载均衡怎么配的？演示过吗？

⚠️ **这是陷阱题**。诚实答案：`upstream` 配置好了，但**只有一个后端实例，轮询策略从未被触发**。

**应对方式**：

> "`upstream` 块已经配置好了，扩展多实例只需追加一行 `server` 条目。
>
> 但**当前只有一个后端实例，所以负载均衡的效果实际上没有被验证过**——这是我明确记录的一个待验证项。
>
> 验证方法很简单：`docker compose up -d --scale platform-service=2` 起第二个实例，然后看 Nginx 访问日志中请求是否分发到不同后端。"

**为什么这样答更好**：主动指出"配置完成 ≠ 功能验证"，反而体现了工程严谨性。

#### 【深度类】限流做了吗？

**诚实回答 + 给出方案**：

> "没有做，这是一个缺口。不过配置很简单——加一个 `limit_req_zone` 定义限流区，然后在 `location /api/` 里加一行 `limit_req` 即可。
>
> 更值得说的是**为什么 Nginx 适合做限流**：因为它是所有请求的必经之路，在这里限流能**保护后端不被突发流量打垮**，而不需要每个服务各自实现。"

### 2.3 MongoDB

#### 【选型类】为什么选 MongoDB 不选 HBase？

**应答要点**（对比要有维度，不能只说"MongoDB 好用"）：

| 维度 | MongoDB | HBase |
| :--- | :--- | :--- |
| 数据模型 | 文档，字段灵活 | 宽表，需预先设计 |
| **查询能力** | 支持条件/范围/聚合 | 主键扫描为主 |
| 部署复杂度 | 单节点即可 | **依赖 HDFS + ZooKeeper** |
| 与本项目匹配度 | 按编号/时间查询直接映射 | 数据量未达海量级，优势难发挥 |

**加分补充**：MongoDB 的**时序集合**特性恰好解决了遥测数据的存储优化与自动过期，这是 HBase 不具备的便利。

#### 【原理类】时序集合是什么？为什么用它？

**应答要点**（讲清"分桶"这个机制）：

> 时序集合把**同一设备相邻时间的数据打包进同一个"桶"**，而不是每条记录独立存储。

```text
传统：文档1 + 索引、文档2 + 索引、文档3 + 索引……（大量文档与索引）
时序：一个桶 { meta: DOG-001, timeRange: 10:00~10:01, data: [...] }
```

**三个收益**：存储占用大幅降低（同源数据列式压缩效果极佳）、索引体积降低、按时间范围查询只需扫描相关桶。

**必须补一句判据**（体现独立思考）：

> **判据的核心是"数据会不会被更新"。** 时序集合面向只追加的数据；如果对时序集合执行频繁更新，既低效又违背设计初衷。

#### 【应用类】`task` 和 `task_log` 为什么要分成两个集合？

**应答要点**：

| 集合 | 性质 | 操作模式 | 存储类型 |
| :--- | :--- | :--- | :--- |
| `task` | 任务**当前状态** | 频繁更新（进度 0→50→100） | 普通集合 |
| `task_log` | 任务**执行流水** | 只追加 | 时序集合（7 天 TTL） |

**核心解释**：两者读写模式完全不同。若混在一张表里，就不得不在时序集合上做更新操作——既低效又违背其设计初衷。

**加分说法**：这是**读写模型分离（CQRS）** 思想的简化实践。

#### 【踩坑类】任务编号是怎么生成的？

**应答要点**（这个问题背后有个真实 Bug，讲出来非常加分）：

> 最初用 `"TASK-" + System.currentTimeMillis()`，只有毫秒精度。而**批量处置告警是循环调用单条逻辑**，一轮循环往往不到 1 毫秒，导致多个任务拿到**相同编号**。
>
> 连锁反应是：指令标识 `msgId` 由 taskId 派生 → 也重复 → **被设备侧的幂等保护判定为"重复投递"而静默丢弃**。结果是勾选 3 条告警指派复核，设备只执行 1 条，而前端还提示"已指派 3 条"。
>
> 改为**数据库原子计数器**（`findAndModify` + `$inc`）后解决——跨进程、跨重启都唯一。

**为什么不用内存 `AtomicInteger`**：JVM 重启后会从 1 重新开始，与当天已有编号碰撞。

**这个案例的升华**（如果面试官继续追问）：

> **幂等设计本身是正确的，但它隐含了"标识必须唯一"这个前提。当标识生成出错时，幂等保护会从"防重复"退化为"静默丢数据"，且不产生任何错误日志。** 这提醒我们设计幂等机制时，必须同时保证标识生成的正确性。

#### 【深度类】数据量大了怎么办？

**分层次回答**：

| 层次 | 措施 |
| :--- | :--- |
| 已有 | 时序集合 + TTL 自动过期、索引优化、服务端分页 |
| 短期 | 深分页改**游标分页**（复杂度 O(页码) → O(1)）；补索引；`findAll()` 改条件查询 |
| 中期 | 部署**副本集**（高可用 + 读写分离） |
| 长期 | 引入**分片**（水平扩展） |

### 2.4 Kafka

#### 【选型类】为什么用 Kafka 不用 RocketMQ？

**应答要点**（要能说出 RocketMQ 的优势，否则显得没做过对比）：

| 维度 | Kafka | RocketMQ |
| :--- | :--- | :--- |
| 吞吐量 | **极高** | 高 |
| 延迟/事务消息 | 弱 | **强** |
| 消息轨迹 | 无 | **有** |
| 生态 | Apache，与 Hadoop/ES 协作资料多 | 阿里系，中文文档友好 |

**选定理由**：① 设备心跳与巡检数据是典型**高吞吐流式**场景，契合 Kafka 设计目标；② 分区内有序 + 持久化满足"上报不丢、指令按序"；③ 与 HDFS、ES 同属 Apache 大数据生态；④ KRaft 模式免去 ZooKeeper 依赖。

**主动补充**：如果业务需要**延迟消息、事务消息、消息轨迹**，RocketMQ 会更合适——**Kafka 在这些方面是弱项**。

#### 【原理类】怎么保证同一设备的消息有序？

**应答要点**：

> Kafka **只保证分区内有序，不保证分区之间有序**。所以用 `deviceNo` 作为**分区键**——相同 Key 的消息经哈希后必然进入同一分区，从而保证同源有序。

**代码佐证**：

```java
kafkaTemplate.send(topic, deviceNo, json);   // 第二个参数就是分区键
```

**为什么需要有序**：设备的"位置→传感→告警"存在因果顺序，若乱序可能出现"告警先于触发它的传感读数"这类逻辑异常。

#### 【陷阱题】★ 你的 topic 有几个分区？

⚠️ **这是本项目的核心陷阱题，也是最容易失分的一题。**

如果答"1 个"就结束了，等于浪费了一个展示深度的机会。**正确的答法是把它变成加分项**：

> "目前所有业务 topic 都是 **1 个分区**。这个发现来自我们做的容量压测——我原本以为加后端实例就能提升吞吐，检查配置时才发现问题所在。
>
> **Kafka 的并行单位是分区，不是消费者。** 一个分区同一时刻只能被同一消费者组内的一个消费者消费，所以：
>
> ```text
> 消费并行度上限 = 分区数 = 1
> ```
>
> 这带来三个推论：① 每个主题只有 1 个消费线程真正工作；② **单个 topic 的消费能力上不去**——即使起了第 2 个后端实例也没用；③ 这是系统的**硬天花板，加 CPU 加内存都没用**。
>
> **⚠ 一个必须说准的细节**（说错了容易被追问倒）：
> 加实例**并非完全无效**——6 个 topic 会被分配到不同实例上，**进程级负载确实被分担了**（CPU/内存/GC 压力减半），也提供了故障隔离。
> 真正的硬约束是：**单个 topic 的吞吐上不去**。
>
> | 场景 | 加实例是否有效 |
> | :--- | :--- |
> | 单进程 CPU/内存吃紧 | ✅ 有效 |
> | **某个 topic 处理不过来** | ❌ **无效** |
>
> 需要说明的是，**这不是单纯的配置疏忽，而是一个权衡**：系统要保证同设备消息有序，这依赖于以 `deviceNo` 作分区键。若随意加大分区数而不调整键策略，会带来数据倾斜。
>
> 优化方向是用 **`deviceNo + 时间窗` 复合键**，把同一设备不同时间窗的消息分散到多个分区，同时提高消费并发度。**代价是牺牲"同设备全序"，换取分区均衡**——这是一个明确的取舍，不是免费的性能提升。"

**为什么这样答很强**：它展示了 ① 你做过压测 ② 你理解分区语义 ③ 你知道优化方案 ④ 你明白优化的代价。

#### 【深度类】消息会丢吗？会重复吗？

**应答要点**（要分层回答，不要一句"不会"）：

| 数据 | 可靠性要求 | 措施 |
| :--- | :--- | :--- |
| 告警、任务回执 | **高** | `acks=all`；消费端幂等 |
| 心跳、传感 | 中 | 允许偶发丢失，后续数据可补偿 |
| 位置轨迹 | 低 | 高频上报，单条丢失无影响 |

**重复问题的处理**：

- 设备侧：`msgId` 幂等去重，`processedMsgIds` 集合
- 存储侧：Elasticsearch 用 `_id = alarmId` 让重复写入变覆盖；MongoDB 时序集合允许重复（追加型数据，重复无害）

**加分观点**：

> **幂等不是全局要求，而是按数据类型区分的**——遥测类追加数据允许重复（重复无害），控制指令必须幂等（重复有害）。

#### 【深度类】Kafka 挂了会怎样？

**应答要点**：影响面是**全局的**——整个数据链路中断（设备上报进不来、指令下发不出去）。

**但要说清楚现状与改进**：

> "当前是**单 Broker、副本数 1**，所以 Kafka 故障会导致服务中断，**不具备高可用能力**。
>
> 生产环境需要部署 3+ Broker 并把副本数设为 3。这是我明确记录的一条不足。"

### 2.5 Elasticsearch

#### 【选型类】既然有 MongoDB，为什么还要引入 ES？

**应答要点**（必须讲出"分工"，否则显得是重复建设）：

| 需求 | 由谁承担 | 为什么 |
| :--- | :--- | :--- |
| 告警列表多条件筛选 | **MongoDB** | 要读完整明细、要能更新处置状态 |
| 处置状态更新 | **MongoDB** | ES 的"更新"是删除+新增，不适合 |
| 按类型/级别分组统计 | **Elasticsearch** | `terms` 聚合是原生能力 |
| 按时间分桶统计 | **Elasticsearch** | `date_histogram` 原生支持 |

**核心解释**：

> ES 的聚合基于 **`doc_values` 列式存储**——聚合时只需读取目标列，不必加载完整文档。而 MongoDB 做同样的事要写聚合管道，且**有 100 MB 的内存限制**，超出需显式开启 `allowDiskUse`。
>
> **同一需求在不同存储上的实现代价可能相差一个数量级**——这不是重复造轮子，而是让每个组件做它最擅长的事。

#### 【原理类】ES 为什么快？

**应答要点**（核心是**两套互补的数据结构**，讲清这个才算真懂）：

| 机制 | 解决什么 | 用在哪 |
| :--- | :--- | :--- |
| **倒排索引** | "**根据内容找文档**" | 全文检索 |
| **doc_values（列式）** | "**根据文档统计字段**" | **聚合分析** |

> 正排是"文档→词项"，倒排是"词项→文档列表"。查询"包含'航拍'的文档"时，直接在倒排表定位 `航拍` 就能得到文档列表，**无需遍历任何文档**。
>
> 而聚合需要的恰恰相反——"根据文档统计字段值"，这是**正排**需求，由 `doc_values` 列式存储满足。

#### 【应用类】索引为什么按天滚动？

**应答要点**：① 单索引体积可控，不会随时间膨胀导致性能衰减；② 便于按时间范围清理归档（删一个索引即可）；③ 便于按时间范围查询（查最近 3 天只需命中 3 个索引）。

#### 【原理类】为什么用 `bool.filter` 而不是 `must`？

| | `must` | `filter` |
| :--- | :--- | :--- |
| 计算相关性得分 | 是 | **否** |
| **结果可否缓存** | 否 | **可以** |

> 我的查询条件是"类型 = ENV"这类**精确匹配**，不需要相关度排序，所以用 `filter` 更合适——**跳过分词与评分计算，且结果能被 bitset 缓存**。

#### 【陷阱题】地理检索实现了吗？

⚠️ **陷阱题**。诚实答案：**没实现，而且底层也没准备好**。

**应对方式**（这个答法反而加分）：

> "没有实现。而且不止是没写代码——我在检查时发现一个更底层的问题：**代码注释里说经纬度应该是 `geo_point` 类型，但实际上没有定义索引模板**，ES 的动态映射把它建成了普通嵌套对象。
>
> **根源在于动态映射只能"从数据形式猜语义"**——它看到一个 `{lat, lng}` 对象，无法判断这是地理坐标还是普通对象。而地理坐标的语义**无法从结构推断**，必须显式声明。
>
> 要修复需要两步：① 定义 index template 声明 `geo_point` 类型；② 重建索引（已存在的索引无法直接改字段类型）。"

**为什么这样答很强**：展示了 ① 对自己代码的细节掌握 ② 理解动态映射的边界 ③ 知道修复方案。

#### 【陷阱题】全文检索做了吗？

**诚实回答 + 说明取舍**：

> "没有做，当前是**基于 `term` 的过滤型检索**，没有分词与 `match` 查询。
>
> 这是有意的取舍：告警检索的典型需求是"按类型、级别、时间精确筛选"，而不是"在描述文本里搜索关键词"。**过滤型检索用 `filter` 比全文检索更快**，因为没有相关度计算且结果可缓存。
>
> 如果后续需要支持'搜索告警描述中的关键词'，再为 `description` 字段配置分词器并使用 `match` 查询即可。"

### 2.6 Docker

#### 【选型类】为什么要用 Docker？

**应答要点**（用"不用会怎样"切入）：

| 问题 | Docker 的解决 |
| :--- | :--- |
| 六类中间件依赖复杂、版本敏感 | **镜像隔离**，从根本上避免冲突 |
| 本地安装每个组件数小时 | **一条命令启动 8 个容器** |
| 环境无法复现 | **一份 YAML 文件**，完全一致 |
| 重置要手工清理注册表/服务/文件 | **`down -v` 一条命令** |

**引用课程建议**：指导说明书也明确建议"统一使用 Docker 镜像规避版本冲突"。

#### 【原理类】容器和虚拟机的区别？容器是怎么隔离的？

**应答要点**（隔离机制是核心）：

| | 虚拟机 | 容器 |
| :--- | :--- | :--- |
| 隔离级别 | 硬件级（Hypervisor） | **进程级** |
| 操作系统 | 每个虚拟机一套完整内核 | **共享宿主内核** |
| 启动时间 | 分钟级 | **秒级** |

**三大内核机制**（能说出这三个才算真懂）：

| 机制 | 作用 | 一句话 |
| :--- | :--- | :--- |
| **Namespace** | 视图隔离 | 让容器"**看不见**"外面的进程与网络 |
| **Cgroup** | 资源限制 | 让容器"**用不了那么多**"内存与 CPU |
| **UnionFS** | 分层复用 | 让镜像能"**一层层叠加**"并共享 |

**举例说明**：8 个容器各自有独立的网络命名空间，所以 kafka 的 9092 和 mongodb 的 27017 互不冲突。

#### 【陷阱题】★ 容器资源限制怎么配的？

⚠️ **陷阱题**。诚实答案：**只有 ES 和 Kibana 设了，其余 6 个没设。**

**应对方式**：

> "只有 Elasticsearch 和 Kibana 设置了内存上限（各 1 GiB），**其余 6 个容器没有设**。
>
> 这在压测时暴露了一个问题：ES 容器内存占用率达到 **99.6%**，Kibana 也到了 90%。核心原因是**中间件在裸机环境下都基于'独占整台机器'的假设自动配置资源池**——MongoDB 的 WiredTiger 缓存默认是可用内存的一半，ES 的 JVM 堆默认是 1/4。放进 8 GB 共享配额的容器环境后，这些默认值会相互冲突。
>
> 8 个容器空载已经占了 **5.7 GiB（71%）**，余量很小。补齐内存限制是一项低成本的改进。
>
> 另外要注意一个坑：**只设 `mem_limit` 而不设 JVM 的 `-Xmx` 是不够的**——JVM 会按容器可用内存自动推断堆大小，但堆之外还有元空间、线程栈、直接内存等开销。合理做法是容器内存约为堆上限的 1.5~2 倍。"

#### 【踩坑类】用 Docker 遇到过什么问题？

**应答要点**（挑 1-2 个讲透，不要罗列）：

**推荐讲"改了代码不生效"**：

> "改完代码执行 `docker compose up -d --build`，构建日志显示成功，但容器内的应用行为还是旧的。
>
> 排查发现：**`--build` 只重建镜像，不重建容器**。Compose 发现容器配置没变，就复用了现有容器，所以跑的仍是旧镜像。`docker ps` 里看到容器状态是 `Up 3 hours` 而不是刚重启，就是这个问题的信号。
>
> 解决是加 `--force-recreate` 强制重建容器。
>
> 这个问题教会我一件事：**Docker 中'改什么用什么命令生效'是分类的**——"
>
> | 改动类型 | 生效方式 |
> | :--- | :--- |
> | 后端代码（打进镜像） | `--build --force-recreate` |
> | Nginx 配置（挂载） | `nginx -s reload` |
> | 前端产物（挂载） | 重新构建前端 |
> | `docker-compose.yml` | `docker compose up -d` |

**也可以讲 DNS 污染**（如果面试官想听网络问题）：

> "所有镜像都拉不下来，报错是连接 `127.0.0.1:443` 被拒。但我在宿主机浏览器里访问同一个域名是正常的。
>
> 后来发现是 **DNS 污染**——`registry-1.docker.io` 在容器内被解析到了本地回环地址。**'宿主机能通、容器不通'是容器网络问题的典型症状**，因为容器有自己的网络命名空间和 DNS 解析路径。
>
> 解决是配置公共 DNS（223.5.5.5）+ 镜像加速器。"

#### 【深度类】为什么不用 Kubernetes？

**应答要点**：

> "本项目是**单机 8 容器**，用 Docker Compose 完全够用。K8s 解决的是**跨主机调度、自愈、滚动更新、服务发现**这些问题——在单机场景下引入 K8s 属于过度设计。
>
> 不过 Compose 和 K8s 的概念是**一脉相承**的：服务定义 → Deployment、环境变量 → ConfigMap、数据卷 → PersistentVolume、服务名 DNS → Service。在本项目建立的认知可以平滑迁移。"

## 三、跨组件的综合题（真正的送命题）

这类问题**不针对单个组件**，考察的是整体架构理解。答好了能一次性证明所有组件的掌握程度。

### 3.1 ★★★ "你的项目瓶颈在哪？"

**这是最可能被问、也最能拉开差距的一题。**

**三段式应答**：

**① 先给结论**：

> "瓶颈在 **Kafka 的分区数**，不在计算资源上。"

**② 给证据**：

> "我们做了容量压测，建立三个观测口径：资源占用（`docker stats`）、消息速率（主题偏移量差分）、以及**消费积压 LAG**。
>
> 关键判据是 **LAG 而不是 CPU**——消息进 Kafka 的速度超过消费速度时 LAG 会持续增长，这比看 CPU 更能反映'真的处理不过来'。
>
> 实测发现所有业务主题**只有 1 个分区**。而 Kafka 的并行单位是分区，所以：
>
> ```text
> 消费并行度上限 = 分区数 = 1
> ```

**③ 给影响与方案**：

> "这意味着**单个 topic 的消费能力上不去**——加实例只能把不同 topic 分散到不同进程（进程级负载分担），但那个 topic 仍然只有一个消费者。加 CPU 内存也突破不了，因为瓶颈是架构约束而非资源约束。
>
> 优化方向是用 `deviceNo + 时间窗` 复合键分散到多个分区，同时提高消费并发。代价是牺牲'同设备全序'换取分区均衡。"

**如果有时间，补一句方法论**（这是最出彩的）：

> "这次压测最大的收获是一个方法论层面的认知：**分布式系统的吞吐瓶颈往往不在单个组件的性能上，而在组件之间的"并行度契约"上**。评估容量时应该先确认并行度契约（分区数、消费者数、连接池大小），再看资源占用，最后才优化单点代码效率。我们这次就是第一项就构成了硬约束，而这恰恰是最容易被忽略的。"

### 3.2 "你这算真正的分布式吗？"

**诚实 + 展示理解**：

> "**使用了分布式中间件、按分布式原则设计，但部署在单机 Docker 上**——是课程环境下的合理简化。
>
> 其中 **HDFS 是真正的分布式架构**：NameNode 与 DataNode 分离部署在两个容器中，WebHDFS 的 307 重定向就是'元数据与数据分离'的直接体现。
>
> 其余组件用到了它们的分布式机制（Kafka 分区与消费者组、ES 按天索引、Nginx upstream），但规模压到了单节点。
>
> 从单机扩到真集群，**要改的是配置而不是代码**：Kafka 加 Broker 和副本、MongoDB 组副本集、ES 加节点、Nginx 后面挂多个后端。"

**如果追问"那哪些是真分布式"**，给个分级表：

| 组件 | 分布式能力 | 项目实际用到 | 程度 |
| :--- | :--- | :--- | :--- |
| HDFS | NameNode/DataNode 分离 | 拆成 2 个容器 | ★★★ |
| Kafka | 分区/副本/消费者组 | 分区键、消费者组；单 Broker | ★★☆ |
| ES | 分片/副本/集群 | 按天滚动索引；单节点 | ★★☆ |
| MongoDB | 分片/副本集 | 时序集合；单实例 | ★☆☆ |
| Nginx | 负载均衡 | upstream 已配；单实例 | ★☆☆ |

### 3.3 "如果设备从 6 台涨到 1 万台，你会怎么改？"

**分层回答**（按优先级，越靠前越紧急）：

| 优先级 | 措施 | 原因 |
| :--- | :--- | :--- |
| **P0** | **提高 topic 分区数 + 消费并发度** | 当前硬瓶颈，不解决其他都白搭 |
| **P0** | HTTP 客户端加超时 | ES/HDFS 卡住会拖死消费线程（当前默认无限等待） |
| P1 | 引入 Redis 做幂等去重 | 当前 `processedMsgIds` 是无界 Set，长时间运行会内存泄漏 |
| P1 | 配置死信队列 | 处理失败的消息不能无限重试卡住分区 |
| P2 | MongoDB 部署副本集 | 高可用 + 读写分离 |
| P2 | 拆分数据接入服务 | 它是唯一随设备数线性增长的模块 |
| P3 | 引入监控体系 | 以 LAG 为核心指标告警 |

**加分补充**：

> "还有一个容易被漏掉的点：**设备类型的数据化**。现在每加一种设备（比如固定摄像头）都要改仿真端、平台消费者、前端三处代码。更合理的做法是把设备类型做成**配置**（声明该类型有哪些能力），消费者用策略模式路由，前端按能力动态渲染。这样**新增设备类型只需加配置，平台代码不动**。"

### 3.4 "系统怎么保证高可用？"

**这个要诚实回答**：

> "**当前不具备高可用能力**——所有组件都是单节点，任何单点故障都会导致服务中断。这是课程环境的合理简化。
>
> 各组件的高可用方案是明确的：Kafka 3+ Broker 副本数 3、MongoDB 副本集、ES 多节点、Nginx 后端多实例。
>
> 不过有一部分**故障隔离**是已经做到的：HDFS 挂了只影响影像上传，不影响设备上报和告警；ES 挂了只影响检索和统计，因为它是可重建的副本，MongoDB 里的权威数据不受影响。"

### 3.5 "这部分是你做的吗？"

**分工类问题，按实际情况答**。关键是**能说出自己那部分的细节**——面试官常在这之后追问具体实现，如果答不上来说明没真做过。
