## 一、引言

在物联网与设备接入类系统中，数据形态往往高度异构：设备台账需要频繁更新、遥测数据只追加且量级巨大、业务实体有完整的生命周期。传统关系型数据库在这种情况下会面临两个困境：一是**Schema 僵化**，业务字段频繁调整需要反复执行 DDL 迁移；二是**单一存储模型难以同时适配"频繁更新的实体"与"海量追加的时序数据"**。

MongoDB 是面向文档的 NoSQL 数据库，2009 年由 10gen（现 MongoDB Inc.）发布。它采用 BSON 文档模型，无需预先定义 Schema；自 5.0 版本起引入的**时序集合（Time Series Collection）** 更是针对带时间戳的测量数据做了专门的存储优化。

本报告调研 MongoDB 的文档模型、存储引擎与时序集合等核心机制，分析其优缺点与适用场景，并结合无人机-机器狗空地协同巡检平台项目，说明实际遇到的问题与解决过程。

## 二、技术原理与架构

### 2.1 文档模型

MongoDB 以 **BSON（Binary JSON）** 文档作为基本存储单位，文档组织在集合（Collection）中。与关系型数据库的概念对应如下：

| 关系型数据库 | MongoDB |
| :--- | :--- |
| 数据库（Database） | 数据库（Database） |
| 表（Table） | 集合（Collection） |
| 行（Row） | 文档（Document） |
| 列（Column） | 字段（Field） |
| 主键（Primary Key） | `_id`（自动创建） |

**核心特点是 Schema-less**：同一集合中的文档可以拥有完全不同的字段结构。

```javascript
// 同一集合中的两个文档，字段可以不同
{ _id: "UAV-001", deviceType: "DRONE",  altitude: 60,   battery: 87 }
{ _id: "DOG-001", deviceType: "ROBOT_DOG", gasValue: 2.1, temperature: 25 }
```

**这一特性的真正价值**在于：业务字段变更时无需执行 DDL 迁移。在需求快速迭代的项目阶段，这显著降低了开发与发布成本。

**代价**是**数据库层面失去了结构约束**——字段类型、必填性、取值范围等约束需要在应用层自行保证，容易因疏漏产生脏数据。

### 2.2 BSON 与 JSON 的区别

BSON 不只是 JSON 的二进制编码，它**扩展了 JSON 不支持的数据类型**：

| 类型 | 说明 | 典型用途 |
| :--- | :--- | :--- |
| **Date** | 64 位整数，表示自 Unix 纪元的毫秒数 | 时间戳（**时序集合强制要求**） |
| ObjectId | 12 字节的唯一标识 | 默认主键 |
| Decimal128 | 128 位十进制浮点数 | 精确的财务计算 |
| Binary | 二进制数据 | 小文件存储 |
| Regex | 正则表达式 | 模式匹配查询 |

**Date 类型的重要性**在本项目中体现得非常充分：MongoDB 的时序集合要求 `timeField` 必须是 `Date` 类型，若传入 long 型时间戳会直接报错。这一点与 JSON 只有"数字"没有"日期"的局限直接相关。

### 2.3 WiredTiger 存储引擎

WiredTiger 是 MongoDB 3.0 起的默认存储引擎，其核心特性包括：

| 特性 | 说明 |
| :--- | :--- |
| **文档级并发控制** | 不同文档的写操作可并行，不必锁定整个集合 |
| **B-Tree 索引** | 默认索引结构，支持等值、范围、排序查询 |
| **数据压缩** | 默认 Snappy 压缩，显著降低存储占用 |
| **MVCC 多版本并发控制** | 读操作不加锁，通过版本快照保证一致性 |
| **可配置缓存** | `wiredTigerCacheSizeGB` 控制缓存大小 |

**关于缓存配置**：MongoDB 默认使用"系统可用内存的一半"作为 WiredTiger 缓存。在多容器共享内存的环境中，这个默认值会与其他容器争抢内存，因此**必须显式限制**。本项目中配置为 512 MB。

### 2.4 索引机制

MongoDB 的索引与关系型数据库类似，基于 B-Tree 实现。常见的索引类型：

| 类型 | 说明 |
| :--- | :--- |
| 单字段索引 | `{ field: 1 }` |
| 复合索引 | `{ field1: 1, field2: -1 }` |
| 唯一索引 | `{ field: 1 }, { unique: true }` |
| 稀疏索引 | 仅索引存在该字段的文档 |
| TTL 索引 | 文档到期后自动删除 |
| 文本索引 | 支持全文检索（分词能力弱于 Elasticsearch） |
| 地理索引 | `2dsphere` / `2d`，支持地理查询 |

**复合索引的字段顺序原则**：应遵循"**等值条件在前、范围或排序条件在后**"。例如 `{ alarmType: 1, eventTime: -1 }` 中，`alarmType` 是等值匹配、`eventTime` 用于排序，这个顺序才能同时利用索引的筛选与排序能力。若顺序颠倒为 `{ eventTime: -1, alarmType: 1 }`，则按 `alarmType` 筛选时无法有效使用该索引。

**关于 `explain()`**：MongoDB 提供执行计划分析工具，可查看查询是否命中索引：

```javascript
db.alarm.find({handleStatus:'PENDING'}).sort({eventTime:-1}).explain('executionStats')
```

关注两个指标：

| 指标 | 含义 |
| :--- | :--- |
| `stage` | 扫描方式：`COLLSCAN`（全表扫描）还是 `IXSCAN`（索引扫描） |
| `totalDocsExamined` | 实际检查的文档数。理想情况下应等于返回的文档数 |

### 2.5 时序集合 ★

**这是 MongoDB 5.0 引入的重要特性，也是本项目的关键技术。**

对于带时间戳的测量类数据，传统做法是把每条记录作为独立文档存储。但这类数据有两个特点：**写入量极大**、**查询模式高度相似**（都是按时间范围和元数据过滤）。为此 MongoDB 提供了专门的存储优化。

**创建方式**：

```javascript
db.createCollection('telemetry', {
  timeseries: {
    timeField: 'eventTime',     // 时间字段（必须是 Date 类型）
    metaField: 'deviceNo',      // 元数据字段（同源数据归一组）
    granularity: 'seconds'      // 数据点的时间粒度
  },
  expireAfterSeconds: 604800    // 7 天后自动删除
});
```

**四个参数的作用**：

| 参数 | 作用 |
| :--- | :--- |
| `timeField` | 分桶的时间依据，**必须是 BSON `Date` 类型** |
| `metaField` | 归组依据，同一 metaField 值的相邻数据被打包进同一个桶 |
| `granularity` | 声明时间粒度，影响分桶的时间跨度（`seconds` / `minutes` / `hours`） |
| `expireAfterSeconds` | 文档自动过期时长，免去人工清理 |

**分桶（Bucketing）机制**：

```text
传统存储（每条独立）：
  文档1 { deviceNo: DOG-001, t: 10:00:00, v: 25.1 }  + 独立索引
  文档2 { deviceNo: DOG-001, t: 10:00:03, v: 25.3 }  + 独立索引
  文档3 { deviceNo: DOG-001, t: 10:00:06, v: 25.0 }  + 独立索引
  ……（大量文档与索引）

时序集合（分桶）：
  ┌───────────────────────────────────────────────┐
  │ Bucket                                        │
  │   meta: DOG-001                               │
  │   timeRange: 10:00:00 ~ 10:01:00              │
  │   data: [ {t:..., v:...}, {t:..., v:...}, ... ]│ ← 列式压缩存储
  └───────────────────────────────────────────────┘
  同一设备的相邻数据被打包成一个桶
```

**三个收益**：

| 收益 | 机制 |
| :--- | :--- |
| **存储占用大幅降低** | 同源数据字段相同、数值连续，列式压缩效果极佳 |
| **索引体积降低** | 桶的数量远少于记录数量，索引条目随之减少 |
| **查询效率提升** | 按时间范围查询时只需扫描相关桶，而非逐条过滤 |

**适用与不适用的数据**：

```text
✓ 适合：每条记录带时间戳、只追加不修改、按时间范围查询、有保留期限
        → 轨迹、传感读数、执行日志、监控指标

✗ 不适合：需要频繁更新单条记录、需要按任意字段做复杂查询
        → 业务实体（如订单、任务、告警），因为它们会被更新
```

> **判据的核心是"是否会更新"**。时序集合面向只追加的数据，若对其执行更新操作，既低效又违背设计初衷。

### 2.6 高可用与扩展

| 机制 | 说明 |
| :--- | :--- |
| **副本集（Replica Set）** | 一组维护相同数据的 mongod 实例，含 1 个 Primary 与多个 Secondary，Primary 故障时自动选举 |
| **分片（Sharding）** | 将数据分散到多个分片集群，通过分片键（Shard Key）决定数据分布 |
| **读关注（Read Concern）** | 控制读取的数据一致性级别 |
| **写关注（Write Concern）** | 控制写操作的确认级别（`w:1` / `w:majority`） |

## 三、技术优缺点分析

### 3.1 优点

**（1）文档模型贴近对象，开发效率高。** 应用的领域对象可直接映射为文档，无需像关系型数据库那样做"对象-关系映射"（ORM）的阻抗匹配。嵌套结构使"一个订单包含多个商品"这类关系可以用单文档表达，避免多表 JOIN。

**（2）Schema 灵活，适应需求迭代。** 字段增减无需 DDL 迁移，适合需求仍在演进的项目阶段。

**（3）查询能力强于多数 NoSQL。** 支持等值、范围、正则、数组、嵌套字段、聚合管道（`$group`、`$match`、`$lookup` 等）、地理查询。这一能力介于关系型数据库与纯键值存储之间，是 MongoDB 的核心竞争力。

**（4）时序集合提供原生的时序数据优化。** 相比引入专门的时序数据库（如 InfluxDB、TDengine），时序集合让项目可以在同一套数据库内同时处理业务数据与时序数据，**降低了技术栈复杂度**。同时内置 TTL 自动过期，免去人工归档。

**（5）水平扩展路径清晰。** 从单节点 → 副本集（高可用）→ 分片集群（水平扩展），演进路径平滑。

**（6）部署轻量。** 单节点即可运行完整功能，无需依赖外部系统（对比 HBase 需要 HDFS + ZooKeeper）。

### 3.2 缺点与局限

**（1）缺少 Schema 约束，易产生脏数据。** 数据库层面不校验字段类型与必填性，约束完全依赖应用层。多人协作的项目中，容易因某处写入遗漏字段而导致下游解析异常。可通过 Schema Validation 部分缓解，但会增加复杂度。

**（2）多文档事务的性能代价。** MongoDB 4.0 起支持多文档事务，但其性能明显低于单文档操作，且事务有 60 秒的默认时限。**设计上应尽量让事务在单文档内完成**——这也是文档模型鼓励嵌套结构的原因之一。

**（3）聚合管道的内存限制。** 聚合管道默认内存上限为 100 MB，超出需显式开启 `allowDiskUse`。大数据量的分组统计用聚合管道实现，性能与内存表现都不理想——**这正是本项目将聚合统计交给 Elasticsearch 的原因**。

**（4）JOIN 能力弱。** `$lookup` 虽能实现关联查询，但性能远不及关系型数据库的 JOIN，且不支持复杂关联。文档模型鼓励用嵌套替代关联，但当数据确实需要多对多关系时，会显得别扭。

**（5）`skip/limit` 深分页性能衰减。** `skip(n)` 的执行方式是**先扫描并丢弃前 n 条文档**，因此复杂度为 O(页码)：

| 页码 | 需扫描并丢弃的文档数 |
| ---: | ---: |
| 1 | 0 |
| 100 | 990 |
| 500 | 4990 |

优化方向是**游标分页**：以上一页最后一条记录的时间戳作为下一页的查询起点，复杂度降为 O(1)。

**（6）默认内存配置不适合容器环境。** WiredTiger 默认使用可用内存的一半，在多容器共享内存时必须显式限制，否则会与其他容器争抢内存。

**（7）全文检索能力弱。** 虽有文本索引，但分词能力、相关度排序、聚合分析都远不及 Elasticsearch，不适合做全文检索的主力。

## 四、适用场景与同类技术对比

### 4.1 适用场景

| 场景 | 判断依据 |
| :--- | :--- |
| 数据结构频繁变化 | 需求快速迭代，Schema 尚不稳定 |
| 半结构化 / 嵌套数据 | 对象天然以文档形式表达（如设备档案、任务单） |
| 读写比例较高、以主键或少量字段查询为主 | 文档模型与索引能很好支撑 |
| **带时间戳的测量数据** | **时序集合专门优化** |
| 内容管理、用户画像、日志存储 | 典型文档型场景 |

### 4.2 不适合的场景

| 场景 | 原因 | 更适合的方案 |
| :--- | :--- | :--- |
| 强事务的金融核心系统 | 多文档事务性能受限 | 关系型数据库（PostgreSQL、Oracle） |
| 复杂多表关联分析 | JOIN 能力弱 | 关系型数据库、数据仓库 |
| 全文检索与复杂聚合 | 文本索引与聚合能力有限 | Elasticsearch |
| 超大规模稀疏宽表 | 文档模型不擅长 | HBase、Cassandra |
| 海量时序数据的长期存储 | 单机容量有限 | 专门的时序数据库（InfluxDB、TDengine） |

### 4.3 同类技术对比

| 维度 | **MongoDB** | HBase | PostgreSQL (JSONB) | Cassandra |
| :--- | :--- | :--- | :--- | :--- |
| 数据模型 | 文档（BSON） | 列族宽表 | 关系 + JSON | 宽列 |
| Schema | 灵活 | 需预定义列族 | 强约束 | 灵活 |
| 查询能力 | **强**（含聚合、地理） | 弱（主键扫描） | **最强**（SQL） | 弱 |
| 写入吞吐 | 高 | **极高** | 中 | **极高** |
| 事务 | 多文档（性能受限） | 单行 | **完整 ACID** | 轻量 |
| 时序优化 | **时序集合** | 无 | TimescaleDB 扩展 | 无 |
| 扩展方式 | 分片 | **原生水平扩展** | 分片（Citus） | **无中心节点** |
| 部署复杂度 | **低** | 高（依赖 HDFS + ZooKeeper） | 低 | 中 |
| 适合的数据量 | 中等至大 | 极大 | 中等 | 极大 |

**选型要点**：

- **数据量未达"百亿行"级别、且查询模式多样** → MongoDB 更合适；
- **需要复杂 SQL 与强事务** → PostgreSQL（含 JSONB，兼具灵活性）；
- **数据量极大、写入吞吐优先、查询模式固定** → HBase / Cassandra；
- **需要原生时序优化且不想引入新组件** → MongoDB 时序集合。

### 4.4 关于"时序集合 vs 专用时序数据库"的讨论

本项目的做法是在 MongoDB 内使用时序集合，而不是引入 InfluxDB 或 TDengine。这是一个值得说明的取舍：

| 维度 | MongoDB 时序集合 | 专用时序数据库（InfluxDB 等） |
| :--- | :--- | :--- |
| 技术栈数量 | **不增加**（复用已有的库） | 需额外部署与运维 |
| 时序压缩比 | 良好 | **更优**（专为时序设计） |
| 时序查询能力 | 基础（按时间范围过滤） | **强**（降采样、连续查询、插值） |
| 与业务数据关联 | **同一库内可直接关联** | 需跨库查询 |
| 运维成本 | 低 | 中 |

**结论**：当项目已使用 MongoDB、且时序查询需求较基础（按时间范围与设备过滤）时，**使用时序集合是更务实的选择**——它避免了引入新组件带来的运维成本，且能与业务数据在同一库内关联。若时序数据规模达到单机瓶颈、或需要降采样等高级分析能力，再考虑引入专用时序数据库。

## 五、在本项目中的实践

### 5.1 数据库设计

项目建立了 9 个集合，按数据特征分为三类：

| 类型 | 集合 | 存储选择 | 理由 |
| :--- | :--- | :--- | :--- |
| **最新值型** | `device_status` | 普通集合 | 每设备一条，心跳到达时覆盖更新 |
| **时间序列型** | `telemetry`、`sensor_data`、`task_log` | **时序集合 + 7 天 TTL** | 只追加、量大、有时效 |
| **业务实体型** | `alarm`、`task`、`media_meta`、`user` | 普通集合 | 有生命周期、会被更新 |

**关键设计——台账与流水分离**：

| 集合 | 性质 | 操作模式 | 存储类型 |
| :--- | :--- | :--- | :--- |
| `task` | 任务**当前状态**，一个任务一份 | 频繁更新（进度 0→50→100） | 普通集合 |
| `task_log` | 任务**执行流水**，只追加 | 只插入 | 时序集合（7 天 TTL） |

若混在一张表中，就不得不在时序集合上执行更新操作，**既低效又违背其设计初衷**。这一分离是读写模型分离（CQRS）思想的简化实践。

### 5.2 遇到的问题与解决方案

#### 问题一：Spring Boot 4 中 MongoDB 配置静默失效

**现象**：项目本地开发时 MongoDB 连接正常，但容器化部署后业务服务始终无法连接数据库，日志显示仍在尝试连接 `localhost:27017`——而配置文件中已明确写入了容器服务名 `mongodb:27017`。

**排查过程**：

1. 进入容器执行 `env | grep MONGO`，确认环境变量已正确注入：

   ```text
   SPRING_MONGODB_URI=mongodb://mongodb:27017/uav_platform
   ```

2. 在容器内测试网络连通性，`mongodb:27017` 可正常解析并连接；
3. 检查应用日志，未发现任何配置相关的报错或警告；
4. 查阅 Spring Boot 4 的迁移文档，发现**配置前缀发生了变更**。

**根因分析**：

Spring Boot 4 将 MongoDB 的配置前缀由 `spring.data.mongodb.*` 变更为 `spring.mongodb.*`。

关键在于：**旧前缀不会导致启动失败，而是被静默忽略，然后回退为默认值**。因此应用照常启动、照常连接 `localhost:27017`（默认值），日志中没有任何异常提示。

```properties
# ✗ 旧写法：Spring Boot 4 下静默失效
spring.data.mongodb.uri=mongodb://mongodb:27017/uav_platform

# ✓ 新写法
spring.mongodb.uri=mongodb://mongodb:27017/uav_platform
```

**解决方案**：

改用新前缀 `spring.mongodb.uri`，环境变量相应改为 `SPRING_MONGODB_URI`。

**经验总结**：

> **配置项"看起来对但不生效"时，应优先怀疑属性名在版本升级中发生了变更。**
>
> 这类问题比"配置错误"更难排查——因为错误配置通常会报错，而**过时的属性名不会报错，只会被静默忽略并回退默认值**。
> 升级框架版本时，务必查阅官方的迁移指南（Migration Guide），而非仅依赖兼容性。

#### 问题二：时序集合写入报错——时间字段类型不符

**现象**：将遥测数据写入时序集合时报错：

```text
'eventTime' must be present and contain a valid BSON UTC datetime value
```

**排查过程**：

1. 确认消息中 `eventTime` 字段确实存在（设备上报的消息体中有该字段）；
2. 检查该字段的值，发现是 long 型毫秒时间戳，如 `1789610393814`；
3. 查阅文档确认：时序集合的 `timeField` **必须是 BSON `Date` 类型**，不接受 long。

**根因分析**：

设备端通过 JSON 序列化消息时，`long` 类型的时间戳被序列化为 JSON 数字。JSON 本身没有"日期"类型，而反序列化到 Java 对象时得到的是 `long`。但 MongoDB 时序集合的分桶机制需要真正的时间类型才能计算时间范围，因此强制要求 `Date` 类型。

**解决方案**：

在实体转换时做类型转换：

```java
doc.setEventTime(new Date(msg.eventTime()));   // long → Date
```

**经验总结**：

> **跨系统传递时间时，必须核对每一跳的数据类型。**
> 这个问题的根源在于 JSON 数据类型与 BSON 数据类型的差异：JSON 只有"数字"没有"日期"，而 BSON 有独立的 `Date` 类型。
> 类似的坑在本项目中出现过多次——向 Elasticsearch 写入时，`date` 字段同样要求 ISO-8601 字符串而非毫秒时间戳。

#### 问题三：深分页查询性能随页码衰减

**现象**：告警列表接口在翻到较后页码时响应明显变慢。

**排查过程**：

1. 使用 `explain('executionStats')` 查看执行计划；
2. 对比第 1 页与第 100 页的 `totalDocsExamined` 指标，发现后者远大于实际返回的文档数。

**根因分析**：

查询使用 `skip((page-1)*size).limit(size)` 实现分页。MongoDB 的 `skip(n)` 需要**先扫描并丢弃前 n 条文档**，因此页码越大，被白白扫描的文档越多，复杂度为 O(页码)。

**解决方案（规划中）**：

改用**游标分页**：以当前页最后一条记录的时间戳作为下一页查询的起点：

```javascript
// 传统分页（O(页码)）
db.alarm.find().sort({eventTime:-1}).skip(5000).limit(10)

// 游标分页（O(1)）
db.alarm.find({ eventTime: { $lt: <上一页最后一条的eventTime> } })
        .sort({eventTime:-1}).limit(10)
```

由于 `alarm` 集合上已建立 `{alarmType:1, eventTime:-1}` 索引，游标分页可直接利用索引定位，复杂度降为 O(1)。

**代价说明**：游标分页无法直接跳转到任意页码（只能"下一页"），因此适用于"无限滚动"式的列表，不适用于"跳转到第 N 页"的交互。这是一个**交互设计与性能之间的取舍**。

## 六、总结与体会

通过本项目的实践，我对 MongoDB 的认识从"一个存储 JSON 的数据库"深化为"一个具备多种存储模型的文档数据库"。

**三点主要收获**：

**第一，理解了"按数据特征选存储"的重要性。** 本项目中的三类数据（最新值型、时间序列型、业务实体型）读写模式完全不同，分别用了普通集合与时序集合。若统一用普通集合存储遥测数据，会面临存储膨胀与索引臃肿；若统一用时序集合，则业务实体的更新操作会变得低效。

**第二，"是否会更新"是选择存储模型的关键判据。** 时序集合面向只追加的数据，普通集合面向会被更新的实体。本项目中 `task`（台账，会更新）与 `task_log`（流水，只追加）的分离就是这一判据的直接应用。

**第三，认识到"静默失效"类问题的排查难度。** Spring Boot 4 配置前缀变更导致的问题没有产生任何错误日志，仅表现为"配置不生效"。这提示我在排查配置问题时，除了检查配置本身的正确性，还要确认**配置项在当前框架版本中是否仍然有效**。
