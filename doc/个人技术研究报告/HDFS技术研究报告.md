## 一、引言

在巡检、监控、影像采集类系统中，图片与视频等大文件占据了绝大部分存储容量。这类数据具有鲜明的特征：**单文件较大、一次写入后很少修改、读取频次远低于写入时的产生速度、需要长期保存**。

用传统关系型数据库存储这类文件存在明显问题：BLOB 字段会撑爆数据库、备份恢复极其缓慢、且数据库的事务与查询能力对二进制数据毫无用处。用单机文件系统则面临容量上限与可靠性问题。

Hadoop 分布式文件系统（HDFS）正是为解决"大数据量的可靠存储"而设计的。它源自 Google 的 GFS 论文，2006 年随 Hadoop 项目开源，现已成为大数据生态的存储基石。

本报告调研 HDFS 的架构设计与读写机制，分析其优缺点与适用场景，并结合无人机-机器狗空地协同巡检平台项目，说明实际遇到的问题与解决过程。

## 二、技术原理与架构

### 2.1 主从架构

HDFS 采用经典的**主从（Master/Slave）架构**，由两类节点组成：

```text
                    ┌──────────────────┐
                    │    NameNode      │  元数据管理者
                    │  （目录树、块映射、│  元数据常驻内存
                    │    块位置信息）    │
                    └────────┬─────────┘
                             │ 元数据操作
              ┌──────────────┼──────────────┐
              ▼              ▼              ▼
      ┌────────────┐ ┌────────────┐ ┌────────────┐
      │ DataNode 1 │ │ DataNode 2 │ │ DataNode 3 │   数据存储者
      │  块 1,2,3   │ │  块 2,3,4   │ │  块 1,3,4   │   实际存放数据块
      └────────────┘ └────────────┘ └────────────┘
```

| 节点 | 职责 |
| :--- | :--- |
| **NameNode** | 管理文件系统的**命名空间**（目录树、文件属性）与**块映射**（每个文件由哪些块组成、每个块存放在哪些 DataNode 上）。**所有元数据常驻内存**，因此能快速响应元数据查询。 |
| **DataNode** | 实际存储数据块。定期向 NameNode 发送心跳与块报告，汇报自身状态与持有的块列表。 |
| **SecondaryNameNode** | 注意：它**不是** NameNode 的备份，而是辅助节点，负责合并编辑日志与镜像文件，缩短 NameNode 重启时间。 |

**Block（数据块）** 是 HDFS 的基本存储单位，默认大小 128 MB。文件被切分为若干块，每块以副本形式存储在多个 DataNode 上。

> **块设计的价值**：块比文件更容易管理——块大小固定，NameNode 只需记录"文件由哪些块组成"，而不必记录文件在磁盘上的物理位置。同时，大块减少了 NameNode 的元数据量。

### 2.2 副本机制与机架感知

**副本（Replication）** 是 HDFS 可靠性的核心。默认副本数为 3，副本的放置遵循**机架感知（Rack Awareness）** 策略：

```text
副本 1：写在客户端所在节点（若客户端不在集群内，则随机选择）
副本 2：写在【不同机架】的某个节点
副本 3：写在【副本 2 所在机架】的另一个节点
```

**为什么这样放置**：

- 副本 2 放在不同机架，保证**单个机架断电或交换机故障**不会导致数据完全丢失；
- 副本 3 与副本 2 同机架，保证**跨机架写入的带宽开销**可控。

这是一个**可靠性与网络开销之间的权衡**——不要为了可靠性把所有副本撒到不同机架，因为跨机架的带宽通常是瓶颈。

**副本的自动恢复**：DataNode 定期向 NameNode 发送心跳。若 NameNode 长时间未收到某 DataNode 的心跳，则判定其失效，并触发副本复制，将失效节点上的块在其他节点上重新复制，恢复到目标副本数。

### 2.3 读写流程与 307 重定向 ★

HDFS 的读写流程体现了其最重要的架构决策——**元数据与数据分离**。

#### 写文件流程

```text
   ┌─────────┐                    ┌──────────┐              ┌──────────┐
   │  客户端  │                    │ NameNode │              │ DataNode │
   └────┬────┘                    └────┬─────┘              └────┬─────┘
        │  ① 请求创建文件                │                        │
        │─────────────────────────────→│                        │
        │                              │  校验权限、检查文件是否存在 │
        │  ② 返回可用 DataNode 地址       │                        │
        │←─────────────────────────────│                        │
        │                                                       │
        │  ③ 直接写入数据块                                       │
        │──────────────────────────────────────────────────────→│
        │                                                       │  ④ 流水线复制
        │                                                       │─────→ 其他 DataNode
        │  ⑤ 确认写入完成                                        │
        │←──────────────────────────────────────────────────────│
```

#### 读文件流程

```text
   ┌─────────┐                    ┌──────────┐              ┌──────────┐
   │  客户端  │                    │ NameNode │              │ DataNode │
   └────┬────┘                    └────┬─────┘              └────┬─────┘
        │  ① 请求读取文件                │                        │
        │─────────────────────────────→│                        │
        │  ② 返回各数据块所在的 DataNode  │                        │
        │←─────────────────────────────│                        │
        │                                                       │
        │  ③ 直接读取数据块（就近选择副本）                          │
        │──────────────────────────────────────────────────────→│
```

#### 为什么客户端要直连 DataNode

这是理解 HDFS 设计中"307 重定向"现象的关键。

> **文件的数据量远大于元数据量。** 假设一个 1 GB 的文件，其元数据（文件名、大小、块列表、块位置）不过几百字节，而数据是 1 GB。数据量相差 6 个数量级。
>
> 若所有数据都经过 NameNode 转发，NameNode 会立即成为整个集群的**性能瓶颈**与**单点故障**——它既要处理全部元数据请求，又要搬运全部数据。
>
> 因此 HDFS 的设计是：**NameNode 只回答"数据在哪里"，客户端直接与 DataNode 交换数据。**

这一设计在 WebHDFS（REST 接口）中的表现就是 **HTTP 307 重定向**：

```text
客户端 → NameNode：PUT /webhdfs/v1/path?op=CREATE
NameNode → 客户端：307 Temporary Redirect
                   Location: http://datanode-x:9864/webhdfs/v1/...?op=CREATE
客户端 → DataNode：PUT <Location>（携带真实文件字节）
DataNode → 客户端：201 Created
```

**因此，307 重定向不是实现细节或兼容性问题，而是 HDFS 架构设计的必然结果。**

### 2.4 三种访问方式

| 方式 | 协议 | 端口 | 适用场景 |
| :--- | :--- | :--- | :--- |
| **Hadoop Java Client** | RPC | 8020 | Java 应用，功能最完整 |
| **命令行 `hdfs dfs`** | RPC | 8020 | 运维操作、脚本 |
| **WebHDFS REST** | HTTP | 9870 | 跨语言、跨环境访问 |

> **端口辨析**：8020 是 RPC 端口，9870 是 HTTP 端口（Web UI 与 WebHDFS 共用）。两者容易混淆。

## 三、技术优缺点分析

### 3.1 优点

**（1）存储容量近乎无限。** 通过增加 DataNode 即可线性扩展容量。NameNode 的元数据常驻内存，可管理数亿文件（取决于内存容量）。

**（2）高容错性。** 多副本机制 + 机架感知 + 自动副本恢复，使单节点甚至单机架故障都不影响数据可用性。

**（3）高吞吐顺序访问。** HDFS 为大文件顺序读写做了深度优化：块大小 128 MB、就近读取副本、流水线复制。对于"一次写入、多次读取"的大文件场景，吞吐量远超普通文件系统。

**（4）与大数据生态无缝集成。** MapReduce、Spark、Hive、HBase 等组件都以 HDFS 作为底层存储。

**（5）硬件成本低。** 设计上假定硬件会故障，因此可以部署在廉价商用服务器上，通过软件层面保证可靠性。

**（6）数据一致性模型简单。** "一次写入、多次读取"的模型使并发控制极为简单——文件写入完成后不可修改（仅支持追加），避免了复杂的一致性协调。

### 3.2 缺点与局限

**（1）不适合大量小文件。** 这是 HDFS 最著名的局限。原因在于：

- NameNode 的内存中，**每个文件、每个块、每个副本都对应一条元数据记录**（约 150 字节）；
- 1000 万个 1 KB 的小文件，其元数据占用约 1.5 GB 内存，而数据本身只有 10 GB；
- 更严重的是，读取小文件需要频繁与 NameNode 交互，NameNode 会成为瓶颈。

**因此 HDFS 的通用实践是：小文件先合并为大文件再存储**（如使用 HAR 归档或 SequenceFile）。

**（2）不支持低延迟访问。** HDFS 为高吞吐优化，牺牲了低延迟。对于需要毫秒级响应的随机读场景（如在线交易），HDFS 不合适。

**（3）不支持文件修改。** 文件一旦写入完成，**只能追加，不能随机修改**。这是"一次写入、多次读取"模型带来的必然限制。

**（4）NameNode 是单点。** 尽管有 HA 方案（NameNode 主备），但配置复杂。单 NameNode 部署下，NameNode 故障将导致整个集群不可用。

**（5）元数据全部在内存中，限制了文件数量。** 集群能管理的文件总数受 NameNode 内存限制，无法通过加磁盘解决。

**（6）部署与运维复杂度较高。** 需要维护 NameNode、DataNode、SecondaryNameNode 等多个角色，且 Java 环境、网络配置、权限体系都有较多细节。相比之下，对象存储与 MinIO 的部署要简单得多。

**（7）权限体系较粗糙。** HDFS 的权限模型是简化的 POSIX 模型（所有者/组/其他 + 读写执行），且早期版本默认不开启。实际生产环境通常需要结合 Kerberos 做认证，配置复杂。

## 四、适用场景与同类技术对比

### 4.1 适用场景

| 场景 | 判断依据 |
| :--- | :--- |
| **大文件存储** | 单文件数百 MB 至 GB 级 |
| **一次写入、多次读取** | 数据产生后很少修改 |
| **高吞吐顺序读写** | 批量处理、离线分析 |
| **需要容错与容量扩展** | 数据重要且持续增长 |
| 大数据生态集成 | 需要与 Spark、Hive 等协作 |

### 4.2 不适合的场景

| 场景 | 原因 | 更适合的方案 |
| :--- | :--- | :--- |
| 海量小文件 | NameNode 内存瓶颈 | 对象存储、合并后存储 |
| 低延迟随机读写 | 为高吞吐优化，延迟较高 | 关系型数据库、SSD 存储 |
| 需要频繁修改文件 | 只支持追加 | 普通文件系统、对象存储 |
| 结构化数据查询 | 无查询能力 | 数据库 |
| 小规模数据（< 1 TB） | 运维成本高于收益 | 普通文件系统、对象存储 |

### 4.3 同类技术对比

| 维度 | **HDFS** | MinIO | Ceph | 对象存储（S3/OSS） |
| :--- | :--- | :--- | :--- | :--- |
| 定位 | 分布式文件系统 | 对象存储 | 统一存储 | 云对象存储 |
| 访问协议 | RPC / WebHDFS | S3 API | S3 / Swift / CephFS | HTTP(S) |
| 文件修改 | 仅追加 | 覆盖 | 覆盖 | 覆盖 |
| 小文件表现 | **差** | 好 | 中 | 好 |
| 部署复杂度 | 高 | **低** | 高 | 无需部署 |
| 扩展性 | 强 | 强 | **最强** | 由云厂商保证 |
| 成本 | 自建硬件 | 自建硬件 | 自建硬件 | 按量付费 |
| 与大数据生态 | **原生集成** | 需适配 | 需适配 | 需适配 |
| 适合规模 | PB 级 | TB~PB 级 | PB~EB 级 | 不限 |

**选型要点**：

- **需要与 Hadoop/Spark 生态集成** → HDFS；
- **只需要一个简单的对象存储、部署要轻** → MinIO；
- **需要统一的块/文件/对象三种存储** → Ceph；
- **不想自建运维** → 云对象存储。

### 4.4 关于"小文件问题"的深入讨论

HDFS 的小文件问题是其架构的直接后果，值得展开。

**问题的本质**：NameNode 在内存中为**每个文件、每个块、每个副本**各维护一条元数据记录。因此：

```text
场景 A：1 个 10 GB 的文件
  → 10 GB / 128 MB ≈ 80 个块
  → 元数据 ≈ 80 × 3(副本) × 150 字节 ≈ 36 KB

场景 B：1000 万个 1 KB 的文件
  → 1000 万个文件 = 1000 万个块（每个文件至少 1 个块）
  → 元数据 ≈ 1000 万 × 3 × 150 字节 ≈ 4.5 GB
  → 而数据总量只有 10 GB
```

场景 B 中，**元数据占用已达 4.5 GB，接近数据量的一半**——这是完全不可接受的。

**通用解决方案**：

| 方案 | 说明 |
| :--- | :--- |
| **文件合并** | 用小文件合并为大文件（如 HAR 归档、SequenceFile），存储时逻辑上仍按小文件访问 |
| **合并写入** | 应用层攒批，多个小文件合并后一次性写入 |
| **使用对象存储** | 对象存储的元数据与数据一同存储，无此瓶颈 |

**本项目的实践**：影像文件按 `设备 / 日期` 两级目录分区（`/uav/media/{设备编号}/{yyyyMMdd}/`），虽未做文件合并，但通过**目录分区避免了单一目录下的条目爆炸**，同时便于按日期整目录清理。这是应对规模增长的通用手段。

## 五、在本项目中的实践

### 5.1 部署与接入方式

**先明确写入与读取的分工**：影像的**写入由设备自己完成**（设备端 `StorageClient`），
平台的 `HdfsService` 只负责**读取**（前端预览、下载）。这一分工是后文"问题一"所引发的
架构改造的结果。

本项目部署 HDFS 3.2.1，采用 **NameNode 与 DataNode 分容器**的方式，模拟分布式部署：

| 容器 | 角色 | 端口 |
| :--- | :--- | :--- |
| `hadoop-namenode` | NameNode | 9870（WebUI/WebHDFS）、9000→8020（RPC） |
| `hadoop-datanode` | DataNode | 9864 |

**接入方式的选择过程**：

项目最初尝试用 `docker exec` 调用 `hdfs dfs -put` 命令上传文件。这种方式在单机开发时可用，但**容器化后立即失效**——业务服务运行在自己的容器内，而该容器中**没有 docker 客户端**，无法"从容器内指挥宿主机"。

随后评估了 Hadoop Java Client。它是官方客户端、功能最完整，但需要：

- 引入 `hadoop-client` 依赖（数十 MB 的依赖树）；
- 配置 `core-site.xml` 等 Hadoop 配置文件；
- 而项目实际只需要"上传文件"与"下载文件"两个功能。

**最终选择 WebHDFS REST**，理由是：标准 HTTP 协议、语言无关、不依赖任何命令行工具、不引入额外依赖，且请求内容可直接用 curl 复现，便于排查问题。

**存储路径规范**：

```text
/uav/media/{设备编号}/{yyyyMMdd}/{fileId}.jpg
例如：/uav/media/DOG-001/20260918/IR-DOG-001-1789610393814.jpg
```

### 5.2 遇到的问题与解决方案

#### 问题一：上传后 HDFS 中出现异常路径

**现象**：影像上传后，在 HDFS WebUI 中看到的路径形如：

```text
/app/sim-files/D:\school\all\项目\企业项目实践\backend\device-simulator\sim-files\IMG-UAV-001-xxx.jpg
```

整个 Windows 绝对路径被当成了**文件名**。

**排查过程**：

1. 查看仿真端日志，确认其上报的 `localPath` 字段是宿主机绝对路径：

   ```text
   D:\school\all\项目\企业项目实践\backend\device-simulator\sim-files\IMG-UAV-001-1789610393814.jpg
   ```

2. 业务服务在容器内尝试用该路径读取文件，失败；
3. 检查容器内实际的文件位置，发现文件被正确挂载到了 `/app/sim-files/` 下；
4. 定位到问题出在路径解析环节。

**根因分析**：

这是一个典型的**跨操作系统路径语义差异**问题：

| 环境 | 路径分隔符 | `Paths.get()` 的行为 |
| :--- | :--- | :--- |
| Windows（仿真端） | `\` | 正确识别为目录分隔符 |
| **Linux（业务服务容器）** | `/` | **不识别 `\`**，将整个字符串视为一个文件名 |

因此 Linux 容器中的 `Paths.get("D:\\school\\...\\xxx.jpg")` 会尝试查找一个名为 `D:\school\...\xxx.jpg` 的文件，自然找不到。

**解决方案**：

用正则剥离所有目录前缀，只保留文件名，再用容器内的挂载路径重新拼接：

```java
// 正则同时兼容 \ 和 / 两种分隔符
String fileName = msg.localPath().replaceAll("^.*[\\\\/]", "");
String realPath = simFilesDir + "/" + fileName;    // /app/sim-files/xxx.jpg
```

正则 `^.*[\\\\/]` 的含义是"从开头到最后一个反斜杠或正斜杠"，因此无论传入哪种分隔符都能正确剥离目录部分。

**经验总结**：

> **跨系统的数据传递中，凡是"路径"都需要特别小心。**
> 路径的表示方式依赖操作系统：分隔符不同、绝对路径格式不同、大小写敏感性不同。
> 更稳妥的做法是：**消息中只传递相对标识（如文件名或 fileId），由接收方根据自身环境拼接完整路径**——这样就把环境相关的部分留在了各自的边界内。

**后续演进（重要）**：

上文的正则剥前缀只是**当时的补丁**，它治标不治本——仍然依赖"平台能访问设备文件系统"
这一前提（靠 Docker 绑定挂载人工制造）。后来我们对这一环节做了**架构层面的改造**：

| | 改造前 | 改造后 |
| :--- | :--- | :--- |
| 谁上传文件 | **平台**（读设备本地文件再上传） | **设备自己**上传 |
| 消息携带什么 | `localPath`（本地绝对路径） | `storageRef`（存储引用） |
| 平台是否接触设备路径 | **是**（故需正则剥前缀绕过环境差异） | **否** |
| "路径分隔符差异"问题 | 存在（需打补丁） | **不再有产生的土壤** |

**核心认知**：**跨系统契约应传递「标识」而不是「位置」。**
`localPath` 是设备端的环境相关信息，平台既无法解析也不该关心；
`storageRef` 是存储系统给出的引用，与环境无关，双方都能理解。

> 这次演进让我体会到：**打补丁解决的是症状，改设计解决的是病因。**
> 当一个问题需要靠"特殊处理"才能绕过时，通常说明设计本身需要重新审视。

#### 问题二：误以为 307 是"异常响应"

**现象**：初次实现 WebHDFS 上传时，代码检查响应状态码是否为 200，结果始终失败——实际返回的是 307。

**排查过程**：

1. 打印响应详情，发现状态码为 307，且响应头中有 `Location` 字段；
2. 用 curl 手工复现请求，观察到了完整的三步过程；
3. 查阅 HDFS 架构文档，理解 307 的设计意图。

**根因分析**：

这不是异常，而是 HDFS 架构的**正常流程**。依据第二章的原理，NameNode 只负责元数据，数据必须由客户端直接写入 DataNode。因此 `op=CREATE` 请求的响应就是 307 重定向，客户端需要：

1. 读取响应头中的 `Location` 字段；
2. 向该地址重新发起 PUT 请求，并在请求体中携带实际数据。

另一个技术细节：Java 的 `HttpClient.newHttpClient()` 默认 `followRedirects = NEVER`，**不会自动跟随重定向**，必须手动处理。

**解决方案**：

```java
// ① 请求创建文件
HttpRequest createReq = HttpRequest.newBuilder()
        .uri(URI.create(webhdfsBase + "/webhdfs/v1" + hdfsPath + "?op=CREATE&overwrite=true"))
        .PUT(HttpRequest.BodyPublishers.noBody())
        .build();
HttpResponse<String> createResp = httpClient.send(createReq, HttpResponse.BodyHandlers.ofString());

// ② 期望得到 307，读取 Location 头
if (createResp.statusCode() != 307) {
    log.error("[HDFS] CREATE 未返回重定向: {}", createResp.statusCode());
    return false;
}
String location = createResp.headers().firstValue("Location")
        .orElseThrow(() -> new IllegalStateException("响应缺少 Location 头"));

// ③ 手动跟随重定向，把真实数据 PUT 到 DataNode
HttpRequest putReq = HttpRequest.newBuilder()
        .uri(URI.create(location))
        .PUT(HttpRequest.BodyPublishers.ofByteArray(data))
        .build();
HttpResponse<String> putResp = httpClient.send(putReq, HttpResponse.BodyHandlers.ofString());
return putResp.statusCode() == 201;
```

**状态码辨析**：`op=MKDIRS` 成功返回 200，`op=CREATE` 最终写入成功返回 **201**，两者不同。

**经验总结**：

> **理解协议背后的架构，才能正确判断"什么样的响应是正常的"。**
> 初次遇到 307 时，直觉会认为"重定向是异常，应该跟随或忽略"。但理解 HDFS 的元数据/数据分离架构后就会明白：**307 恰恰是这个架构得以成立的关键机制**——它在告诉客户端"数据不在我这里，去那边写"。

## 六、总结与体会

通过本项目的实践，我对 HDFS 的理解从"一个分布式文件系统"深入到"一个围绕大文件高吞吐场景深度优化的存储系统"。

**三点主要收获**：

**第一，理解了"设计取舍"而非"功能列表"才是理解一个系统的关键。** HDFS 的许多"缺点"（不支持小文件、不支持修改、延迟较高）其实都是它为"大文件、一次写入、高吞吐"这个目标所做的主动取舍，而非设计缺陷。理解它为什么这样取舍，才能判断自己的场景是否适合。

**第二，通过 307 重定向理解了"元数据与数据分离"的架构价值。** 这个机制初看反直觉（为什么要把请求重定向走？），但理解后就会发现它是避免 NameNode 成为瓶颈的必要设计。**很多看似"绕弯"的设计，背后都是为了解决某个具体的瓶颈问题。**

**第三，认识到跨系统协作中"约定"的重要性。** 本项目中遇到的路径分隔符问题，本质上不是技术难题，而是两个系统对"路径"这一概念的约定不一致。这类问题在分布式系统集成中极为常见，也提醒我在设计跨系统接口时，应尽量**传递与平台无关的标识，而非平台相关的具体形式**。
