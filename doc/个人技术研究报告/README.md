## 二、统一报告结构

六份报告采用同一套结构，便于评阅对比：

```text
一、引言
二、技术原理与架构          ← 核心：讲清"它是什么、怎么做到的"
三、技术优缺点分析          ← 核心：不能只讲优点，必须讲局限
四、适用场景与同类技术对比   ← 核心：回答"什么时候该用它"
五、在本项目中的实践
    5.1 部署与配置
    5.2 遇到的问题与解决方案  ← 必须是真实遇到的问题
六、总结与体会
参考文献
```

**撰写要点**：

| 章节 | 要点 | 常见问题 |
| :--- | :--- | :--- |
| 原理与架构 | 讲清**机制**（为什么这样做能解决问题），而非罗列名词 | ❌ 只抄官方文档的功能列表 |
| 优缺点 | **必须写局限**。只讲优点的分析被认为没有独立思考 | ❌ 通篇赞美 |
| 适用场景 | 给出**判据**（什么情况下该用、什么情况下不该用） | ❌ 写成"什么场景都能用" |
| 项目实践 | 用**真实的报错信息与排查过程**，不虚构 | ❌ 编造从未遇到的问题 |
| 参考文献 | 官方文档 + 技术图书 + 网络资源，规范标注 | ❌ 只写网址不写标题 |

## 三、与《组件实现说明》的分工

项目中有两份内容相近的文档，定位不同：

| | [../组件实现说明/](../组件实现说明/README.md) | **本目录（个人技术研究报告）** |
| :--- | :--- | :--- |
| **定位** | 项目组共同产出 | **个人独立作业** |
| **视角** | 我们**怎么实现的** | 这项技术**本身是什么** |
| **侧重** | 代码、配置、项目设计决策 | 原理、架构、行业对比、适用判据 |
| **读者** | 项目组内部、答辩评委 | 课程评阅教师 |
| **署名** | 项目组 | **个人** |

> **可以引用，但不能照搬**。研究报告应体现**个人对技术的理解**，而非项目实现的复述。
> 建议在"在本项目中的实践"一节引用实现说明中的具体代码与问题，其余章节独立撰写。

## 四、六份报告覆盖的技术面

```text
                ┌──────────────────────────────────┐
                │        分布式系统技术栈            │
                └──────────────────────────────────┘
                                │
        ┌───────────┬───────────┼───────────┬───────────┐
        ▼           ▼           ▼           ▼           ▼
    消息队列     分布式存储   分布式文件   检索引擎    接入网关
      Kafka      MongoDB        HDFS         ES        Nginx
        │           │           │           │           │
        └───────────┴───────────┴───────────┴───────────┘
                                │
                        ┌───────▼────────┐
                        │  Docker 容器化  │  ← 承载上述全部组件的运行环境
                        └────────────────┘
```

**Docker 报告的特殊性**：其他五份是"被容器承载的组件"，Docker 是"承载者本身"。
它需要覆盖的不只是容器原理，还包括**多容器编排**——这正是本项目 8 个容器能够一键启动的原因。
