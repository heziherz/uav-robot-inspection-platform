## 一、引言

在分布式企业应用开发中，一个项目往往需要同时运行多种中间件：分布式文件系统、分布式数据库、消息中间件、检索引擎、负载均衡网关。这些组件各有自己的运行时依赖、版本要求与配置体系，若安装在同一台机器上，极易产生端口冲突、依赖冲突与版本冲突。

传统的解决方式是虚拟机：为每个组件创建一个独立虚拟机，在虚拟机内安装运行环境。但虚拟机需要模拟完整的硬件并运行独立的操作系统内核，资源开销大（每个虚拟机至少需要数 GB 内存与数十 GB 磁盘）、启动慢（分钟级）。

Docker 于 2013 年发布，它提出了一种更轻量的方案：**容器不模拟硬件、不包含独立内核，而是直接复用宿主内核**，通过操作系统提供的隔离机制实现进程级的资源隔离。容器启动在秒级、资源开销接近原生进程。

本报告调研 Docker 的隔离原理、镜像机制与容器编排能力，分析其优缺点与适用场景，并结合无人机-机器狗空地协同巡检平台项目，说明实际遇到的问题与解决过程。

## 二、技术原理与架构

### 2.1 容器与虚拟机的本质区别

```text
虚拟机：
  ┌──────────────────────────────────────┐
  │  应用 A  │  应用 B  │  应用 C         │
  ├──────────┼──────────┼────────────────┤
  │ Guest OS │ Guest OS │ Guest OS       │  ← 每个虚拟机一套完整内核
  ├──────────┴──────────┴────────────────┤
  │         Hypervisor（虚拟化层）          │
  ├───────────────────────────────────────┤
  │          Host OS（宿主内核）            │
  ├───────────────────────────────────────┤
  │              硬件                      │
  └───────────────────────────────────────┘

容器：
  ┌──────────────────────────────────────┐
  │  应用 A  │  应用 B  │  应用 C         │
  ├──────────┼──────────┼────────────────┤
  │ 依赖库    │ 依赖库    │ 依赖库          │  ← 只打包应用与依赖
  ├──────────┴──────────┴────────────────┤
  │      Docker Engine                    │
  ├───────────────────────────────────────┤
  │   Host OS（共享同一个内核）              │  ← 复用宿主内核
  ├───────────────────────────────────────┤
  │              硬件                      │
  └───────────────────────────────────────┘
```

| 维度 | 虚拟机 | **容器** |
| :--- | :--- | :--- |
| 隔离级别 | 硬件级（Hypervisor） | **进程级（Namespace + Cgroup）** |
| 操作系统 | 每个虚拟机一套完整 OS | **共享宿主内核** |
| 镜像大小 | GB 级 | **MB 级** |
| 启动时间 | 分钟级 | **秒级甚至毫秒级** |
| 资源开销 | 大 | **接近原生进程** |
| 隔离强度 | **强**（内核级隔离） | 较弱（共享内核） |
| 适合场景 | 强隔离、异构操作系统 | **微服务、多组件环境、CI/CD** |

**核心差异**：容器**共享宿主内核**。这既带来了轻量的优势，也带来了隔离强度弱于虚拟机的局限——内核漏洞可能影响所有容器。

### 2.2 三大隔离机制

容器的隔离并非由 Docker 实现，而是借助 Linux 内核的三项机制：

#### （1）Namespace —— 实现"看不见"

Namespace 让进程只能看到自己所属命名空间内的资源，从而实现视图隔离：

| Namespace | 隔离内容 | 效果 |
| :--- | :--- | :--- |
| **PID** | 进程号 | 容器内进程从 PID 1 开始，看不到宿主进程 |
| **NET** | 网络设备、端口、路由表 | 每个容器有独立的网络栈与 IP |
| **MNT** | 挂载点 | 每个容器有独立的文件系统视图 |
| **UTS** | 主机名与域名 | 容器可拥有独立主机名 |
| **IPC** | 进程间通信 | 隔离信号量与共享内存 |
| **USER** | 用户与用户组 | 容器内 root 可映射为宿主普通用户 |

**本项目中的体现**：8 个容器各自拥有独立的网络命名空间，因此 `kafka` 容器的 9092 端口与 `mongodb` 容器的 27017 端口互不冲突；容器间通过 Docker 创建的虚拟网络（bridge）通信，通过**服务名**互相访问。

#### （2）Cgroup —— 实现"用不了那么多"

Control Group 限制进程组可使用的资源：

| 资源 | 限制项 |
| :--- | :--- |
| **内存** | 上限、软限制、OOM 行为 |
| **CPU** | 权重、配额（`--cpus`）、绑定核心 |
| 块设备 I/O | 读写速率上限 |
| 进程数 | `pids.max` |

**本项目中的体现**：

```yaml
elasticsearch:
  mem_limit: 1g       # 限制 ES 容器最多使用 1 GB 内存
```

配合 JVM 参数 `-Xms512m -Xmx512m`，把 ES 的堆内存限制在堆栈可控范围内。

> **注意**：如果只设 `mem_limit` 而不设 JVM 的 `-Xmx`，JVM 会按"容器可用内存"自动推断堆大小。在容器中运行 Java 应用时，**堆内存与容器内存限制必须同时配置**。

#### （3）UnionFS —— 实现"分层复用"

容器的文件系统采用**联合文件系统（Union File System）**，将多个只读层叠加为一个统一视图：

```text
容器文件系统视图：
  ┌─────────────────────────────┐
  │  可写层（容器层）             │  ← 运行时的修改写在这里
  ├─────────────────────────────┤
  │  应用层（COPY app.jar）      │  ← 镜像层，只读
  ├─────────────────────────────┤
  │  依赖层（RUN mvn package）   │  ← 镜像层，只读
  ├─────────────────────────────┤
  │  基础层（FROM jre）          │  ← 镜像层，只读
  └─────────────────────────────┘
```

**核心机制——写时复制（Copy-on-Write）**：多个容器可以共享同一镜像的只读层，只有当容器需要修改某个文件时，才会将该文件复制到自己的可写层。

**收益**：

| 收益 | 说明 |
| :--- | :--- |
| **镜像分层复用** | 多个镜像共享基础层，节省磁盘 |
| **快速启动** | 无需复制整个文件系统，只需创建可写层 |
| **构建缓存** | Dockerfile 中未变化的层可复用缓存，加速构建 |

**本项目中的体现**：8 个容器分别基于不同镜像，但共享宿主机的存储驱动（overlayfs）。实测 `docker info` 显示存储驱动为 `overlayfs`。

### 2.3 核心概念

| 概念 | 含义 |
| :--- | :--- |
| **镜像（Image）** | 只读模板，包含应用及其全部运行依赖；由 Dockerfile 构建 |
| **容器（Container）** | 镜像的运行实例，可独立启停；在镜像之上加一个可写层 |
| **数据卷（Volume）** | 独立于容器生命周期的持久化存储，由 Docker 管理 |
| **绑定挂载（Bind Mount）** | 将宿主机目录直接挂载进容器，路径由用户指定 |
| **网络（Network）** | 容器间的隔离网络，同一网络内可通过服务名互相访问 |
| **仓库（Registry）** | 镜像的存储与分发服务（如 Docker Hub） |

**数据卷 vs 绑定挂载**（本项目中两种都用到了）：

| | 数据卷（Volume） | 绑定挂载（Bind Mount） |
| :--- | :--- | :--- |
| 路径 | Docker 管理（`/var/lib/docker/volumes/`） | **用户指定**（如 `./nginx/conf.d`） |
| 典型用途 | **数据持久化**（数据库文件） | **配置与代码挂载** |
| 本项目用例 | `mongodb-data`、`kafka-data`、`es-data` | Nginx 配置、前端产物、Mongo 初始化脚本 |

### 2.4 Docker 的架构分层

```text
  ┌──────────────────────────────────┐
  │  docker CLI（用户命令）            │
  └────────────┬─────────────────────┘
               │ REST API
  ┌────────────▼─────────────────────┐
  │  dockerd（Docker Daemon）         │  镜像管理、网络、卷
  └────────────┬─────────────────────┘
               │
  ┌────────────▼─────────────────────┐
  │  containerd（容器运行时管理）       │  容器生命周期
  └────────────┬─────────────────────┘
               │
  ┌────────────▼─────────────────────┐
  │  runc（OCI 运行时）                │  调用内核创建容器
  └──────────────────────────────────┘
```

理解这一分层有助于排查问题：**`docker` 命令只是客户端**，真正干活的是 `dockerd` 与 `containerd`。因此当 Docker 出现异常时，问题可能出在任意一层。

### 2.5 容器编排：Docker Compose

单容器管理很简单，但一个系统往往包含多个容器，且它们之间存在启动顺序与网络依赖。手动逐个 `docker run` 不仅繁琐，还容易出错。

**Docker Compose** 通过声明式的 YAML 文件定义多容器应用：

```yaml
services:
  mongodb:
    image: mongo:8.3.9
    volumes:
      - mongodb-data:/data/db

  platform-service:
    build: ../backend/platform-service
    depends_on: [mongodb, kafka]
    environment:
      SPRING_MONGODB_URI: mongodb://mongodb:27017/uav_platform

volumes:
  mongodb-data:
```

**核心能力**：

| 能力 | 说明 |
| :--- | :--- |
| **服务定义** | 用 YAML 声明所有服务，一处管理 |
| **依赖声明** | `depends_on` 指定启动顺序 |
| **环境变量注入** | 同一镜像适配不同环境 |
| **数据卷管理** | 声明式定义持久化存储 |
| **自动网络** | 自动创建 bridge 网络，服务名即 DNS 名 |
| **一键启停** | `docker compose up -d` / `down` |

**一条命令启动整套环境**：

```powershell
cd deploy
docker compose up -d      # 启动全部 8 个容器
docker compose ps         # 查看状态
docker compose down       # 停止并删除容器（保留数据卷）
docker compose down -v    # 连同数据卷一起删除（重置环境）
```

## 三、技术优缺点分析

### 3.1 优点

**（1）环境一致性。** 镜像封装了应用及其全部依赖，"在我机器上能跑"的问题被根除。本项目涉及六类中间件，容器化从根本上避免了依赖冲突。

**（2）资源开销低、启动快。** 共享宿主内核，无需运行独立操作系统。容器启动在秒级，资源开销接近原生进程。

**（3）版本隔离。** 每个组件运行在独立镜像中，可用不同版本的运行时。例如 HDFS 镜像基于 Java 8，而业务服务基于 Java 17，两者互不影响。

**（4）快速重置与排错。** 容器与数据卷可独立删除重建，`docker compose down -v && docker compose up -d` 即可回到干净状态，这对反复调试极为有利。

**（5）声明式编排。** Docker Compose 让"8 个容器、5 个数据卷、1 个网络"的复杂环境变成一份可版本控制的 YAML 文件，团队成员可一键复现完全相同环境。

**（6）生态丰富。** Docker Hub 上有海量官方与社区镜像，绝大多数中间件都有现成的官方镜像。

**（7）与 CI/CD 天然契合。** 镜像即交付物，构建一次可在任意环境运行。

### 3.2 缺点与局限

**（1）隔离强度弱于虚拟机。** 容器共享宿主内核，内核漏洞可能影响所有容器；且容器内的 root 用户（若未启用 User Namespace）在宿主上也是 root，存在安全风险。

**（2）只支持 Linux 容器（本质）。** Windows 与 macOS 上运行 Linux 容器需要一层虚拟化（Windows 用 WSL2 或 Hyper-V，macOS 用轻量 VM）。这意味着**在这些平台上 Docker 的性能与资源表现受虚拟化层限制**。

**（3）网络与存储的行为差异。** 绑定挂载在不同平台上的行为不一致（文件权限、大小写敏感性、文件监听机制），跨平台开发时容易踩坑。

**（4）持久化与备份需要额外设计。** 容器本身是无状态的（删除即丢失可写层），数据必须放在数据卷中。数据卷的备份与恢复需要额外工具。

**（5）调试难度增加。** 应用运行在容器内，日志、网络、文件系统的排查都需要通过 `docker exec`、`docker logs` 等命令间接进行，不如直接在宿主机调试直观。

**（6）资源限制容易配置不当。** 内存、CPU 限制不配置会导致容器互相争抢；配置不当则会导致应用 OOM 或性能受限。**在容器中运行 JVM 应用时尤其需要注意堆内存的配置**。

**（7）Docker Compose 的能力边界。** Compose 只适合**单机编排**。跨主机的调度、自愈、滚动更新、服务发现等能力需要 Kubernetes 等编排系统。

**（8）镜像体积与构建速度。** 若不注意 Dockerfile 的分层优化，容易产生体积臃肿、构建缓慢的镜像。

## 四、适用场景与同类技术对比

### 4.1 适用场景

| 场景 | 判断依据 |
| :--- | :--- |
| **多组件开发环境** | 需同时运行多种中间件，本地安装繁琐 |
| **微服务部署** | 每个服务独立打包、独立伸缩 |
| **CI/CD 流水线** | 构建产物即镜像，环境一致 |
| **快速验证与学习** | 一条命令拉起重型中间件（如 ES、Kafka） |
| **单机多服务编排** | Docker Compose 可满足 |

### 4.2 不适合的场景

| 场景 | 原因 | 更适合的方案 |
| :--- | :--- | :--- |
| 需要强隔离的多租户环境 | 隔离强度弱于虚拟机 | 虚拟机、Kata Containers |
| 跨主机的容器编排 | Compose 只支持单机 | Kubernetes、Swarm |
| 需要运行异构操作系统 | 容器共享宿主内核 | 虚拟机 |
| 对性能有极致要求的场景 | 存在虚拟化与网络转发开销 | 物理机部署 |
| Windows 原生应用 | 容器以 Linux 为主 | 虚拟机或原生部署 |

### 4.3 同类技术对比

| 维度 | **Docker** | Podman | containerd | Kubernetes |
| :--- | :--- | :--- | :--- | :--- |
| 定位 | 容器引擎 + 工具链 | 容器引擎（无守护进程） | 容器运行时 | 容器编排平台 |
| 架构 | 客户端-守护进程（C/S） | **无守护进程（daemonless）** | 底层运行时 | 集群编排 |
| Root 权限 | 需要 daemon 以 root 运行 | **支持 rootless** | 需要 | 需要 |
| 编排能力 | **Docker Compose（单机）** | Podman Compose | 无 | **完整集群编排** |
| 自愈与滚动更新 | 无 | 无 | 无 | **有** |
| 服务发现 | 服务名 DNS（单机） | 同 Docker | 无 | **完整** |
| 学习曲线 | 低 | 低 | 中 | **陡** |
| 适用规模 | 单机 | 单机 | 被上层调用 | 集群 |
| 生态成熟度 | **最高** | 中 | 高（底层） | **最高**（集群场景） |

**选型要点**：

- **单机开发环境、学习与快速验证** → **Docker + Compose**（本项目选择）；
- **对安全性要求高、需要 rootless** → Podman；
- **生产集群、需要自愈与弹性伸缩** → Kubernetes；
- **只是需要一个底层运行时** → containerd。

### 4.4 关于"容器化 vs 本地安装"的讨论

本项目涉及六类中间件，若不使用容器，需要在本地逐个安装配置。两种方式的对比：

| 维度 | 本地安装 | **容器化** |
| :--- | :--- | :--- |
| 初始搭建耗时 | 每个组件数小时 | **一条命令** |
| 版本冲突风险 | 高（如 Java 版本、端口冲突） | **低（完全隔离）** |
| 环境复现 | 需详细文档 + 手工操作 | **一份 YAML 文件** |
| 重置成本 | 需手工清理（注册表、服务、文件） | **`down -v` 一条命令** |
| 团队协作 | 每人环境可能不同 | **完全一致** |
| 学习成本 | 需了解各组件安装细节 | 需额外学 Docker |
| 性能开销 | 无 | 轻微（网络与存储转发的开销） |

**结论**：对于本项目这类"多组件、需反复调试、需要团队协作复现"的场景，**容器化是明确更优的选择**。课程指导说明书也明确建议"统一使用 Docker 镜像规避版本冲突"。

## 五、在本项目中的实践

### 5.1 部署形态

本项目采用 **Docker Compose 单机编排 8 个容器**：

| 容器 | 镜像 | 角色 |
| :--- | :--- | :--- |
| `hadoop-namenode` | bde2020/hadoop-namenode:3.2.1 | HDFS 元数据节点 |
| `hadoop-datanode` | bde2020/hadoop-datanode:3.2.1 | HDFS 数据节点 |
| `mongodb` | mongo:8.3.9 | 分布式数据库 |
| `kafka` | apache/kafka:4.3.1 | 消息中间件（KRaft） |
| `elasticsearch` | elasticsearch:9.5.3 | 检索引擎 |
| `kibana` | kibana:9.5.3 | 检索可视化 |
| `platform-service` | 本项目 Dockerfile 构建 | 业务服务 |
| `nginx-gateway` | nginx:1.30-alpine | 网关 |

**一个关键设计：设备仿真端不容器化。**

仿真端（`device-simulator`）代表园区中真实的无人机与机器狗，属于**系统外部设备**，因此在宿主机上作为独立进程运行。若将它也放进容器，则"设备经消息中间件接入平台"的架构语义就不成立了。

**运行环境**：Windows 11 + Docker Desktop（WSL2 后端），分配 28 CPU + 8 GB 内存。

### 5.2 遇到的问题与解决方案

#### 问题一：镜像拉取失败——DNS 污染

**现象**：执行 `docker compose up -d` 时，所有镜像拉取均失败，报错形如：

```text
Error response from daemon: Get "https://registry-1.docker.io/v2/": dial tcp 127.0.0.1:443: connect: connection refused
```

**排查过程**：

1. 在宿主机上用浏览器访问 `https://registry-1.docker.io/v2/`，可以正常返回；
2. 在容器内测试同一个域名，解析结果异常；
3. 检查 DNS 解析结果，发现 `registry-1.docker.io` 被解析到了 `127.0.0.1`。

**根因分析**：

这是一个典型的 **DNS 污染**问题。Docker 容器默认继承宿主机的 DNS 配置，而某些网络环境下，`registry-1.docker.io` 域名会被解析到本地回环地址 `127.0.0.1`，导致连接被拒绝。

值得注意的是：**在宿主机浏览器中可以访问，但在容器中不行**——因为浏览器可能使用了代理或不同的 DNS 解析路径，而容器直接使用了被污染的 DNS 结果。这种"宿主机能通、容器不通"的现象很有迷惑性。

**解决方案**：

分两步解决：

**① 配置公共 DNS**，在 Docker Desktop 的设置中指定：

```text
DNS: 223.5.5.5        （阿里公共 DNS）
     119.29.29.29      （腾讯公共 DNS）
```

**② 配置镜像加速器**，在 `daemon.json` 中添加：

```json
{
  "registry-mirrors": [
    "https://docker.m.daocloud.io",
    "https://dockerproxy.com"
  ]
}
```

> **实践提示**：镜像加速器地址会随时间变化，部分公共加速器可能失效或被限制。当配置了加速器仍失败时，应尝试更换其他可用的镜像源，或检查该加速器当前的可用性。

**经验总结**：

> **"宿主机能访问、容器不能访问"是容器网络问题的典型症状。**
>
> 排查时应先在容器内部测试网络连通性（`docker exec <容器> ping/curl`），而不是想当然地认为"宿主机能通容器就一定能通"。容器有自己的网络命名空间与 DNS 解析路径，两者可能完全独立。

#### 问题二：修改配置后容器行为未变

**现象**：修改了后端代码并执行 `docker compose up -d --build platform-service`，构建过程显示成功，但容器内的应用行为仍是旧版本。

**排查过程**：

1. 确认镜像确实重新构建了（构建日志显示编译成功）；
2. 执行 `docker images` 查看镜像的创建时间，确认是最新的；
3. 执行 `docker ps` 查看容器状态，发现容器的 `STATUS` 显示为 `Up 3 hours`——**容器并未重启**。

**根因分析**：

Docker Compose 的 **`--build` 参数只重建镜像，不重建容器**。若容器的配置未发生变化，Compose 会认为现有容器仍然可用，直接复用它，因此容器内运行的仍是旧镜像的代码。

这是一个容易产生误导的现象：**构建日志显示成功，但改动没有生效**。

**解决方案**：

使用 `--force-recreate` 强制重建容器：

```powershell
docker compose up -d --build --force-recreate platform-service
```

**同类问题的另一个表现**：Nginx 的配置文件是以**绑定挂载**方式挂进容器的。修改配置文件后，若只是重启容器，Nginx 仍会读取挂载目录中的新文件——但由于 Nginx 只在启动时读取配置，因此需要显式重载：

```powershell
docker exec nginx-gateway nginx -s reload
```

**经验总结**：

> **Docker 中"改代码/改配置后如何生效"因改动类型而异，必须区分清楚**：

| 改动类型 | 生效方式 |
| :--- | :--- |
| 后端代码（镜像内） | `--build --force-recreate` |
| Nginx 配置（绑定挂载） | `nginx -s reload` |
| 前端产物（绑定挂载） | 重新构建前端即可（Nginx 直接读取） |
| `docker-compose.yml` | `docker compose up -d` |

#### 问题三：内存配额与容器的资源争抢

**现象**：系统运行一段时间后，部分容器变得不稳定，响应变慢。

**排查过程**：

1. 执行 `docker stats` 查看各容器资源占用，发现：

```text
NAME               MEM USAGE / LIMIT     MEM %
elasticsearch      1020MiB / 1GiB        99.59%
kibana             922MiB / 1GiB         90.04%
kafka              1.066GiB / 7.639GiB   13.96%
mongodb            251.7MiB / 7.639GiB   3.22%
...
```

2. 发现只有 `elasticsearch` 与 `kibana` 设置了内存上限（`mem_limit: 1g`），其余 6 个容器的 LIMIT 显示为宿主机的总配额（7.639 GiB）。

**根因分析**：

项目在不使用 Docker 时，各组件默认配置是基于"独占整台机器"的假设：

- **Elasticsearch**：JVM 默认堆大小为可用内存的 1/4，WiredTiger 缓存默认为可用内存的一半；
- **MongoDB**：WiredTiger 缓存默认为可用内存的一半；
- **Kafka**：JVM 堆按默认策略推断。

在 8 GB 的共享配额下，这些"独占假设"会相互冲突。**本项目已对 ES 与 MongoDB 做了限制**（ES 设 `mem_limit: 1g` + `ES_JAVA_OPTS=-Xms512m -Xmx512m`，MongoDB 设 `--wiredTigerCacheSizeGB 0.5`），但其余容器**尚未设置内存上限**。

**风险**：任何单个未限制的容器内存失控，都会挤占其他容器的内存，甚至导致整机内存耗尽。

**解决方案（规划中）**：

为所有容器补上内存限制：

```yaml
kafka:
  mem_limit: 2g
  environment:
    KAFKA_HEAP_OPTS: "-Xmx1g -Xms1g"     # 显式限制 JVM 堆

hadoop-namenode:
  mem_limit: 1g

hadoop-datanode:
  mem_limit: 1g

platform-service:
  mem_limit: 1g
```

**关键点——容器内存限制与 JVM 堆必须同时配置**：

> 只设 `mem_limit` 而不设 `-Xmx` 时，JVM 会按"容器可用内存"自动推断堆大小（JDK 10+ 已支持容器感知）——但推断值可能仍然偏大，因为堆之外还有元空间、线程栈、直接内存等开销。
>
> 合理的做法是：**容器内存限制 = JVM 堆上限 × 1.5 ~ 2 倍**，为堆外内存留出余量。

**经验总结**：

> **容器化不是"把应用塞进容器就完事"，资源限制是必须显式配置的一环。**
>
> 中间件在裸机环境下都会基于"独占机器"的假设自动配置资源池。放入共享配额的容器环境后，这些默认值会相互冲突，**必须逐一显式限制**。

#### 问题四：宿主机休眠后容器全部暂停

**现象**：开发过程中，机器休眠（或长时间未操作）后唤醒，执行 `docker exec` 报错：

```text
Error response from daemon: Container mongodb is paused, unpause the container before exec
```

进一步执行 `docker ps` 发现**所有容器状态均为 `Up N hours (Paused)`**。

**排查过程**：

1. 执行 `docker unpause mongodb`，恢复成功；
2. 但其他容器仍处于暂停状态；
3. 执行 `docker unpause $(docker ps -q)` 批量恢复，其中有一个容器报 `is not paused`（因为它已被上一步恢复）。

**根因分析**：

当宿主机进入休眠状态时，Docker Desktop 的 WSL2 虚拟机会被挂起，其中的所有容器随之进入暂停状态。唤醒后，容器**不会自动恢复**，需要手动 `unpause`。

**解决方案**：

```powershell
# 批量恢复所有暂停的容器
docker unpause $(docker ps -q --filter status=paused)
```

**经验总结**：

> **这是开发环境的常见现象，不是容器或应用的故障。**
>
> 遇到"容器在跑但命令执行失败"时，应**先看 `docker ps` 的状态列**，确认容器是真的在运行、还是处于 `Paused`、`Restarting`、`Exited` 等状态。直接看状态列往往能快速定位问题，比翻日志高效得多。

#### 问题五：绑定挂载阻止了构建工具清理目录

**现象**：前端项目执行 `npm run build` 后，发现 `dist/assets/` 目录下**累积了十几个历史构建产物**（每次构建的 JS 文件都保留着），目录体积不断增长。

**排查过程**：

1. 确认 Vite 默认配置会在构建前清空输出目录（`emptyOutDir` 默认为 true）；
2. 手动检查目录，确认旧文件确实没有被删除；
3. 回顾容器配置，发现 Nginx 容器以绑定挂载方式占用了该目录。

**根因分析**：

```yaml
nginx:
  volumes:
    - ../frontend/dist:/usr/share/nginx/html:ro    # ← 绑定挂载
```

Nginx 容器通过绑定挂载占用了 `frontend/dist` 目录。在 Windows + Docker Desktop 的环境下，**被容器挂载的宿主机目录会处于被占用的状态**，导致宿主机的构建工具在尝试删除该目录下的文件时失败（且失败是静默的，Vite 不报错）。

**影响**：虽然 `index.html` 始终引用最新的构建产物，功能不受影响，但目录中会累积大量无用文件。

**解决方案**：

构建前先停止占用该目录的容器：

```powershell
cd deploy
docker compose stop nginx
cd ../frontend && npm run build
cd ../deploy && docker compose start nginx
```

**经验总结**：

> **绑定挂载让宿主机与容器共享目录，但共享也意味着约束。**
>
> 容器对该目录的占用会影响宿主机对它的操作（删除、重命名等）。这类问题在两个平台上表现不同（Linux 上通常无此问题），属于**跨平台行为差异**的典型例子。

## 六、总结与体会

通过本项目的实践，我对 Docker 的认识从"一个打包工具"深化为"一套基于内核特性的进程隔离方案"。

**三点主要收获**：

**第一，理解了容器的本质是"内核特性的组合应用"。** Docker 本身并不实现隔离——隔离由 Namespace（看不见）、Cgroup（用不了那么多）、UnionFS（分层复用）三项内核机制共同提供。Docker 的价值在于**把这些底层机制封装成了易用的工具链**。理解这一点后，许多现象（为什么容器共享内核、为什么镜像能分层复用、为什么内存限制要单独配置）都能从原理上解释清楚。

**第二，认识到"容器化"不等于"零配置"。** 中间件在裸机环境下基于"独占机器"的假设自动配置资源池，放进共享配额的容器环境后会相互冲突。因此**内存限制、JVM 堆大小等参数必须显式配置**。本项目实测 8 个容器空载已占 5.7 GiB（占 8 GiB 配额的 71%），其中 Elasticsearch 容器占用率达 99.6%——这正是"默认配置不适配容器环境"的直接体现。

**第三，积累了容器环境的排查方法。** 本项目遇到并解决了五类问题：DNS 污染导致的镜像拉取失败、`--build` 不重建容器、内存配额争抢、宿主机休眠导致容器暂停、绑定挂载阻止目录清理。这些问题的共同特点是：**它们都不是应用代码的问题，而是容器环境本身的特性**。排查这类问题的关键，是建立"先看容器状态、再看容器日志、最后看应用日志"的分层排查习惯。

> **一点延伸思考**：本项目只用到 Docker Compose 的单机编排能力。当系统规模增长、需要跨主机调度、自愈、滚动更新时，就需要引入 Kubernetes。但**Compose 与 K8s 的核心概念是一脉相承的**——服务定义、依赖、环境变量、数据卷、服务名 DNS，这些在本项目中建立的认知，可以平滑迁移到 K8s 的 Deployment、Service、ConfigMap、PersistentVolume 等概念上。
